# simulation 设计：经营事实、事件与会计结果

本文规定仿真模块的目标结构与算法接线方式。目录目前仅有文档，类型名与模块划分属于拟议实现；本文件不证明功能已经完成。统一接口及简单模式见[完整设计蓝图](../../../../../../agents/remaining-questions-and-features/q14-financial-model-design.md)，本文件专注 `simulation`。

没有财务或编程基础时，可以先读第 1 节的概念，再读第 5～7 节的公式，最后按第 10.12 节把一家公司的一个月从头算到尾。第 2、8、11 节主要解释代码如何实现这些规则。

公式借鉴附件的英文命名方式，用完整英文标识表达概念，公式后紧接中文解释、单位及数字例子。正文继续使用中文。所有演示数字均为虚拟假设，不能当成真实公司数据或已经确定的游戏参数；借鉴公式写法不表示照搬附件中未经核验的公司数字或会计简化。

## 1. 建模思想

模型依次回答四个问题：市场需要什么，公司能够做什么，公司实际做了什么，这些行为怎样影响财务。收入、利润和现金余额由不同事实形成，不能互相替代。

```text
公共环境与行业需求
        ↓
公司报价、订单与经营决策
        ↓
资源约束下的生产、研发、项目或金融业务
        ↓
交付、债权债务与实际收付款
        ↓
会计分录、经营状态与财务报告
        ↓
约束以后期间的经营决策
```

行业决定业务链，参数决定响应方式，状态保留过去的影响，决策决定当前行动。随机性作用于需求、成本、交付或项目结果，不在财报生成后随机改利润。

品牌、技术、客户关系和研发管线可以影响未来业务，但不自动成为账面资产。成长、周期、研发等特征可以叠加，并随事实变化；同属半导体行业的设备公司和晶圆厂也需要不同业务过程。

### 1.1 先分清这些词

| 概念 | 日常含义 | 在模型中怎样使用 |
| --- | --- | --- |
| 参数 | 做事的规则，例如每件产品需要多少工时 | 配置输入，先说明单位和适用条件 |
| 状态 | 现在实际有什么，例如库存 20 件、现金 1 万元 | 保存并随已发生事件更新 |
| 决策 | 打算做什么，例如计划生产 80 件 | 必须通过资源检查，计划不等于完成 |
| 事件 | 已经发生什么，例如交付 90 件、收到 6,000 元 | 改变相关状态并产生记账依据 |
| 需求 | 客户可能想买多少 | 需要分配、承接和履约，不是已完成销售 |
| 产能 | 一段时间最多能完成多少生产 | 是生产上限，不是保证有人买 |
| 库存 | 已经拥有、尚未交付的货 | 只有符合可售条件的部分才能交付 |
| 收入 | 满足确认条件后，这次业务算卖了多少钱 | 可以先有收入、以后才收到钱 |
| 成本与费用 | 为已实现业务或当期活动消耗的资源 | 有些先付款后计入，有些先发生后付款 |
| 利润 | 按相同期间口径计算的收入与各项损益之差 | 不等于银行账户增加的钱 |
| 应收账款 | 客户还欠公司的钱 | 是公司的资产，但不能当现金立即支付 |
| 应付账款 | 公司还欠别人的钱 | 是公司的负债，付款后才减少 |
| 现金流 | 某段时间实际收到和付出的钱 | 收到减付出等于该范围内的现金净变化 |
| 权益 | 公司资产扣除负债后的账面剩余 | 不是一份额外可花的现金 |

“确认收入”需要满足对应业务的会计条件，不是“创建订单就算收入”。本文普通货物例子假定交付时条件全部满足；项目、银行、保险仍使用各自规则。

### 1.2 怎样读公式

- `min(80, 100)` 表示取较小值，结果为 80；常用来表达资源不足时只能做多少。
- `max(0, Value)` 表示在零与 `Value` 之间取较大值；只在定义允许如此处理时使用，不能用来掩盖非法负现金。
- `Σ` 表示逐项相加，例如总收入是每种产品收入相加。
- `×`、`÷` 分别表示乘和除；20% 在计算时是 0.20，万分之二是 0.0002。
- 下标 `t` 表示本期，`t-1` 表示上期；本期必须明确是一日、一月还是一年。下标 `product`、`option`、`contract` 分别指产品、需求选项、合同，不是相乘。
- `Opening` 表示期初，`Closing` 表示期末；`Before` 与 `After` 表示某个事件发生前后，不一定跨月。
- “元／件 × 件 = 元”，“兆瓦 × 小时 = 兆瓦时”；单位不匹配就不能直接相乘、相加。

例如 `Revenue` 读作“营业收入”，`CashBalance` 读作“现金余额”。不用先记住全部单词，每个公式后都会解释本节所需标识。`Revenue` 在代码里可对应 `revenue`，`CashBalance` 可对应 `cash_balance`；统一使用同一词根，不把收入、利润、现金都命名为含义不清的 `value`。

文中的 `=` 通常表示“用右边算左边”，不是要求把一份事实存两次。例如利用率由产量和产能算出，不再单独随机生成。`≤` 表示“不超过”，是需要校验的约束；箭头只表示因果或步骤，不意味着一个变量等于另一个变量。

最基础的两条核对关系是：

$$
\mathrm{Assets} = \mathrm{Liabilities} + \mathrm{Equity}
$$

$$
\mathrm{ClosingCash}
= \mathrm{OpeningCash} + \mathrm{CashReceipts} - \mathrm{CashPayments}
$$

| 英文标识 | 中文含义 | 单位与取值口径 |
| --- | --- | --- |
| `Assets` | 资产 | 元，同一日期、同一报告范围的账面金额 |
| `Liabilities` | 负债 | 元，与资产同口径 |
| `Equity` | 权益，即账面净资产 | 元，可以为负；不是可用现金 |
| `OpeningCash` / `ClosingCash` | 期初／期末现金 | 元，同一主体、同一现金范围 |
| `CashReceipts` / `CashPayments` | 期间实际收款／付款 | 元，只含已经执行的现金变动 |

第一条看公司拥有什么、欠什么以及剩余多少；第二条只看现金进出。利润通过经营及会计过程影响权益，不能直接替代第二条里的实际收付款。

比如期初现金 100 元，本期收到 30 元、支付 20 元，期末现金就是 110 元；即使本期确认利润 50 元，也不能把期末现金改成 150 元。现金核对式假设同一币种且没有另列的汇兑、范围调整等项目；存在这些项目时必须显式列出并核对，不能塞进经营收付款。

为便于手算，金额例子用元。实现时 `AccountingAmount` 内部用 `i128` 分、wire 用元字符串；市场 `Money` 内部用 `i64` 分、wire 用分字符串。英文公式不是采用浮点金额的理由：比例、舍入、累计余数沿用明确的精确计算规则，金额互转必须检查范围。金额可为负不等于任何科目都允许负余额；现金不足不能用负现金补平。

## 2. 代码封装与状态归属

目标父层是 `company/`，以 `CompanySystem` 统一基本面查询、能力、披露及保存恢复入口，内部选择 `simple/` 或 `simulation/`。`environment` 只是环境模块，不代表整个公司系统。本文暂留在现有 `company/economy/system_sim/` 路径；目录迁移与代码接线另行实施，不能把目标布局当作当前代码状态。

`simple/` 按可配置的月、季度、半年或年度结算周期调整营收和开支，再推算利润及完整财务结果；ROE 由共同指标层按适用 A 股口径计算，不作为生成参数。默认采用持续一段自然时间的趋势加小幅随机波动，营收和开支分别配置年化趋势。在趋势不变的期间，换算公式为：

$$
\mathrm{PeriodGrowth}
=(1+\mathrm{AnnualGrowth})^{\mathrm{PeriodMonths}/12}-1
$$

`AnnualGrowth` 是年化增长率（12% 写作 0.12）；`PeriodMonths` 是期间月数（月、季度、半年、年分别为 1、3、6、12）；`PeriodGrowth` 是未加入扰动的期间增长率。年化 12% 对应月度约 0.949%、季度约 2.874%、半年约 5.830%、年度 12%。公式只换算增长趋势，不规定扰动分布；随机波动的幅度及跨周期聚合仍需明确。趋势持续时间按自然时间表达，期间内趋势变化按持续时间分段复合；季度营收与上一季度比较，不能拿月营收乘季度增长系数冒充季度营收。

简单模式不必建立具体客户、生产或研发过程，基本面结算也不等于报告公开；公开排期仍由共同披露机制处理。`simulation/` 则拥有本节以后介绍的经营链，本节对简单模式周期的配置不改写仿真模块的月度经营计划。两种模式对上层支持相同的查询、报告、披露与股本行为，内部数据结构可以不同，不能仅因选择简单模式而缺少功能。

简单模式的公司财务是汇总账面生成模型，不追踪真实公司资金来源；此前 `SyntheticFunding`、补款周期和额度提案已取消。分红、配股、增发及回购计划由各公司可配置的行为偏好结合财务条件生成，再经共同规则执行。投资者资金与股份保持真实、唯一、幂等和原子，认购检查投资者本人现金，涉及撮合的回购仍须真实成交；公司报表现金不作为简单模式分红的实际付款预算。这个简化不适用于本文仿真模式的有限现金约束。完整简单模型、期间计算和待补充的参数细节见设计蓝图第二章。

目标依赖为 `session → company → 所选实现`，两种模式复用 `accounting` 与共同结算规则。上层不得绕过入口修改内部状态，两个实现不互相调用。共同身份不强制携带仿真专属账套和合同；简单模式可以用汇总事件及账簿提供完整财务结果，无需创建完整经营网络。

### 2.1 仿真实现的目录边界

后续仿真专属实现全部收敛在 `simulation/`，使其能够作为同一 Git 仓库中的独立开发单元。按以下边界安排代码：

| 变更内容 | 所属位置与要求 |
| --- | --- |
| 环境、行业、公司决策和业务过程 | 目标 `company/simulation/` 及其子目录；不向父层添加经营公式 |
| 仿真参数、状态、随机事件及内部类型 | 本目录；父层不逐项了解新增行业字段 |
| 客户资金、研发、生产和跨主体结算算法 | 本目录；调用共享领域服务，不在旧入口继续新增仿真实现 |
| 仿真状态导出和恢复校验 | 本目录的 `persistence.rs`；父层只封装模式和调用入口 |
| 单元测试、模块间场景及 fixture | 本目录的模块测试或 `tests/`、`fixtures/`；不依赖另一任务的临时数据 |
| 示例、参数说明及模型设计 | 本目录；入口维护在 `README.md`，机制维护在 `DESIGN.md` |
| 共同模式分派、公共查询和宿主协议 | 父层及原有适配层；只有确实改变公共契约时才修改 |
| 仿真账套、行业子账和财务接线 | `simulation/finance/`；通过引用关联业务状态，调用唯一的会计算法 |
| 通用金额、会计及报表算法 | 两种模式复用 `accounting/`，简单模式不必建立细粒度经营子账 |
| 公司身份、发行人映射及真正共用的规则 | 保留共同领域边界；不包含强制财务或客户状态 |
| 仿真到期事项与事件调度 | 仿真内部复用现有算法；不让简单模式依赖贷款、客户等专属事件 |

新增行业原则上只修改本目录内的实现和注册位置。一般模型参数增加或内部状态调整，不应要求修改 `simple/`、UI 或父层业务逻辑；确需改变公开字段或严格存档校验时，单独说明跨层影响并同步消费者，不能为减少冲突跳过契约更新。

本设计不创建嵌套 Git 仓库、submodule 或新的工作区。同一仓库按路径划分提交范围，便于独立开发；共同契约和共享文件仍可能发生冲突，不能承诺物理隔离。首次迁移需要同步修改旧调用方，但迁移后不保留散落在旧目录的另一套仿真实现或兼容入口。

### 2.2 状态结构

```text
CompanySimulation
    EnvironmentState           公共环境与随机状态
    IndustryState[]            行业需求池及市场结构
    OperatingState[CompanyId]  公司与业务单元的持续状态
    CompanyFinance             账套与行业子账的唯一状态所有者
    CustomerState[]            轻量客户状态及债务引用
    PendingEvents              尚未执行的经营事件
    ProcessedFacts             防止重复生效所需的业务事实
```

上述名称为设计示意。实现应优先使用既有 `CompanyId`、会计金额、账簿、债务与调度类型，不为改目录重复创造同义类型。

| 数据 | 唯一负责位置 | 不允许的重复状态 |
| --- | --- | --- |
| 公司现金、资产、负债、权益 | 既有账簿与子账 | 再设一个可独立增加的经营现金字段 |
| 产品、产能、工时、库存批次 | 对应业务模块，与库存／固定资产子账对接 | 物理数量和账面数量各自随机演化 |
| 研发项目、品牌和技术 | `research/` 及对应经营状态 | 把经营评分直接加入资产负债表 |
| 客户现金及债务 | `customers/`，复用现有客户账务事实 | 每个债权公司各复制一份客户余额 |
| 月度计划与执行进度 | 对应公司状态 | 保存为已实现收入或公开业绩 |
| 利润、利用率、杠杆率 | 从账簿和经营事实派生 | 再抽一个比率覆盖真实结果 |

各模块持有必要事实，查询视图和缓存可重建。`CompanyFinance` 是职责示意，可直接组织既有行业账套；不要求包一层新类型，更不复制账簿。共享客户由一个所有者更新；跨公司处理通过事件引用协调。

例如一家公司欠客户应退款时，财务模块记录债务事实，经营模块通过同一事件引用它；不是双方各留一份可独立修改的“真实债务”。客户系统同样只负责有限现金和偿付，不递归创建完整上市公司。

## 3. 配置和初始化

初始化按以下顺序进行：

1. 选择公司业务单元与适用的行业会计处理器。
2. 校验行业、产品、区域、数量、金额和时间单位。
3. 建立现金、设备、库存、项目及债务等期初事实，说明相应资金来源。
4. 建立品牌、技术、渠道和研发阶段等非账面状态。
5. 构造一致的期初账簿与子账，检查资产等于负债加权益。
6. 安装合同、到期事项和随机状态，开始自然日推进。

净资产不能唯一决定产能、品牌或销售能力。场景可以提供成套配置，但不能用统一资产倍数推导所有行业收入。

参数必须说明单位、作用对象和合法范围。例如增长率说明月度还是年度，产能说明产品单位／期间，信用风险区分概率与预期损失。具体默认数字采用明确标注的虚拟假设，不从真实案例中直接复制。

## 4. 时间推进和事件生命周期

月度更新慢状态，自然日执行业务。沿用 `CivilClock` 与日结 candidate，不在每个证券交易 tick 扫描全部公司。

```text
月初：公共环境 → 行业需求 → 公司计划
每日：到期事件 → 业务履约 → 收付款 → 会计过账
期末：计量与结账 → 报表与解释 → 按披露安排发布
日终成功：提交当前状态 → 生成持久存档候选
```

月度计划仅使用此前已知状态。月末才完成的产出、回款和信息，不能提前支持月初交付或付款。

业务事件需要具有稳定来源标识、发生日期、公司／交易对手、业务引用、数量或金额及因果引用。生命周期为“提出 → 校验 → 在候选状态执行 → 过账并提交”，接受计划不等于已经执行。

同一业务事件重试不得重复收入、付款或研发投入。未发生的计划可取消；已发生事实的更正应通过明确的更正流程，不直接删除历史收付来重抽结果。

## 5. 环境、竞争与经营计划算法

### 5.1 需求池

按行业、产品和区域建立需求池。对适用的产品：

$$
\begin{aligned}
\mathrm{DemandGrowth}_{t}
&= \mathrm{GrowthPersistence}\times\mathrm{DemandGrowth}_{t-1}
 + \mathrm{DemandShock}_{t} \\
\mathrm{MarketActivity}_{t}
&= \mathrm{MarketActivity}_{t-1}\times(1+\mathrm{DemandGrowth}_{t}) \\
\mathrm{IndustryDemand}_{t}
&= \mathrm{MarketActivity}_{t}\times\mathrm{AdoptionRate}_{t}
 \times\mathrm{UnitsPerActivity}_{t}
\end{aligned}
$$

| 英文标识 | 中文含义与输入来源 | 单位／范围 |
| --- | --- | --- |
| `DemandGrowth` | 基础活动量的月度变化率，从上期状态与本期冲击计算 | 无量纲，不低于 -1 |
| `GrowthPersistence` | 上月变化率延续多少，由配置给定 | 本候选关系使用 0～1 |
| `DemandShock` | 本月新增的有界行业扰动，来自可复现随机流或明确事件 | 变化率增量，如 0.01 为 1 个百分点 |
| `MarketActivity` | 本月基础活动总量，如汽车市场候选购车量 | 本月的辆数，不是公司销量 |
| `AdoptionRate` | 目标技术在基础活动中的采用比例 | 0～1，无量纲 |
| `UnitsPerActivity` | 每单位活动需要的产品数量 | 如千瓦时／辆 |
| `IndustryDemand` | 本月行业候选产品需求 | 如本月的千瓦时数 |

行业周期可用扩张、减速、收缩、修复的持续状态表达，阶段影响需求或成本，不规定净利润方向。技术渗透、市场总量与公司份额分别计算；已是新能源车数量的输入不能再次乘新能源比例。

这里“行业需求变化”是相对于上月的变化率，“持续系数”表示上月变化保留多少，“冲击”表示本月新增的变化。三者的输入范围要在配置中校验；增长率不能小于 -100%，数量不能变成负值。

**按数字计算一次：** 上月基础活动量为 1,000 辆／月，上月变化率为 2%，持续系数为 0.5，本月冲击为 +1 个百分点：

$$
\begin{aligned}
\mathrm{DemandGrowth}_{t} &= 0.5\times0.02+0.01 = 0.02 \\
\mathrm{MarketActivity}_{t} &= 1{,}000\times(1+0.02)=1{,}020 \\
\mathrm{IndustryDemand}_{t} &= 1{,}020\times0.20\times50=10{,}200
\end{aligned}
$$

三行分别得到本月增长率 2%、活动量 1,020 辆、需求 10,200 千瓦时。采用比例为 20%、单车用量为 50 千瓦时，尚未考虑公司份额。

这一步只更新行业需求池，尚未决定哪家公司卖出多少，也没有产生收入。若本月冲击改为 -3 个百分点，则本月变化率为 -2%，活动量为 980 辆；公司是否亏损，还取决于后续份额、交付和成本。

### 5.2 报价和分配

公司根据前期成本、库存、竞争和定价政策提出报价。用定义明确的价格、质量、品牌与渠道响应形成非负吸引力权重，在同一需求池内归一化分配，保留外部供应和不购买选项。

整数需求使用最大余数法分配；余数相同时按稳定业务标识处理。候选需求经过订单条件和交付能力校验后才能成为实际业务。实际市占率由真实销量另算，不能将意向需求直接写成收入。

把“归一化”展开，就是除以所有选项的权重之和：

$$
\begin{aligned}
\mathrm{TotalWeight} &= \sum_{\mathrm{option}}\mathrm{AttractionWeight}_{\mathrm{option}} \\
\mathrm{DemandShare}_{\mathrm{option}}
&= \frac{\mathrm{AttractionWeight}_{\mathrm{option}}}{\mathrm{TotalWeight}} \\
\mathrm{CandidateDemand}_{\mathrm{option}}
&= \mathrm{IndustryDemand}\times\mathrm{DemandShare}_{\mathrm{option}}
\end{aligned}
$$

`AttractionWeight` 是报价、质量等响应得到的非负吸引力权重，`TotalWeight` 是所有选项权重之和，二者不代表金额。`DemandShare` 是该选项的候选需求占比，无量纲；`CandidateDemand` 是舍入前候选数量，与 `IndustryDemand` 使用相同产品单位。此处 `option` 包括公司、外部供应者和“不购买”。

**例子：** 行业有 100 件需求，公司甲、公司乙和“不购买”的权重分别为 6、3、1。总权重为 10，因此甲得到 60 件候选需求，乙得到 30 件，还有 10 件不购买。权重只是相对吸引力，不是元、产能或现实统计概率；其价格、质量等来源须在配置中说明。总权重为零时明确全部未分配，不能除以零或偷偷平均分配。

如果需求只有 7 件，直接计算得到 4.2、2.1、0.7 件，不能制造小数件。先分配整数部分 4、2、0，余下 1 件分给小数余数最大的“不购买”项，最终为 4、2、1。这就是最大余数法；“不购买”项的分配表示这部分需求未转为订单。

报价会先改变权重，再改变候选需求。不能在提高单价时仍强制保留原销量，否则会变成无成本提价。

权重的响应函数及默认参数尚需明确配置，这几条式子只规定怎样分配已有权重，不声称已经给出完整竞争模型。计算结果写入候选需求；后续合同与交付事件才可能形成收入。

### 5.3 资金和资源计划

已有到期普通债务先按原到期日及登记序号处理，再按公司明确优先级执行可选采购、研发和扩产。公司可以有不同优先级，但必须显式保存，不能受线程完成顺序影响。

现金、材料和工时只分配一次。未签约或无授信的采购不能直接创造应付款来绕过约束；已发生的合同义务则仍要确认。可拆分计划允许缩量，不可拆分计划不足时延期或拒绝。

$$
\mathrm{AvailableCash} = \mathrm{CashBalance} - \mathrm{ReservedCash}
$$

`CashBalance` 是账簿中真实现金，`ReservedCash` 是已有合法占用中尚未支付的部分，`AvailableCash` 是当前可用于新操作的现金，单位均为元。占用不是付款，付款后要同步释放对应占用；已经扣出的款不能再减一次。占用超过现金属于状态错误，不用 `max(0, ...)` 隐藏。未提款授信和预计回款都不计入 `AvailableCash`。

**例子：** 公司有可用现金 1,000 元，当天必须支付的到期债务为 300 元，支付后只剩 700 元。计划研发 500 元、扩产 400 元。若该公司的已配置优先级为研发在先，则完成研发后只剩 200 元；不可拆分的 400 元扩产只能延期。这不是“扩产失败损失了 400 元”，因为尚未付款、也没有形成资产。

## 6. 业务模块算法

### 6.1 制造与库存

$$
\begin{aligned}
\mathrm{FeasibleProduction}
&= \min(\mathrm{PlannedProduction},\mathrm{MaterialLimit},
        \mathrm{LaborLimit},\mathrm{EquipmentLimit},\mathrm{FundingLimit}) \\
\mathrm{ActualProduction} &\leq \mathrm{FeasibleProduction} \\
\mathrm{QualifiedOutput}
&= \mathrm{ActualProduction} - \mathrm{RejectedOutput} \\
\mathrm{DeliveredQuantity}
&= \min(\mathrm{DeliverableOrders},\mathrm{SaleableInventoryAtDelivery}) \\
\mathrm{ClosingInventory}
&= \mathrm{OpeningInventory}+\mathrm{QualifiedOutput}
   -\mathrm{DeliveredQuantity}-\mathrm{OtherInventoryOutflow} \\
\mathrm{Revenue}
&= \sum_{\mathrm{contract}}
   \left(\mathrm{RecognizedQuantity}_{\mathrm{contract}}
   \times\mathrm{ContractNetPrice}_{\mathrm{contract}}\right)
\end{aligned}
$$

| 英文标识 | 中文含义与来源 | 单位 |
| --- | --- | --- |
| `PlannedProduction` / `FeasibleProduction` | 计划投产量／资源上限内可投产量 | 同一种产品的件数 |
| `MaterialLimit` / `LaborLimit` / `EquipmentLimit` / `FundingLimit` | 已分配材料、人力、设备时间和资金分别支持的最大投产量 | 先换算为件；不能拿元与工时直接取最小值 |
| `ActualProduction` | 实际完成加工的投入数量，延期部分不计入 | 件 |
| `RejectedOutput` / `QualifiedOutput` | 该批实际不合格量／合格量 | 件，来自完成与检验事件 |
| `DeliverableOrders` | 到期且满足交付条件的订单量 | 件 |
| `SaleableInventoryAtDelivery` | 交付当时已经可售的库存 | 件，不含未完成加工或未认证产品 |
| `OpeningInventory` / `ClosingInventory` | 本期间合格成品的期初／期末数量 | 件 |
| `OtherInventoryOutflow` | 成品报废等其他出库 | 件，不再扣一次已经排除的不合格产出 |
| `RecognizedQuantity` | 已满足收入确认条件的交付数量 | 件，逐合同记录 |
| `ContractNetPrice` | 合同计入收入的单位净价 | 元／件，按适用口径处理折让和税 |
| `Revenue` | 本期间已确认营业收入 | 元 |

这组库存关系适用于没有采购入库、退货和跨库调拨的局部过程；有这些事件时逐项加入，不能漏掉实物变化。含在制品、返工或不同规格转换的工艺需要单独的数量桥接，不直接套“投入件数减不合格件数”。资源上限是计划约束，实际完成数仍须来自事件。

产能限制生产，库存限制交付。期初库存可以支持本期销量超过本期产量。多产品共享设备时先分配工时；陈化、认证或验收未完成的产品不可提前销售。

营业成本由实际成本归集与结转产生。贡献毛益与财报毛利分开；设备购建形成符合条件的资产，后续折旧不能与资本开支重复扣费。

**把生产公式拆开：** 计划投产 100 件，材料支持 90 件，人力支持 100 件，设备支持 80 件，资金支持 70 件，则可投产 `min(100, 90, 100, 80, 70) = 70` 件。假设这 70 件均已完成加工，检验出 7 件不合格且无返工，合格品为 `70 - 7 = 63` 件，实际合格率为 90%。若只用期望良率估计计划产量，不能把它冒充已检验的合格数；实际实现需明确整数产出与损耗记录。

期初可售库存为 20 件，完成上述产出后可售 83 件。如果满足交付条件的订单为 75 件，便交付 `min(75, 83) = 75` 件，期末可售库存为 8 件。

这些量不能混成一个“销量”：投产 70 件、合格产出 63 件、销售交付 75 件、期末库存 8 件。销售大于当期产出，是因为使用了旧库存，并没有凭空造货。

再看钱的计算：

$$
\begin{aligned}
\mathrm{GrossProfit} &= \mathrm{Revenue}-\mathrm{CostOfSales} \\
\mathrm{ContributionMargin} &= \mathrm{Revenue}-\mathrm{VariableCost} \\
\mathrm{SimplifiedOperatingResult}
&= \mathrm{ContributionMargin}-\mathrm{RemainingFixedCost}
\end{aligned}
$$

`GrossProfit` 是财报毛利，`CostOfSales` 是已售商品或服务结转的营业成本。`ContributionMargin` 是管理分析使用的贡献毛益金额，`VariableCost` 是相同业务范围的变动成本；这里的 `Margin` 是金额，不是百分比。`RemainingFixedCost` 是该范围尚未计入前项的固定成本，`SimplifiedOperatingResult` 是扣除后的局部经营结果。所有项单位均为元，必须使用相同期间及业务范围。

例如交付 75 件、每件售价 100 元，收入是 7,500 元。若已售货物结转成本为 4,500 元，则毛利为 3,000 元。客户当天可能只付款 2,000 元，剩余 5,500 元是应收，不影响已经满足确认条件的这笔收入。

最后一条只是解释经营杠杆的局部算式，不能直接命名为净利润。利息、税费、减值及其他损益仍按各自口径处理；已经进入营业成本的折旧或固定成本不能再减一次。

### 6.2 研发与能力积累

项目保存目标、阶段、累计投入、剩余工作、最早评估日期及虚拟结果分布。有效资源减少剩余工作；达到工作和时间条件后才抽取一次阶段结果，进入下一阶段、完成、延期或失败。

成功登记技术或产品状态，之后仍须认证、客户采用、生产及销售才产生收入。失败保留已发生支出，并按事实处理剩余资产与知识。研发费用化、资本化、摊销和减值交给相应会计规则。

品牌、技术、渠道和客户关系按“原状态减衰减／流失加验证有效增量”更新。花钱不保证增加能力；这些状态不直接等同于会计资产。

研发进度可以使用有明确定义的工作量单位：

$$
\begin{aligned}
\mathrm{EffectiveWork}
&= \min(\mathrm{OpeningRemainingWork},
        \mathrm{ActualPersonDays}\times\mathrm{WorkPerPersonDay}) \\
\mathrm{ClosingRemainingWork}
&= \mathrm{OpeningRemainingWork}-\mathrm{EffectiveWork}
\end{aligned}
$$

$$
\mathrm{CanEvaluate}
= (\mathrm{ClosingRemainingWork}=0)
  \land(\mathrm{CurrentDate}\geq\mathrm{EarliestEvaluationDate})
$$

`OpeningRemainingWork` / `ClosingRemainingWork` 是阶段期初／期末剩余工作量，`EffectiveWork` 是本期实际完成量，单位为该阶段明确定义的工作单位。`ActualPersonDays` 是实际投入人日，`WorkPerPersonDay` 是每人日有效完成量，来自已发生投入及配置效率。钱只用于支付资源，不能直接代替人日。

`CanEvaluate` 是“允许评估”的真假结果；`CurrentDate` 为当前日期，`EarliestEvaluationDate` 为最早评估日期，`∧` 表示两个条件必须同时成立。达到条件后仍要校验阶段尚未评估，并保存唯一结果事件，不能每天再抽一次。

**例子：** 阶段剩余工作为 100 个工作单位，本月实际投入 20 人日、每人日完成 2 单位，则完成 40 单位，还剩 60。即使有现金，也不能跳过需要等待的试验或认证日期。“工作完成”只是可以评估，不等于评估必然通过；概率只用于定义明确的阶段结果，并保留当次抽样事实。

若本阶段虚拟通过概率是 60%，表示大量独立同条件试验中的模型概率，不表示每十次必有六次成功，更不能让同一项目失败后不断重试抽签直到成功。这个数只用于解释概率含义，不是研发默认参数。

能力积累采用另一条状态关系：

$$
\mathrm{ClosingCapability}
=\mathrm{OpeningCapability}-\mathrm{CapabilityLoss}+\mathrm{VerifiedGain}
$$

`OpeningCapability` / `ClosingCapability` 为期初／期末能力，`CapabilityLoss` 为已发生的过时或流失，`VerifiedGain` 为已验证成果的增量；全部使用同一种能力单位或已定义评分范围。每个能力分别更新，不能把品牌分与技术分直接相加。损失超过原有状态或结果越界须按明确模型规则处理，不靠无声截断掩盖错误。

例如技术评分期初为 50，本期过时损失 2，新成果增加 3，期末为 51。评分不是 51 元，不能记入现金或直接加到净资产；后续通过产品性能、良率或客户选择影响业务。

### 6.3 行业专属过程

| 业务 | 执行链 | 核心口径 |
| --- | --- | --- |
| 房地产与项目 | 拿地、开发、预售、建设、交付、成本结转 | 预售收款与收入分开，保留项目批次和历史成本 |
| 银行 | 合同、计息、收付、信用损失与资本／流动性检查 | 利息收入减利息支出形成净利息收入，NIM 从期间平均生息资产派生 |
| 保险 | 承保、服务期间、收保费、赔付、准备金及投资 | 保费收款不等于当期利润，沿用既有保险会计边界 |
| 资源 | 排产、储量消耗、产出、销售、成本及折耗 | 产量不等于销量，品位、回收率和资源单位一致 |
| 券商与平台 | 真实业务、合同计费、资管、自营与收付 | 客户资产不是公司现金，不按同一成交额重复生成手续费 |
| 公用事业 | 可用装机、运行、资源及调度约束、上网电量、售电 | 功率乘时间才是电量，按对应合同价格结算 |
| 多业务与一体化 | 单元业务、内部供货、外部收支、合并抵销 | 内部交易不重复创造集团利润，一体化不保证低风险 |

行业特有的认证、监管或会计规则须明确支持情况。未实现部分不能由通用默认值冒充。全部参考公司与因子逐项映射见[完整设计蓝图](../../../../../../agents/remaining-questions-and-features/q14-financial-model-design.md)，本目录不再维护另一份会漂移的样本清单。

## 7. 有限现金客户与结算

客户保持独立现金余额、经营收支、债务及逾期状态。普通客户共享算法，重要客户使用个体参数；不把所有客户扩展成完整上市公司。

读取已经到账的可用现金，按 `(OriginalDueDate, DebtSequence)` 遍历普通到期债务。两个英文标识分别是原合同到期日和债务登记序号；每付一笔，立即更新下一笔可以使用的余额：

$$
\begin{aligned}
\mathrm{Payment}
&= \min(\mathrm{AvailableCash},\mathrm{OutstandingDebt}) \\
\mathrm{PayerCashAfter}
&= \mathrm{PayerCashBefore}-\mathrm{Payment} \\
\mathrm{PayeeCashAfter}
&= \mathrm{PayeeCashBefore}+\mathrm{Payment} \\
\mathrm{DebtAfter}
&= \mathrm{OutstandingDebt}-\mathrm{Payment}
\end{aligned}
$$

`Payment` 是本次实际支付额，`AvailableCash` 是本次付款前可用现金，`OutstandingDebt` 是该笔到期债务尚未偿付金额，单位都是元且不能为负。`PayerCashBefore/After` 与 `PayeeCashBefore/After` 分别是付款人与收款人前后现金，`DebtAfter` 为付款后剩余债务。`Payment = 0` 表示没有转账，不生成伪造的成功收款。

上述更新连同应收减少或核销后回收处理进入同一候选事务。剩余债务保留原合同到期日与原逾期起点，部分付款不重新开始计算逾期天数。

客户经营现金流使用与欠款缺口无关的经营输入。模拟内交易必须扣减对方现金；模拟外经营来源应明确登记边界和生成规则。到期、失败或重试不能触发补钱。

普通经营偿付不冒充破产清偿。核销不自动免除债务，回收不再次确认原销售收入，部分付款是合法业务结果。

若无占用现金 70 元、到期债务 90 元，则 `Payment = min(70, 90) = 70` 元，付款人现金归零，`DebtAfter = 20` 元。对未核销应收，收款人增加 70 元现金并减少 70 元应收；已核销债权按恢复收款的会计规则处理，不能减成负应收。两边变动必须来自同一事件，本例无手续费，双方现金总和不变：

$$
\mathrm{PayerCashAfter}+\mathrm{PayeeCashAfter}
=\mathrm{PayerCashBefore}+\mathrm{PayeeCashBefore}
$$

多个债权人都看到付款前的 70 元时，不能各自收走 70 元。由付款人统一排队后，第一笔支付多少，就立即减少后续债务可用的余额。

## 8. 账务、并行和失败处理

共享账簿是报表事实来源。业务事件先校验，再在候选状态中同时更新经营状态、子账和分录。借款本金、营业收入、费用和现金收付分别处理，不使用“现金加净利润”。

公共环境和行业状态先形成只读快照，公司独立计算并行产生提案。共享付款人在其所有者处统一分配资金；跨主体事件以配对标识提交双方账簿。无关联主体可并行处理，不能为了并行牺牲同笔资金的唯一分配。

随机流按环境、行业、公司或项目分开保存。失败重试使用同一输入与抽样事实，不重新抽样谋求成功。经营顺序不改变证券委托受理顺序。

“候选状态”可以理解为先在草稿里完成当天处理；“原子提交”表示检查通过才把整份结果作为正式事实。比如付款人扣了 70 元，但收款人的账簿更新出错，这整笔转账不能算成功，双方都回到转账前。与之不同，现金只够付 70 元、另有 20 元未付，是合法的部分偿付，应保留真实结果。

现金不足、订单未满足或研发失败是业务结果，可以如实提交；金额溢出、未知引用、重复过账或借贷不平是系统错误，阻止候选提交。双边收付不得只完成一边，完整日结失败不得替换上次有效存档。

## 9. 报告、解释与保存恢复

报表从已发生分录生成。解释引用业务事件和计算贡献，例如销量增加、售价下降、折旧增加、客户延付；不在利润生成后编造原因。

内部计划、未披露事实、公开报告和账户本人获知集合分别管理。玩家与 NPC 不能读取未来收入或尚未公开的研发结果。业务事件只能通过信息与个人决策影响证券订单，不直接改股价。

月中日终存档保留本月计划、执行进度、合同、未清债务和随机状态。恢复后继续未完成日期，不重抽整月计划，也不建立两种模式的转换。严格当前契约不附加 schema 版本或兼容路径。

报告中应将下面三个问题分开回答：本期业务赚了多少；本期账户实际多了或少了多少钱；期末还拥有和欠下什么。下一节的完整算例会分别核对这三件事。

## 10. 经营案例与计算示例

本节借鉴用户附件“我看完这一批案例后……”中的机制说明，结合此前讨论补足示例。公司名称只指明研究方向，以下数字全部为虚拟算例，未复述或重新核验真实公司财报，也不指定游戏默认参数。例子各自说明局部因果链，省略的税费、折旧或其他项目会明确标出。

### 10.1 品牌、稀缺与产品结构：贵州茅台

假设有两种已满足陈化条件的产品，单价分别为 100 元、200 元。本月售出 80 件普通产品和 20 件高价产品，收入为 12,000 元；下月售价不变，售出 70 件和 30 件，收入为 13,000 元。

两月总销量均为 100 件，增加的 1,000 元来自产品结构，不是统一提价或销量增长。对应实现是逐产品订单、合格库存、合同单价及交付，汇总后再计算 `ASP`。高价产品库存不足时不能凭空完成结构升级，提价也须影响需求响应。

$$
\begin{aligned}
\mathrm{Revenue}
&= \sum_{\mathrm{product}}
   \mathrm{RecognizedQuantity}_{\mathrm{product}}
   \times\mathrm{ContractNetPrice}_{\mathrm{product}} \\
\mathrm{AverageSellingPrice}
&= \frac{\mathrm{Revenue}}
        {\sum_{\mathrm{product}}\mathrm{RecognizedQuantity}_{\mathrm{product}}}
\end{aligned}
$$

`AverageSellingPrice` 是平均售价，通常缩写为 `ASP`，单位元／件；`RecognizedQuantity` 与 `ContractNetPrice` 沿用第 6.1 节含义，这里按产品汇总同单位、同口径的已确认销售。不同合同价格不同时仍须逐合同计算金额。没有销量时平均售价不可用，不能返回零价。

代入本例：第一月 `Revenue = 80 × 100 + 20 × 200 = 12,000` 元，平均售价为 120 元／件；下月收入 13,000 元，平均售价 130 元／件。两个产品均未提价，平均售价仍然提高，这就是“卖出的高价产品占比增加”。

品牌与供给稀缺作用于客户选择和报价承受能力，不直接给净利润乘一个系数。尚未陈化的库存不能因需求旺盛立即变为可售产品。

### 10.2 技术渗透与价格竞争：宁德时代、比亚迪

虚拟汽车市场本月活动量为 1,000 辆，目标技术采用比例为 20%，每辆需要 50 千瓦时电池，得到行业候选需求 10,000 千瓦时。某供应商候选份额为 30%，分到 3,000 千瓦时需求；实际收入还取决于订单、可交付量和合同价格。

下一月采用比例提高到 30%，其他输入不变，行业需求为 15,000 千瓦时。这是行业扩张，不是供应商自动提高市占率。如果供应商产能只有 3,000 千瓦时且没有库存或有效外部采购，就不能把分到的 4,500 千瓦时全部记为销售。

价格竞争另行作用。设产品销量从 100 件增至 120 件，售价从 100 元降至 85 元，单位变动成本仍为 60 元：收入从 10,000 元增至 10,200 元，贡献毛益却从 4,000 元降至 3,000 元。这个例子说明收入增长时盈利仍可能下降；尚需扣除固定成本等项目才能得到相应利润。

### 10.3 成熟市场仍能变化：美的、海康威视、格力候选

在总需求不变时，企业仍可以通过质量、渠道和报价争取订单，或通过真实流程改进减少材料与工时消耗。例如同样交付 100 件，单位变动成本由 60 元降至 55 元，贡献毛益增加 500 元；若当期为改进支付并费用化 800 元，则当期经营结果反而少 300 元，未来还要看改进能否持续。

海外扩张先建立地区渠道与订单，承受准入、汇率、物流和维护成本；并购则先记录对价、资金和合并范围，再区分外购业务与内生增长。不能直接把“全球化”或“管理优秀”作为利润加成。

此处美的与海康来自附件机制线索；格力只作为后续同类比较对象，不声称已经核验其具体十年经营路径。

### 10.4 研发时滞：恒瑞、迈瑞、北方华创

设某虚拟项目需完成三次阶段评估，每阶段既有最早检查日期，也有工作量和资源要求。前两个月各投入并费用化 100 万元，尚无新产品收入。第三个月达到第一阶段条件后，才依据该阶段虚拟规则确定通过、延期或失败。

通过只意味着进入下一阶段，不能把此前 200 万元支出直接变成现金、无形资产或销售。失败则保留已发生费用，并处理剩余合同或资产。研发成功后仍需完成对应商业化链：药物可能涉及临床与审批，器械涉及认证与医院采用，设备涉及技术验证、客户验收和交付。

阶段成败、渐进改进与技术突破可以组合，不将三个参考公司固定为不同成功概率，也不承诺多花钱必然突破。会计资本化条件独立判断，不能用阶段成功替代。

### 10.5 产能利用率与经营杠杆：中芯、京东方、三安

设一家虚拟工厂可用产能为每月 1,000 件，没有期初库存，产品售价 100 元、单位变动成本 60 元，每月固定成本 30,000 元。

当实际生产并售出 1,000 件时，收入 100,000 元，贡献毛益 40,000 元，扣固定成本后的简化经营结果为 10,000 元。若仅生产并售出 600 件，则收入 60,000 元，贡献毛益 24,000 元，扣固定成本后为 -6,000 元。

产能没有消失，需求和利用率下降已经足以导致亏损。该算例假设没有期末库存、未列其他费用和税费；真实库存成本归集还须区分固定制造成本分摊和当期费用。扩产资金形成资产后再按规则折旧，不能重复扣费。

$$
\mathrm{CapacityUtilization}
=\frac{\mathrm{ActualProduction}}{\mathrm{AvailableCapacity}}
$$

`AvailableCapacity` 是该期间、该产品口径的可用加工能力，`ActualProduction` 是同口径实际完成加工量；`CapacityUtilization` 为无量纲的产能利用率。1000 件与 600 件分别对应 100% 与 60%。可用产能为零时该比率不可用；停机应影响可用能力或实际产出，不能重复扣同一时段的能力。

本例假设合格率为 100% 且全部产品售出，所以第 6.1 节的 `SimplifiedOperatingResult` 分别为 `1,000 × (100 - 60) - 30,000 = 10,000` 元和 `600 × (100 - 60) - 30,000 = -6,000` 元。若有不合格品或留存库存，就不能用加工量直接当确认销售量。

### 10.6 预售、交付与项目批次：万科、保利

假设项目累计土地及建设成本为 100 万元，全部满足项目成本归集条件。客户预付 120 万元时，先增加现金和合同负债，不确认 20 万元利润。

后续满足交付与收入确认条件时，确认收入 120 万元、结转成本 100 万元，得到未考虑其他费用与税费的毛利 20 万元。交付当日可能没有新增收款，因此“本期利润增加”不等于“本期现金流入”。

另一批项目即使面积相同，也可能因历史购地成本、建设阶段、融资条件或售价不同产生不同结果。减值先进入对应项目的账面价值与损益，以后结转时不能再重复扣除原已确认损失。

### 10.7 商品价格与纵向一体化：紫金、中国神华

设已售资源量为 10 吨，单位变动现金成本为 40,000 元。售价从每吨 50,000 元升到 70,000 元时，销售收入从 500,000 元增至 700,000 元，贡献从 100,000 元增至 300,000 元。后者仍不是净利润，还需处理固定成本、折耗、利息和税费。

资源产量还受储量、品位、工艺和实际投入约束，不能只因价格高就无限开采。金属与煤炭须分别保留数量和品质口径。

在煤炭、运输与发电组合中，内部煤价变化会改变各单元表观结果，但集团必须抵销内部交易。只有外售价格、外购成本、外销比例、产量和其他真实条件的变化影响相应集团结果；一体化本身不保证低波动。

### 10.8 资产负债业务：招商银行

设一年期间平均生息资产为 1,000 万元，相关利息收入为 50 万元，付息负债的利息支出为 30 万元，净利息收入为 20 万元，年化 `NIM` 为 2%。这不等于净利润，还存在费用、其他收益、信用损失及税费。

借款人到期未付某笔贷款时，保留欠款、逾期及真实收付记录；预期信用损失按相应条件计量。不能把贷款不良率增加的百分比直接乘全公司利润，也不能因账面有权益就不检查放款现金和资本约束。

月度计息使用合同日数口径，不能把上述全年 2% 直接用于一个月末总资产，伪造月收入。

把其中两个缩写展开：`NIM` 是净利息收益率，`NPL` 是不良贷款相关指标；二者既不是同一个比率，也不是现金余额。这里的计算是：

$$
\begin{aligned}
\mathrm{NetInterestIncome}
&= \mathrm{InterestIncome}-\mathrm{InterestExpense} \\
\mathrm{AnnualizedNetInterestMargin}
&= \frac{\mathrm{NetInterestIncome}}
        {\mathrm{AverageEarningAssets}\times\mathrm{ReportingYearFraction}}
\end{aligned}
$$

| 英文标识 | 中文含义与单位 |
| --- | --- |
| `InterestIncome` / `InterestExpense` | 同一期间的利息收入／利息支出，元；不等于已收／已付利息 |
| `NetInterestIncome` | 净利息收入，元 |
| `AverageEarningAssets` | 同一期间的平均生息资产，元；不能随意换成期末总资产 |
| `ReportingYearFraction` | 该报告期间占一年的比例，无量纲，由指标的明确年化口径计算 |
| `AnnualizedNetInterestMargin` | 年化净利息收益率，简称 `NIM`，无量纲 |

按万元代入全年例子：净利息收入 `50 - 30 = 20`，`ReportingYearFraction = 1`，因此 `NIM = 20 ÷ (1,000 × 1) = 2%`。平均生息资产为零或年占比不合法时不能计算此指标。

对不足一年的期间，年化时还要除以相应期间占一年的比例。合同若明确按 30／360 计息，100 万元本金、年利率 6%、30 天的利息为 `100万 × 6% × 30 ÷ 360 = 5,000元`；本例只说明期间换算，不能把这一日数约定套给所有贷款。

$$
\mathrm{AccruedInterest}
=\mathrm{Principal}\times\mathrm{AnnualRate}\times\mathrm{ContractYearFraction}
$$

`Principal` 是本计息段本金，元；`AnnualRate` 是合同年利率，无量纲；`ContractYearFraction` 按该合同日数规则计算，例中为 `30/360`；`AccruedInterest` 是应计利息，元。此式适用于该段本金与利率不变的单利合同，变化时须分段，复利按合同另算。合同计息的年占比与报表指标年化的 `ReportingYearFraction` 不是同一个配置，不能混用；应计利息也不直接给银行增加现金。

### 10.9 资本市场与平台：中信证券、东方财富

若某虚拟经纪业务的合同计费基础为 1,000 万元、费率为万分之二，则费用金额为 2,000 元。若来自本局真实投资者，必须使用同一条收费与结算事实，不能既在交易系统收过一次，又在公司经营模块生成第二笔收入或扣款。

$$
\mathrm{BrokerageFee}
=\mathrm{BillingBase}\times\mathrm{CommissionRate}
$$

`BillingBase` 是该合同的计费金额，元；`CommissionRate` 是适用费率，无量纲；`BrokerageFee` 是据此算得的费用金额，元。本例 `10,000,000 × 0.0002 = 2,000`。这只展示纯比例计费；实际若有最低佣金、费用拆分或税费，须复用适用规则和已有结算结果，不能用本式替代真实收费。

若客户触达人数为 1,000 人，只有 100 人转化、其中 60 人活跃，则后续计费基于这 60 人实际发生的业务，不能用 1,000 人乘预计佣金当收入。获客支出、流失与服务成本独立记录。

资管按合同计费资产与期间计算，客户受托资产不进入公司自有现金；自营业务使用公司真实持仓与适用计量，不能按指数上涨幅度直接增加现金。

`AUM` 表示受托管理的资产规模。若某合同约定按平均 AUM 收取年费 1%，计费平均资产为 1,200 万元，合同规定该期按一年中的 1／12 计算，则基础费用为 `1,200万 × 1% × 1／12 = 1万元`。1,200 万元是计算服务费的基础，不是公司突然获得了 1,200 万元现金；业绩报酬、费用减免等须按合同另算。

$$
\mathrm{ManagementFee}
=\mathrm{AverageBillingAssets}\times\mathrm{AnnualFeeRate}
 \times\mathrm{ContractYearFraction}
$$

`AverageBillingAssets` 是合同规定的平均计费受托资产，元，不一定包含全部 `AUM`；`AnnualFeeRate` 为年费率；`ContractYearFraction` 为该合同计费期间年占比；`ManagementFee` 为基础管理费，元。平均资产和期间的采样方法按合同保存，不能用今天的资产乘全年费率冒充本月收入；费用确认与实际收款仍分别发生。

### 10.10 物理产出与电价：长江电力

设虚拟机组可用装机为 100 兆瓦，考察 100 小时，在已综合来水、检修和调度限制后实际利用系数为 0.8，则发电量为 8,000 兆瓦时。若厂用电与其他损耗后上网电量为 7,600 兆瓦时，适用结算电价为 300 元／兆瓦时，则售电金额为 228 万元。

这是收入计量的基础，还要按合同与会计条件确认、收款，并处理运行费用、折旧和融资。不能把 100 兆瓦直接当作电量，也不能因为水电标签就保证现金流稳定。

$$
\begin{aligned}
\mathrm{GeneratedEnergy}
&=\mathrm{AvailablePower}\times\mathrm{PeriodHours}\times\mathrm{RealizedOutputFactor} \\
\mathrm{GridEnergy}
&=\mathrm{GeneratedEnergy}-\mathrm{OwnUseAndLosses} \\
\mathrm{ElectricitySalesAmount}
&=\mathrm{GridEnergy}\times\mathrm{ContractEnergyPrice}
\end{aligned}
$$

| 英文标识 | 中文含义与单位 |
| --- | --- |
| `AvailablePower` | 本例计算采用的可用装机功率，兆瓦 |
| `PeriodHours` | 考察时长，小时 |
| `RealizedOutputFactor` | 该功率与时长范围的实际综合出力系数，0～1 |
| `GeneratedEnergy` | 实际发电量，兆瓦时 |
| `OwnUseAndLosses` | 厂用电及其他未上网电量，兆瓦时 |
| `GridEnergy` | 按本例边界计算的上网电量，兆瓦时 |
| `ContractEnergyPrice` | 合同适用电价，元／兆瓦时 |
| `ElectricitySalesAmount` | 本合同售电计量金额，元；仍需满足收入确认条件 |

代入后依次为 `100 × 100 × 0.8 = 8,000` 兆瓦时、`8,000 - 400 = 7,600` 兆瓦时、`7,600 × 300 = 2,280,000` 元。这里时段功率口径固定；实际功率或电价改变时分时段计算后相加。

利用系数 0.8 在本例已经综合了所述限制，不能再为同一停机时段重复乘另一个折扣。没有达到合同收款条件时，这笔收入对应应收，不等于已经收到 228 万元。

### 10.11 同一现金只能付一次：跨行业客户

客户有现金 70 万元，先到期债务为 50 万元，后到期债务为 40 万元。按普通偿付顺序，第一笔支付 50 万元，第二笔只支付 20 万元，客户现金变为零，剩余债务 20 万元保留原到期日与逾期起点。

以后因已配置且实际发生的经营收入收到 15 万元，可以再补付 15 万元，剩余 5 万元；不能因为还差 5 万元就自动生成经营收入。债权公司收到旧款时只减少应收并增加现金，不能再次确认销售收入。

### 10.12 从月初到下月回款：完整走一遍

下面只研究一家虚拟公司的一个月，把需求、库存、收入、利润和现金串起来。金额均为元。为便于手算，本例货物全部按每件 60 元外协采购，验收即可销售；不另设固定资产、折旧、融资和税费，研发 1,000 元假设全部符合当期费用化条件。真实模块仍须处理适用的其他项目。

**第一步：看月初有什么。** 公司有现金 10,000 元、可售库存 20 件，每件账面成本 60 元，因此存货价值为 1,200 元。没有负债，期初权益为 11,200 元。

$$
\begin{aligned}
\mathrm{OpeningInventoryValue}
&= \mathrm{OpeningInventory}\times\mathrm{UnitCarryingCost}
 = 20\times60 = 1{,}200 \\
\mathrm{OpeningAssets}
&= \mathrm{OpeningCash}+\mathrm{OpeningInventoryValue}
 = 10{,}000+1{,}200 = 11{,}200 \\
\mathrm{OpeningAssets}
&= \mathrm{OpeningLiabilities}+\mathrm{OpeningEquity}
 = 0+11{,}200 = 11{,}200
\end{aligned}
$$

`OpeningInventory` 是期初库存件数，`UnitCarryingCost` 是每件账面成本（元／件），`OpeningInventoryValue` 是期初存货账面金额（元）。`OpeningAssets`、`OpeningLiabilities`、`OpeningEquity` 分别为期初资产、负债、权益，单位都是元。本例没有其他期初资产，所以资产正好等于现金加存货。

这只是开局事实，不是本月赚了 11,200 元。客户另外持有现金 6,000 元，公司不能提前使用客户的钱。

**第二步：分配需求。** 行业本月有 150 件候选需求，公司的需求比例为 60%，因此分到 `150 × 60% = 90` 件。假设这些需求均满足合同条件，形成可交付订单。此时没有交付，也没有收入。

**第三步：补充货物。** 公司按已确定的库存计划，向外部供应商实际支付 `80 × 60 = 4,800` 元并收到 80 件合格货物。现金变为 5,200 元，可售库存变为 100 件，账面存货为 6,000 元。这一步把现金换成货物，不会立即把全部 4,800 元认作已售商品成本。

$$
\begin{aligned}
\mathrm{PurchasePayment}
&=\mathrm{PurchasedQuantity}\times\mathrm{PurchaseUnitCost}
 =80\times60=4{,}800 \\
\mathrm{CashAfterPurchase}
&=\mathrm{OpeningCash}-\mathrm{PurchasePayment}
 =10{,}000-4{,}800=5{,}200 \\
\mathrm{InventoryAfterPurchase}
&=\mathrm{OpeningInventory}+\mathrm{PurchasedQuantity}
 =20+80=100
\end{aligned}
$$

`PurchasedQuantity` 为收到的件数，`PurchaseUnitCost` 为采购单价（元／件）；`PurchasePayment` 和 `CashAfterPurchase` 为采购付款、付款后现金（元），`InventoryAfterPurchase` 为到货后库存件数。本例收到货物且立即全额付款；信用采购或预付款不能照搬这一时点组合。

**第四步：交付并确认收入。** 90 件订单都可交付，合同单价为 100 元，收入为 `90 × 100 = 9,000` 元。先记为客户欠款，应收增加 9,000 元。实际交付的货物成本为 `90 × 60 = 5,400` 元，剩余 10 件存货价值 600 元。

$$
\begin{aligned}
\mathrm{Revenue}
&=\mathrm{RecognizedQuantity}\times\mathrm{ContractNetPrice}
 =90\times100=9{,}000 \\
\mathrm{CostOfSales}
&=\mathrm{RecognizedQuantity}\times\mathrm{UnitCarryingCost}
 =90\times60=5{,}400 \\
\mathrm{GrossProfit}
&=\mathrm{Revenue}-\mathrm{CostOfSales}
 =9{,}000-5{,}400=3{,}600
\end{aligned}
$$

`RecognizedQuantity` 是本次满足确认条件的 90 件，`ContractNetPrice` 是合同净单价 100 元／件；其余标识沿用前述含义。这里所有批次的每件成本相同，才能直接用 60 元计算营业成本；成本不同应按适用的存货计价规则结转。

**第五步：客户部分付款。** 假设全部货款已到期，但客户只有现金 6,000 元，因此实际支付 `min(6,000, 9,000) = 6,000` 元。客户现金归零，公司现金增加到 11,200 元，应收剩余 3,000 元。不能因客户付款再次增加 6,000 元收入。

$$
\begin{aligned}
\mathrm{Payment}&=\min(6{,}000,9{,}000)=6{,}000 \\
\mathrm{CashAfterCollection}
&=\mathrm{CashAfterPurchase}+\mathrm{Payment}
 =5{,}200+6{,}000=11{,}200 \\
\mathrm{ClosingReceivables}
&=9{,}000-\mathrm{Payment}=3{,}000
\end{aligned}
$$

`CashAfterCollection` 是公司收款后的现金，`ClosingReceivables` 是本例最终尚未收回的应收，单位均为元。`Payment` 同时减少客户现金，不是公司独立生成的收入。本例没有期初应收，也没有后续其他应收事件。

**第六步：投入研发。** 公司实际支付研发服务费 1,000 元，该服务当期发生并费用化，现金变为 10,200 元，研发费用为 1,000 元。项目进度按实际工作更新，不直接产生新收入。

$$
\begin{aligned}
\mathrm{NetIncome}
&=\mathrm{Revenue}-\mathrm{CostOfSales}-\mathrm{ResearchExpense} \\
&=9{,}000-5{,}400-1{,}000=2{,}600
\end{aligned}
$$

`NetIncome` 是本例净利润，`ResearchExpense` 是本期确认的研发费用，均为元。本例研发已经全额付现，所以实际研发付款 `ResearchPayment` 也为 1,000 元；它与费用相等是本例条件，不是一般恒等式。

因为本例明确省略其他损益及税费，这里净利润恰为 2,600 元；不能把这个三项公式当作所有公司的完整利润公式。

**第七步：对照完整过程。**

| 时点 | 公司现金（元） | 库存数量（件） | 库存账面金额（元） | 应收（元） | 本月累计利润（元） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 月初 | 10,000 | 20 | 1,200 | 0 | 0 |
| 候选需求变成订单 | 10,000 | 20 | 1,200 | 0 | 0 |
| 采购到货并付现 | 5,200 | 100 | 6,000 | 0 | 0 |
| 交付 90 件并结转成本 | 5,200 | 10 | 600 | 9,000 | 3,600 |
| 客户支付 6,000 元 | 11,200 | 10 | 600 | 3,000 | 3,600 |
| 研发服务发生并付现 | 10,200 | 10 | 600 | 3,000 | 2,600 |

**第八步：检查三张报表是否说得通。**

$$
\begin{aligned}
\mathrm{OperatingCashFlow}
&=\mathrm{Payment}-\mathrm{PurchasePayment}-\mathrm{ResearchPayment} \\
&=6{,}000-4{,}800-1{,}000=200 \\
\mathrm{ClosingCash}
&=\mathrm{OpeningCash}+\mathrm{OperatingCashFlow}
 =10{,}000+200=10{,}200 \\
\mathrm{ClosingInventoryValue}
&=\mathrm{ClosingInventory}\times\mathrm{UnitCarryingCost}
 =10\times60=600 \\
\mathrm{ClosingAssets}
&=\mathrm{ClosingCash}+\mathrm{ClosingInventoryValue}+\mathrm{ClosingReceivables} \\
&=10{,}200+600+3{,}000=13{,}800 \\
\mathrm{ClosingLiabilities}&=0 \\
\mathrm{ClosingEquity}
&=\mathrm{OpeningEquity}+\mathrm{NetIncome}
 =11{,}200+2{,}600=13{,}800
\end{aligned}
$$

`OperatingCashFlow` 为经营现金净流量，`ClosingInventoryValue` 为期末存货金额；`ClosingAssets`、`ClosingLiabilities`、`ClosingEquity` 分别为期末资产、负债、权益，均为元。本例全部收付款属于经营活动，所以现金变化恰等于经营现金净流量；如果有投资和筹资活动，须另列后一起核对现金。期末资产 13,800 元等于负债 0 元加权益 13,800 元。

公司赚了 2,600 元，但现金只增加 200 元。差异可以继续核对：

$$
\begin{aligned}
\mathrm{ReceivablesIncrease}
&=\mathrm{ClosingReceivables}-\mathrm{OpeningReceivables}
 =3{,}000-0=3{,}000 \\
\mathrm{InventoryValueDecrease}
&=\mathrm{OpeningInventoryValue}-\mathrm{ClosingInventoryValue}
 =1{,}200-600=600 \\
\mathrm{CashIncrease}
&=\mathrm{NetIncome}-\mathrm{ReceivablesIncrease}+\mathrm{InventoryValueDecrease} \\
&=2{,}600-3{,}000+600=200
\end{aligned}
$$

`OpeningReceivables` 是期初应收，`ReceivablesIncrease` 是本期应收净增加额，`InventoryValueDecrease` 是存货金额净减少额，`CashIncrease` 是现金净增加额，均为元。增加应收意味着确认的收入尚未全变成现金；存货减少意味着本期成本有一部分来自以前取得的货物。

这是本例没有其他项目时的核对关系；存在折旧、应付、投资或融资时还需加入相应调整项。不能将它当作任何公司的通用现金流公式。

**第九步：把状态带到下个月。** 保存现金 10,200、库存 10 件及其成本 600、应收 3,000、客户欠款和研发状态等事实。如果客户下月从另一项真实经营活动收到 3,000 元，再用于补付，公司现金变为 13,200 元，应收归零；仅这次收款不会产生下月销售收入或利润。没有那笔实际来款，欠款就继续保留，不能在跨月时自动补齐。

从代码看，这九步分别落在 `industry.rs`、`decisions.rs`、`businesses/`、`customers/`、`research/` 和共享账簿中，由统一的日级推进协调。每一步只更新自己负责的事实，并用事件连接其他模块。

以上案例应在对应业务模块实现时转为小 fixture 单测。案例只规定要验证的关系，不表示相关代码或测试已经存在。

## 11. 现有代码如何迁入

当前相关入口包括：

- [company/operations.rs](../../operations.rs)：自然日经营编排与行业处理器入口。
- [company/scheduler.rs](../../scheduler.rs)：到期业务队列。
- [company/customer_finance.rs](../../customer_finance.rs)：客户现金与债务领域。
- [accounting/mod.rs](../../../accounting/mod.rs)：共享会计能力。
- [session/company_operations.rs](../../../session/company_operations.rs)：CivilClock 与日结接线。

当前 `company/mod.rs` 中的 `Company` 强制持有 `Books`、`CounterpartyLedger`、`ContractBook` 和预算，`CompanyConfig` 初始化也要求这些对象；`CompanySpec` 还组合了身份、会计类型与集团关系。因此迁移不只是把 `economy` 改名，需要拆出共同身份与模式专属实体，让简单模式能够独立创建和恢复。

先建立 `company/` 的薄契约，将上层读取统一到相同功能的基本面／披露查询，再按职责迁入仿真专属算法与状态。通用会计算法和金额继续复用，仿真账套装配及子账状态归入 `simulation/finance/`，客户和调度保留各自唯一所有者；不复制现金系统、不保留旧路径为另一套公开入口。现有测试与 fixture 按职责迁入目标 `company/simulation/`，公共协议与宿主测试仍留在其责任层。

旧调用方包括 `session/company_operations`、公司装配、公开报告、NPC 财报抽取、保存恢复及 Web 查询。它们依赖共同财务及结算结果，不依赖各模式内部账套布局；不能增加模式分支来回避简单模式的必需功能。相同状态下的共同查询和股本行为规则须一致，目录、当前文档及引用在迁移时统一更新。本轮仅修改设计说明，没有移动运行时代码。

到期队列的 key 去重不能替代业务幂等：出队后仍需要判断该业务是否已过账。迁移时同步调整状态导出、恢复、调用方与测试，不因移动目录改变金额、披露或 A 股语义。

## 12. 验收与维护

优先使用短单测核对：有期初库存时的销售、共用设备工时、收入与回款分离、研发失败、资本开支与折旧、客户部分支付、原逾期起点、核销后回收、双边失败回滚、重复事件以及月中恢复。

固定输入与事件轨迹下验证并行和恢复结果，不单凭相同 seed 要求不同并发受理轨迹的整局字节相等。普通测试遵守十秒上限，长验收按仓库规则单独分类。

算法、状态或模块边界变化应同步修改本文；完整参考索引继续维护在设计蓝图。当前仅建立文档，未实现新算法、未运行代码测试，也未完成独立 subagent 审查，不宣称设计门禁或实现验收已通过。
