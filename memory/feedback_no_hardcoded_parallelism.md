并行度相关参数（rayon worker 数、tokio 线程数等）不允许经验性写死在配置/代码里。**负载由用户创建游戏时决定**（5/10/100 只股票都可能）——worker 数必须在开局时按本局参数（股票数等）运行时推导（f(stocks) 公式、核数为上限），不同对局各自建池；各负载下的"最优 N"曲线只用于标定公式，不作为配置值；公式随结构优化重标定（join 粗化会使峰值右移）。

**Why:** 用户 2026-10-07 明确：当前 worker=4 是 5 股负载的经验点，但后面要用 128 核、股票要加到 50~100 只——经验参数随负载失效；正确形态是引擎只负责提交任务，线程规模交给机器/OS 自适应。

**How to apply:** ①worker 数改为按负载推导（f(stocks) 等，试验 F 的曲线数据出公式）+ 机器核数上限 + 环境变量覆盖（部署应急，不是常设值）；②tokio 线程数同理（当前生产默认 128 线程也要收敛为显式自适应）；③任何"测出来 N 最优就写死 N"的提交都要过用户确认；④大方向配套：任务粗化（join 扁平化）让多 worker 在碎负载下也成立——粗化落地后重测 worker 曲线。

**用户追加（2026-10-07）：位置性预留也算硬编码**——"许可数=工人数−1"、"给某任务单留一条泳道"这类做法本质是预留专属线程，造成核心调度不均，一律不允许。调度的合法形态二选一：**(a) 自研分层调度层**（按负载类别分层分配线程）；**(b) 全部平级交 OS 调度**（需要区分时用 OS 线程优先级 API，如 nice/SCHED_IDLE，仍由 OS 裁决）。现有 fastest_permits_for_workers=workers-1 与"actor 第 5 泳道"思路均属被否定的位置性预留，只可作诊断参考不可进生产。相关：[[engine-perf-1000x]]

**用户追加（2026-10-09）：线程数量多不是负优化的免责理由。** 如果性能下降来自任务拆分、投递、等待唤醒或同步争用，应首先作为调度／并行实现问题核查并修复，不能仅以“线程太多”接受退化或硬截 worker 数掩盖问题。NUMA 等硬件因素可以讨论，但必须有真实拓扑与采样证据，不能把自旋、带宽争用或跨节点访问的推测当归因。

**Why:** 用户明确指出“线程多也不应该就有负优化”，若是调度造成则是调度实现有问题。

**How to apply:** 保持同输入、同线程数及同资源对照，分离任务组织／等待同步与 NUMA 放置等假设，先定位机制再修复重测；减少 worker 数可作诊断对照，不自动成为已获用户认可的最终方案。相关：[[negative-result-attribution]]

**用户部署合同拍板（2026-10-10，三向重测负结果归因后）：**
- **默认 worker 语义＝按需取用**：“这个数目不是算出来的，是实际用的时候用出来的，需要多少就用多少”——不做预测性预算公式（明确否决 Astra 提出的 p*=argmin 成本模型作为默认机制），池随实际并发任务需求按需增长/取用。
- **显式配置值＝自适应上限**：配置128表示上限，实际每阶段按任务量在[1,128]内自适应。
- **优先目标＝单局吞吐**：单局Fastest吃满预算冲吞吐（1000x口径）；多局按剩余预算分配；宿主余量靠预算上限保护，不靠预留线程。

**Why:** 128worker下所有版本大幅退化（基线自身仅16核速度28%）且池接线修复未追回；16worker三档负载稳定正收益。用户重申调度交给实际需求而非预计算。

**How to apply:** ComputeContext默认路径改为按需取用（实现形态待设计：需求驱动池增长或按会话负载运行时推导，不写死、不预测公式）；显式配置作上限；验证顺序＝fixed的16w基线→按需机制实现→同affinity worker宽度对照→128w重测。相关：[[engine-perf-1000x]]
