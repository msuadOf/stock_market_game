用户对 tick 主循环的目标模型与判定（原话要旨）：tick 核心就两件事——NPC 决策（并行）→ 交易簿撮合（并行），顶多每 tick 在 commit 前对 view 做一次同步；一股至少能吃一个核；决策阶段需要几个 NPC 开几个线程、撮合可并行。**当前多核性能倒退（128w −43~−63%、每 tick CPU 12~21×）被用户判定为并行模型不对的结果**——loop 里塞了太多杂七杂八（协调/台账/多段收发），不是参数问题。

**Why:** 四臂判决实验（2026-10-11，完整 0-127 核）证实 128w 明确退化且与 burst 配额化无关；16w 仅用 42% CPU（串行脊限死真实并行度）。用户据此否决了全部"现有模型内调参数"方案（默认16w止血/粒度治理/分级池/自定义运行时）。

**How to apply:**
1. 串行脊简化循环的纲领从"现有模型内化繁为简"升级为"以两阶段模型为规格重审 loop"：loop 里每一件不属于（决策∥/撮合∥/commit前同步）的东西都要给出去留依据（A股语义必需须援引 trading-rules/ADR，编排冗余删）。
2. 任何新的并行/调度工作先问"是否符合两阶段模型"，不再在旧模型上加协调机器。
3. 领域前提待审计钉死：A股语义下每 tick 是否恰好一轮决策+一轮撮合；撮合按股天然独立；决策读共享 view 写各自 intent。
4. 关联：[[concurrent-matching-policy]]（撮合并行化既有政策）、[[resource-entity-model]]（所有权流动消除共享写，与按需开线程同向）。
