## 二、口径澄清（Leader 自查，纠正自己的汇报错误）

**「28x」是 Leader 误引用的旧数据，不是现状。**

- 28x 来源：memory 文件首行 **2026-10-17** 的 `B 全语义 118.7/121.1 t/s（~28×）`。
- 实际最新（memory 正文，2026-10-19）：**双口径千元达成**
  - 裸引擎 A：mean **1011.8**（tag `perf/bare-1000x-viewcampaign`）
  - 全语义 B：**1032.7**（tag `perf/fullsem-1000x-viewcampaign`）
  - 两 tag 均为 main 祖先（已核实 `merge-base --is-ancestor`）
- 日界批实测（`agents/day-boundary-kline/ledger.md:141`）：
  1000tick×3 轮中位 speed_x **952.2 → 905.8（−4.9%）**。

⇒ **当前 main 的量级是 ~900x，不是 28x。** Leader 此前汇报失实，已向用户更正。

## 三、用户要求（核心架构决策）

**引擎日内独立跑，不受外部（组端/会话端/web）同步拖累；日终同步一次；
同步可选、可配置。**

这把「每拍同步」从硬编码路径改为**可配置的日终汇合**。

## 四、待调查（下一批，只读诊断先行）

1. **当前 main 的实际性能**（A/B 双口径，重集成多批之后是否从 ~900x 回退）。
2. **每拍同步面盘点**：`install_market_views` / `install_candles` / 账户回写
   （group→session）等，各自每拍成本与必要性。
3. **日终同步可行性**：哪些面可以推迟到日终而不破坏语义（B3 存档/发布协议/
   Abort 回滚/首错顺序）；哪些必须每拍。
4. **配置面设计**：同步策略的开关与默认值（默认应为"日内不同步"还是"每拍"？需数据）。

## 六、性能门覆盖盘点（Leader 2026-10-22 查账，重要缺口）

| 批次 | 性能门 | 关键内容 |
|---|---|---|
| B2 | ✅ | 初版 **−8.5%** → 收口 **−0.6%**；根因「**install 段每 tick 全量重建镜像**（双拷贝 ~100μs/tick）」，改增量追加后回平 |
| **B3** | ❌ **无记录** | 改热路径（远程登录全链）却无性能验收 |
| **B4a** | ❌ **无记录** | 改热路径（公司域）却无性能验收 |
| B4b | ✅ | 中位 −0.02% |
| 日界 | ✅ | 中位 +0.11%；另记 1000tick×3 轮 **952.2 → 905.8（−4.9%）** |

**两个推论**：
1. **B3 / B4a 是回退的重点嫌疑**——动了热路径但从未测性能。
2. **B2 的 −8.5% 案例很可能就是全案机制**：「每 tick 全量重建镜像/同步」。
   若 B3/B4a/B4b 又引入同类每拍全量同步，会累积——**这正是用户"日内不该跟外面同步"的实证来源**。

**待确认**：日界那个 −4.9% 的口径（相对 1000x 基线 还是 相对上一批）。
