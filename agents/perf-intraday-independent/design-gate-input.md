# 设计门输入（骨架）：引擎日内独立跑 / 日终汇合

> 状态：**待诊断数据填充**。数据到手后补 §2/§3，再送 Sol 设计门。
> 目的：避免"每拍与外部同步"拖慢引擎；落实用户指令「引擎酷酷跑，日内不用管外面，
> 日终同步一次，且可选可配置」。

## 1. 目标（用户权威指令）

- 引擎日内**不与外部**（组端/会话端/web）汇合；
- **日终同步一次**；
- 同步**可选、可配置**（可以选同步，也可以不同步）。

## 3. 候选方案（待数据裁决）

| 方案 | 形态 | 风险 |
|---|---|---|
| **A. 日终汇合（默认）** | 日内不同步；日终一次全量汇合 | 日终可能成尖峰；Abort/存档语义需重证 |
| **B. 可配置（日内/日终/每拍）** | 配置开关，默认日终 | 多形态并存→测试矩阵膨胀、语义分叉风险 |
| **C. 保持每拍但优化** | 沿用 B2 的"增量代替全量" | 已被 B2 证明只能回平，不能提速；未触及用户诉求 |

## 4. 语义约束（必须保持，不可让步）

1. **失败原子性**：一拍失败必须整体回滚，不得留下部分提交。
2. **Abort 回滚**：组端可逆日志语义不变。
3. **存档一致性**：B3 远程登录 / 日终档必须拿到一致快照。
4. **事件顺序**：首错顺序、事件 seq 单调。
5. **A 股语义**：撮合/费用/T+1/首错顺序不可为性能让步。

## 5. 待 Sol 裁决的问题

1. 方案 A 的"日终一次汇合"是否破坏 §4 的任一约束？特别是**日终汇合失败**时，
   日内已经跑完的 tick 如何回滚（当前每拍汇合的原子性边界会改变）。
2. **可配置**（方案 B）是否值得？多形态会否导致语义分叉、测试矩阵失控？
   或应"只做日终汇合，不留每拍模式"？
3. 混合场景：**部分面必须每拍**（如持仓可见性用于当拍决策）、**部分可日终**——
   如何划定边界？请给判据而非清单。
4. 与 wasm 线程层（R4a）的关系：wasm 宿主无 OS 线程、串行管线，
   日内解耦在 wasm 下是否等价成立？
5. 与 B4c/B4d（公司域日终链、权益通道）的交互：日终同步点与日终链的顺序。

## 6. 验收判据（草案，待补数据阈值）

- 性能：相对 1000x 基线，回退从当前值收敛到 **≥900x**（先定目标，再谈更高）；
- 语义：§4 五项全绿（含 Abort/存档/事件序的既有测试）；
- 可配置性：未开启同步时行为与"日终汇合"一致；开启时退回当前每拍行为；
- 证据：binary SHA 绑定、配对中位、load 记录。

- 不为性能削弱 §4 任一约束；
- 不逐点微优化掩盖架构问题（B2 已经说明"增量代替全量"只能回平）；
- 不在数据到手前拍板方案。
