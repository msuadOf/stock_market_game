## 1. 目标陈述（用户原话要旨）

**裸引擎疯狂跑，分布式维护 view，外部直接观测，零会话层税。**

展开为可验收的三句话：

1. 权威状态只活在 owner 线程里（组线程持账户/个人态、交易部持股簿、协调者持全局域），
   引擎热路径不再为会话镜像搬运任何全名册数据。
2. 观测面（行情、盘口、K 线、账户读面、计划进度、事件流）由各数据所有者**内生维护**，
   经统一协议发布；`GameSession` 从"每拍安装镜像的权威副本"退位为"发布版本的读者"。
3. 外部（server actor / 测试 / 存档）只通过发布版本读、通过显式命令面写；不绕过 owner。

两条收窄（终裁 §5，写进战役宪法，防过度承诺）：

- 所有权转移解决资源归属与写冲突，**不自动解决跨线程一致发布**——发布协议是本战役的核心交付物。
- 观测可以很便宜、可以按需、可以复用 owner 已维护的数据，**但不能承诺零成本**——
  发布一致版本、保留读者数据、生成事件和存档都有真实成本，按数据定标。

## 3. 核心设计问题清单（五项，每项给候选方向 + 需实验验证的点）

> 排序即建议的决裂顺序：Q1/Q2 是协议主干（先定型），Q3/Q4 是命令面（可并行设计），
> Q5 是冷路径（最后收口）。

### Q1 版本化发布协议（跨线程一致读点）

**问题**：分别读各线程"最新值"会得到账户 N 拍 + 盘口 N+1 拍的撕裂视图。外部读取必须
拿到"一个固定提交版本 + 它的全部分片句柄"，且生命周期受保护（读者长期持有旧版本不能
use-after-free，也不能无限保留）。终裁明确：单加一个 epoch 数字解决不了分片一致性与内存
生命周期；working/旧 committed 可并存，但不得成为两套独立演进的业务权威。

**候选方向**：
- (a) **发布快照对象**：owner 各自准备不可变分片（`Arc` 句柄），协调者在现有收束点
  （converge，commit 前唯一同步）组装/交换一个全局 `Arc<PublishedTick>`；读者 clone Arc
  即得一致读点，旧版本随最后一个读者释放。发布成本=每拍一次指针交换+分片构建。
- (b) **epoch + 每 owner RCU 指针交换**：读者 pin epoch 后逐 owner 取分片——免全局组装，
  但回收需要 epoch 守卫或有界代数，复杂度更高。
- (c) **小分片 seqlock 拷贝读**：仅适合极小热数据（如最新价），可作 (a) 的补充。

**需实验验证**：
1. 发布成本定标：分片构建+交换 vs 当前安装链（D1-D6 全链）在 B 探针的净差——P0 差分
   profiling 先行（方法学 §1.1，基线 worktree 配对）。
2. 读者持有旧版本的保留内存上限：模拟"外部慢读者持版 N-100"的内存曲线。
3. 分片粒度取舍：按 owner（组/股/全局域） vs 按查询面（行情/账户/事件）——影响构建量
   与读者组装量，用查询面清单（snapshot.rs 消费盘点）对表。
4. `business_state_hash`/验证入口的观察点迁移：hash 在哪个版本上算、Abort 时候选分片
   如何不外泄（失败原子性张力，终裁表 4 行）。

### Q2 同拍交付的提交点归属

**问题**：当前 `GroupReport` 在决策/发单结束时发出（`runtime/group.rs:3553-3569`），最终
`DeskBatch` 实体批次之后才到、组内在**下一 `Start`** 才落账（staging :492、`apply_staging`
:880，模块注释 :7-9）。收齐 G+N 报告≠组账户已应用最终成交。ADR-0017 游戏契约要求成功
`step()` 返回后本拍现金/股份/T+1/成本/计划进度可见——今天的解法就是 D3 双写投影。删双写
必须让 owner 在"读面发布"之前完成本拍收尾确认。

**候选方向**：
- (a) **报告后移**：组把 `GroupReport` 推迟到消费完本拍最终 `DeskBatch`、完成期末落账后
  再发。改动最小，但收束点变晚，可能损失分段 flush 的流水线重叠（ADR-0043 决策 4）。
- (b) **两段确认**：保留早 `GroupReport`（决策事实）+ 新增"读面就绪"确认（owner 已应用
  最终批次）；协调者收齐后者才发布版本。可与现有收束协议整合，不必然加一整轮全局屏障
  （终裁原话）。
- (c) **投影降级为派生读面**：资源仍下一 `Start` 落账（预算截点不动），但读面版本由
  最终成交事实**推导**（不写回权威）——本质是把今天的 session 投影搬到 owner 侧派生层。

**硬约束**：同拍可见 ≠ 同拍资源复用——提前完成期末落账不能让续行重新消费本拍释放的
资源（"下一 tick 才可复用"的游戏简化必须保留，终裁张力表第 3 行）。

**需实验验证**：
1. (a) 的流水线损失：A 探针（10 组、分段 flush 重叠敏感）报告后移前后配对测。
2. (b) 的协议轮数成本：收束消息数 +1 轮确认的 wall 影响（预期小，需实测）。
3. Continue 交互：step_frame 接轨前置 #1（Continue 早轮成交双计）要求投影改**逐轮消费**
  ——Q2 方案必须自带轮次去重语义，端到端红测试"Continue 早轮成交恰一次落账"先行。
4. 语义锚：#103 批语义单测（本拍结果可见/失败零泄漏/资源不可提前复用）作为行为合同，
  方案 (a)/(b)/(c) 任一都要全绿。

### Q3 带副作用查询路由（history_reads）

**问题**：`query_stock_history`（`session/history_reads.rs:17`）读取 K 线的同时记录个人
历史读取经历（`:40-49`，`history_reads.record`）。视图内生后读者拿的是不可变发布版本，
写不进去；而这条副作用是 NPC 决策输入（经历域），丢了=语义漂移。

**候选方向**：
- (a) **查询即命令**：查询走与宿主写注入（Q4）同一命令面——携带目标 owner、受理截点、
  结果身份，owner 在自己的拍内处理并回流结果。副作用时点=owner 受理拍，语义最干净。
- (b) **副作用意图队列**：读者向 owner 收件箱追加读记录意图，owner 下一拍消费——实现
  简单，但读记录的可见拍后移一格，需要先裁定是否有决策在同一拍消费它。
- (c) **经历域小分片集中**：history_reads 等纯计数型个人经历留在协调者侧小分片，消息
  更新——避免每次查询一跳线程，但重新引入一个共享写点（与所有权模型相悖，仅作对照）。

**需实验验证**：
1. 副作用消费时点审计：grep/追踪 `history_reads`（及同型 `attention`/`information_checks`
   等查询面）的读方，确认是否存在"同拍查询→同拍决策消费"路径——决定 (a) 还是 (b)。
2. 全查询面副作用盘点：对所有 `pub fn query_*`/`&mut self` 查询入口做一次清点（防漏网，
   终裁只点名了 history_reads，审计要全覆盖）。
3. (a) 的查询延迟：一跳线程往返（受理截点对齐）对 server API 延迟的影响实测。

### Q4 宿主写注入面

**问题**：宿主（server actor、测试 fixture、admin）注入玩家输入/撤单/管理命令。终裁要求：
命令必须携带目标 owner、受理截点及结果身份；不能绕过 owner 直接修改共享 view。当前由
会话镜像向组线程提供个人输入（`InstallPersonal` 跨 `Start` 待上行位，protocol.rs :551 一带）
属迁移实现选择（c 类），应并入统一命令面。

**候选方向**：
- (a) **统一 `HostCommand` 信封**：`{target_owner, deadline_tick, command_id, payload}` 经
  协调者下游分发（复用现有 broadcast/批消息通道，M1 批发形态），回执事件携带
  `command_id`——玩家输入、带副作用查询（Q3a）、admin、测试注入共用一个机制。
- (b) **每 owner 直连注入通道**：宿主→组 mpsc 直发，协调者只做受理截点仲裁——少一跳，
  但受理顺序的全局可推理性弱。

**硬约束**：玩家输入截点语义（ADR-0032 session ingress receipt order 一族）不变；注入序
与受理序等价（同种子受理序列逐字段等价，沿用 P2-3c 注入序倒置判别式）。

**需实验验证**：
1. 现有注入路径全清单：`InstallPersonal`、`AdminBatch`、测试 fixture 通道（drive.rs :809
   一带的迁移分支"组簿空时不覆盖 session 测试注入计划"即兼容残留，随手登记可删）。
2. (a) vs (b) 的受理延迟与吞吐影响（B 探针 + server actor 路径各测）。
3. 命令面契约版本化（ADR-0029 契约版本思想）——结果身份/超时/拒收的错误结构化口径。

### Q5 日结存档投影

**问题**：ADR-0025 日终存档。今天为日终存档而每拍同步全部可持久事实（终裁 c 类，随 D1-D6
一起消失）；视图内生后，存档候选必须在日结静点由全部相关 owner + 公司域 + 披露共同到达后
组合，成本按日承担。

**候选方向**：
- (a) **日结收集轮**：协调者触发日结 → 等 owner 静点确认（复用 Q2 的收尾确认机制）→
  拉取各 owner 可序列化投影 → 组合不可变候选。结构与 Q1/Q2 同源，一次设计三处复用。
- (b) **增量事实日志**：owner 向 append-only 日志发持久事实，日结时惰性组装——免全量
  拉取，但把成本挪回每拍（与"零会话层税"目标相悖，仅当 (a) 日结成本不可接受时启用）。

**需实验验证**：
1. (a) 的日结组装成本：50/300/1000 股规模各测一轮（阶梯口径，见 §4），单日一次的
   wall 预算拍板（占日长比例）。
2. save/restore roundtrip 等价：现有锚（如 sol4r_serial_cursor_survives_save_restore_
   roundtrip；step_frame 前置 #2 的 desk 序号游标问题——游标随 `DeskReport` 每拍上行
   的长期方案在此一并定）。
3. 恢复后继续运行的多日跨日结用例（B fixture 单日不跨日结是已知探针盲区，方法学 §1.2）。

## 4. 阶梯验收（承接 50/100/300/1000 分级）

Sol 建议的 1000x 分级验收（登记于 perf 主线记忆）：50 → 100 → 300 → 1000。当前位置：

| 口径 | 第一阶段终测（2026-10-17，外部负载窗） | 净机窗参考 |
|---|---|---|
| B 300 tick（全语义） | mean 302.7（290.8-308.2），events 3336/fees 0 逐位 | 309-315 |
| B 1000 tick | 501.5，events 11119/fees 5705 逐位，零衰减 | 489-501 |
| A 3000 tick（裸 World） | mean 1409.2，守恒逐位 5/5 | — |

阶梯解读：300 级已过（302.7），当前卡在 300→1000 之间，B/A 收敛比 0.21。剩余候选里
attention heap 重建（D6）、EnvelopeLedger 会话重建（D6）、组线程 memcpy 归因、jemalloc
缺页税（方案级）四项中前两项本战役直接删除，后两项平行推进。

**本战役目标区间（建议值，P0 差分定标后修订——按方法学 §4.3，不空口承诺倍数）**：

| 档 | 门槛（必须达） | 进取（达标线） | 判据 |
|---|---|---|---|
| B 300 tick | ≥ 500 | ≥ 700 | events/fees 逐位；净机 ≥3 轮 mean/min/max |
| B 1000 tick | ≥ 700 | ≥ 1000（触达阶梯末级） | 零衰减；events/fees 逐位 |
| A 3000 tick | ≥ 1350 不降 | ≥ 1400 | 守恒逐位；A 变=语义回归立即停 |
| 架构健康度 | B/A ≥ 0.35 | ≥ 0.5 | 双写删除+镜像安装链归零后的收敛比 |

目标区间的依据与不确定性（如实登记）：终裁已确认 driver 线程 ~79.85% cycles 集中在
ledger 插入/分配复制/heap 构造（正是 D5/D6 链），且 P2 系列每刀实证该链份额巨大；但
"约 5× 差距"含负载差异不可全记会话，故门槛定在 +65%（302.7→500）、进取定在 B/A 减半。
