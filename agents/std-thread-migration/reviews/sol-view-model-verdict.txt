| 张力 | 本质与必要处理 |
|---|---|
| 跨组、跨股票的一致读 | 分别读取各线程“最新值”可能得到账户 N 拍、盘口 N+1 拍。需要一次读取固定的提交版本及其全部分片句柄。 |

| 宿主注入 | 命令须携带目标 owner、受理截点及结果身份。不能绕过 owner 直接修改共享 view。 |
| 日结存档 | 所有相关 owner、公司域与披露共同到达日结静点后，组合完整不可变候选；成本按日承担。 |

因此，**只把现有 Echo 换成共享指针不够**。需要把 owner 的报告或新增收尾确认推进到“该 owner 已准备好完整本拍读面”的位置。这个确认可以与现有收束协议整合，并不必然增加一整轮全局屏障。

外部读取应获得已发布、不可变、生命周期受保护的版本。单独加一个 epoch 数字，不能解决分片一致性和内存生命周期。读者长期持有旧版本，也会带来保留内存或复制成本。这里允许 working／旧 committed 版本并存，但它们不应成为两套独立演进的业务权威。

- 事件身份、seq、逐 tick 时间序列与交付缓冲。
- 查询时的必要组装／序列化，以及日终存档投影。

**双写不再必要。** [ADR-0043 决策 8](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/docs/decisions/0043-std-thread-ownership-runtime.md) 把双写绑定到了“组内最终批次下拍应用”的现有机制。此前增加同拍公开投影，是在该机制下修复交付缺口；它不能证明双写本身不可删除。

还有一项不能遗漏：查询未必纯读。[`query_stock_history`](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/packages/engine/src/session/history_reads.rs:17) 会记录个人历史读取经历。改造后应把这种行为显式路由给 owner，不能因为改用不可变 view 就丢掉副作用。

**4. 成本估计、改造范围与收尾排序**

**定性估计：当前额外安装链的大部分有架构删除路径；整个“约 5× 差距”尚不能可靠拆成可消除与必要成本。**

1358 t/s 对应约 0.736 ms/tick，263–272 对应约 3.68–3.80 ms/tick，表观差约 2.94–3.07 ms。但其中混有分组、完整决策链、交易阶段和负载差异，不能把这约 3 ms 全记给会话。

现有证据支持优先改架构：

- P2-4a 仅消除全量账户 Echo，就有同窗 **82%–104% 吞吐提升**，无需削弱产品语义。
- 本次只读解析已有 `p14-fp2-after-4a.perf.data`，driver 线程仍占约 **79.85% CPU cycles**，热点包括 ledger 插入、分配／复制和 heap 构造。这支持继续追查串行镜像维护，**不等于 80% wall time 可以删除**。
- 300 tick 归档没有成交费用，不能把其剩余差距主要归于成交结算双写。

所以我不认可“必要语义占八成”或“架构能拿回四倍”这样的现成比例。需要以**相同完整 `WorldSpec`、分组和输入**，区分 owner 计算、收尾确认、镜像安装、协议发布成本后再估算；不能通过关掉业务链测出一个好看的上限。

改造属于**中大型跨层重构**，核心撮合与费用算法原则上无需重写：

| 范围 | 主要涉及文件／契约 |
|---|---|
| owner 收尾与版本发布 | `runtime/group.rs`、`desk.rs`、`protocol.rs`、`coordinator.rs`、`world.rs` |
| 删除会话重装及补偿投影 | `runtime/drive.rs`、`session/failure.rs`、`session.rs` |
| 查询与带副作用的读取 | `snapshot.rs`、`history_reads.rs`、活动委托／个人态查询 |
| 提交、事件与日结候选 | `session/protocol/commit.rs`、`protocol/civil/session.rs`、persistence、hash／验证入口 |
| 架构文档 | ADR-0043 的提交时序、双写和共享边界必须修订；ADR-0017/0025 保留产品承诺并更新实现映射；ADR-0042 腿方向契约应保持不变 |

另外发现一个**当前收尾门禁问题**：

server actor 调用 [ProtocolSession 的 `step_frame()`](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/apps/server/src/actor.rs:1155)，它经 [协议提交入口](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/packages/engine/src/session/protocol/commit.rs:90) 进入 [旧 candidate 管线](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/packages/engine/src/session/pipeline/authoritative_tick.rs:27)。B 探针调用的却是 `GameSession::step()`。**当前 B 数字不能证明宿主生产入口已接入 runtime，也未覆盖完整协议交付成本。**

我的排序建议是：

1. **现在先做 #103 语义测试收口**，固定本拍结果、失败零泄漏、资源不可提前复用、跨组账户映射和日结恢复。
2. **终验收前解决或明确裁定宿主入口分叉**，核对完整 publication 失败是否仍在同一提交边界。不能用 `step()` 的绿证代替 `step_frame()`。
3. 当前迁移按最终冻结版本做 Sol 终验收；通过后才合并。
4. **视图内生作为紧接着的下一战役**，避免把协议大改混进当前未提交性能修改和删除批。
5. **拆分批 9**：已经证明无消费者的内容可以按门禁删除；会话镜像桥接留到新读面替代后删除。WASM 仍使用的串行路径必须保留。

这意味着现在重排验收与删除顺序，但不建议立即在当前混合工作树上展开整套重构。若宿主入口收口本身必须调整提交协议，应单列前置批，先完成再终验收。

**5. 最终理由**

用户的质疑在两个核心点上成立：

- **所有权转移不要求会话镜像成为统一读面权威。**
- **同拍交付不要求“公开面先结算、内部权威下拍再结算”的双写。**

需要收窄的只有两个断言：

- 所有权转移解决资源归属与写冲突，**不会自动解决跨线程一致发布**。
- 观测可以很便宜、可以按需、可以复用 owner 已维护的数据，**但不能承诺零成本**。

因此，应把视图内生确立为后续架构方向；不能继续以“这些都是语义必需”维护当前安装链，也不能用两个不同负载的吞吐比值承诺重构收益。本复核不构成当前分支可合并的终验收结论。
