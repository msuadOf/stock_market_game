**ADR 必要成本与可优化实现的边界**

[ADR-0017](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/docs/decisions/0017-escrow-parallel-tick.md) 要求本拍成功后立即可见完整结算、失败不泄漏部分状态；计划依赖必须在同 tick 继续执行。这些必须保留。

但它不要求：

- 每 tick 深复制全部账户和个人态；
- 每个 NPC 重算相同公共 observation；
- 用不断增长的旧 scheduler 镜像维护查询；
- 每次重建全部 ledger、mirror 和历史；
- 将每笔 Accepted 广播给无关组。

当前“组内 staging 下一 Start 落账＋session 本拍成交投影”的双写，是实现选择。[drive.rs:578](/data1/baiyifan/workplace/stock_market_game/.worktree/std-thread-model/packages/engine/src/runtime/drive.rs:578) 的**本拍可见性必要**；整账户先同步、再施加成交 delta 的搬运方式可改为提交投影批次。最终增量必须恰一次消费，且不能把本拍释放提前用于本拍预算。

| **P1** | 修复 heap 重复入队/无消费增长；保持权威 candidate 与恢复合同 | B 300 tick 暂估回收 **5–25%**；更关键是消除随运行时长恶化 |
| **P1** | 每 snapshot 共享 `MarketView` 和 attention signal；不改变 RNG 消费顺序 | A 暂估回收 **40–65%** 时间；首轮目标约 **150–250 t/s** |
| **P2** | 将账户、个人态、attention、plans/trace 合并为提交投影；传 dirty rows/共享不可变页 | B 暂估回收 **30–60%** 时间；保持安装原子性与本拍查询 |
| **P2** | 按 snapshot/library 版本共享公共 observation、technical、收益聚合和 issuer map | B 暂估回收 **15–40%**；个人 belief、risk、经验演进仍独立执行 |
| **P3** | Accepted 按 owner 批发；事件单遍派发；book 聚合与 mirror/ledger 增量维护 | 对剩余时间争取 **10–30%**；按 profile 选择顺序 |
| **P4** | 再标定组数、分片与 affinity，处理实际关键线程 | 当前 groups=10 只增 18%，不宜先投入大量调度调参 |

我的恢复判断是：

- **A：300–450 t/s 是合理的优化目标区间**，300+ 值得争取；现有证据不足以承诺恢复 664，更不足以承诺 1000。
- **当前 B fixture：先争取 20–50 t/s，完成投影与公共计算优化后，以 60–150 t/s 为探索区间。** 置信度低于 A。
- **同初态、同完整决策链的 World 与 GameSession 配对后，session/World 耗时比以 1.5–3× 为目标。** 不能拿轻量 A 直接证明此比例已经可达。

1000× 若对应 1000 tick/s，就要求完整生产路径 **≤1ms/tick**。当前 B 约 200ms/tick，需要约 200× 改善。上述路线主要解决重复计算和复制，不能据此承诺达到 1000×。应以完整连续竞价路径的 50、100、300、1000 t/s 分级验收。

**3．建议的测量分解**

需要行为归一化，但不能只增加“每成交耗时”。建议分三层：

1. **决策层固定输入。** 固定同一公共 snapshot、个人态和 RNG 输入，分别测 evaluate、公共 observation、个人 observe、strategy、意图转换。报告 ns/候选、ns/实际观察、ns/决策及分配字节。保持候选集合和 RNG 消费一致。
2. **执行层固定受理事实。** 重放同一订单/撤单受理轨迹，分别测入簿、撮合、费用、回流、公共簿投影。报告 ns/受理、ns/fill、live orders 和价档数。撮合成本更接近笔数与簿状态，不能按股数简单归一化。
3. **生产层同 fixture 配对。** 比较完整 World 与 GameSession，分别覆盖开盘申报、清算、连续竞价、收盘和日界。记录冷启动，另报稳态 p50/p95 与随 tick 序号的曲线。

每 tick 至少分解为：

`baseline → World 关键路径 → 账户/个人态投影 → 事件 → attention → candles → envelope/mirror`

同时记录 heap 项数、dirty accounts、复制字节、候选/观察/决策数、Accepted 数、轮数、live orders、fill 数和累计成交量。跨线程 CPU time 与端到端 wall time 分别报告，不能把重叠 span 相加。

已有相位标记不够细，部分安装发生在 `step_frame_equivalent` 的 Commit 标记之后；不能直接把现有十相时间当完整 `GameSession::step` 分解。未来正式吞吐运行关闭捕获，短诊断运行启用采样，并核对真实活跃线程；`threads=16` 只配置 ComputeContext，不证明 runtime 使用了 16 个决策组。

另外，B 当前探针只断言股份相等及现金不增加，没有独立核对 desk fee sink 方程。因此“守恒全绿”应准确记为**该探针断言通过**，不等同 A 的现金＋费用严格对账。

**最终比例估计**

必须分开看，不能把 A/B 混成一个精确百分比：

| 分母 | 语义必要成本 | 可回收浪费 |
|---|---:|---:|
| A 当前约 11.4ms/tick，以恢复 300–450 t/s 估计 | **20–30%** | **70–80%** |
| A 相对历史约 1.51ms/tick 的新增落差 | **约 7–20%** | **约 80–93%** |
| B 当前运行时间，低置信度规划估计 | **15–30%** | **70–85%** |

这些是用于排序工作的先验估计，不是实测归因结果。**最可靠的结论是：存在足够明确、且不必削弱交易语义即可回收的实现浪费；应先做公共视图共享和提交投影修复，再决定 std-thread 方案的性能去留。**
