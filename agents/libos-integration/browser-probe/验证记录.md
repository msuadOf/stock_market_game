# LibOS 浏览器探针记录

2026-11-11，隔离 fixture 直接编译 `packages/engine/src/libos/mailbox.rs` 与 `clock.rs`，不修改生产宿主。固定 `nightly-2026-09-05`，使用标准 `build-std`、atomics、共享 memory，非 ADR-0044 受控 tombstone std。初次构建 `-j 8`，进程外 120 秒 deadline；观察到两个 rustc 同时分别约 79% 和 78% CPU。链接成功。

在仓库根目录运行（需先安装固定工具链和 rust-src）：

```sh
PATH="/Users/asuad/.cargo/bin:$PATH" CARGO_TARGET_DIR=/tmp/stock-libos-browser-target \
RUSTFLAGS='-C target-feature=+atomics,+bulk-memory,+mutable-globals -C panic=abort -C link-arg=--import-memory -C link-arg=--shared-memory -C link-arg=--max-memory=1073741824 -C link-arg=--export=__stack_pointer' \
node --input-type=module -e 'import {runBoundedCommand} from "./scripts/run-with-deadline.mjs"; await runBoundedCommand({command:"cargo",args:["+nightly-2026-09-05","build","--offline","--manifest-path","agents/libos-integration/browser-probe/Cargo.toml","--features","verification-harness","--target","wasm32-unknown-unknown","-Zbuild-std=panic_abort,std","-j","8"],timeoutMs:120000});'
node scripts/run-with-deadline.mjs 10000 -- node agents/libos-integration/browser-probe/run.mjs
```

本机 Chromium headless、跨域隔离，三条 Dedicated Worker 分别实例化同一个 WASM module 和 shared memory。三块 512 KiB 栈通过 WASM allocator 分别分配并保持存活，依次实例化三个 Worker；后两个实例化完成后检查共享 sentinel 未被重置。该 sentinel 检查不证明所有数据、allocator 或 TLS 初始化行为；512 KiB 栈没有溢出保护或最大栈使用证据。接收方报告等待状态已登记后，发送方送值 123；另一轮发出 `AbortHandle::abort`，接收方得到 `Aborted`。单次输出分别为 0.76 ms、0.04 ms；这包含调度与 JS 消息，仅为通过性观察，不是性能基准。`PARKED` 证明登记，不证明底层已进入 atomic wait；故障来源是 Rust handle，不是产品宿主的 `GLOBAL_ABORT` 或 tombstone。

早期探针曾手动放置栈，独立复核指出无法证明与 allocator 等区域隔离；现改为由 allocator 分配并保留栈。工作进程在结束时整体销毁，fixture 不做资源回收验收。

## 断连、超时及提前入队补测

同一浏览器 fixture 另验证：接收方登记等待后销毁最后一个 `Sender`，接收方得到 `Disconnected`；空队列以 80 ms 期限返回 `Empty`（本次端到端观察约 84.2 ms）；发送方先入队 456 后再启动接收，收到原值。发送和故障通知的原有两例也再次通过。以上仍为各单次功能检查，并非吞吐、延迟基准或完整调度覆盖。新增断连与超时用例在 fixture 增加对应出口之前分别触发 panic 失败，补齐 probe 出口后通过；失败来自探针缺少预期结果处理，不能解读为消息通道的功能红灯。

独立复核指出先前超时计时包含主页面到 Worker 的消息调度，可能造成误判；现由 Worker 在 `probe_receive` 调用前后单独计时，并以该时长校验。复跑中 80 ms 等待在 Worker 内约 85.1 ms；预先入队调用内部约 0.005 ms。数字仍是单次功能观察，不是性能基准。浏览器侧尚未覆盖缓冲消息与断连并存或多个发送者。

## 多槽与 engine 测试入口

同一 `FaultDomain` 下创建两个通道，在两个 Dedicated Worker 上分别确认登记 `PARKED`，由第三个 Worker 调用一次 `abort`，两方均返回 `Aborted`。这只确认登记和结果，不证明底层已进入阻塞；仍未覆盖真实宿主或受控 std。

## 新 LibOS verification API 接线（2026-11-12，待执行验证）

探针 crate 已改为依赖 `engine` 的 `verification-harness` feature，并以薄 C ABI wrapper 调用
`engine::verification::{prepare, prepare_group, send, disconnect, abort, stop, run_receive,
run_phase_receive, try_receive, finish}`。浏览器侧通过 API 返回的 opaque session id 调用操作；
`wait_word` 与 `active` 只用于只读观察，消息和故障仍只能经 typed API 发布。探针不再把
LibOS 源文件逐个 `#[path]` 编入第二份模块树。`Cargo.lock` 仅通过离线依赖锁定更新；没有执行
测试、编译、构建或浏览器运行。

本轮 harness 代码保留了共享 memory、多 Worker 栈/sentinel、发送、FaultDomain abort、断连、
预入队消息、同一 FaultDomain 多槽一次 abort 唤醒两个 Worker、有限 deadline 与 phase deadline、downlink stop 后队列为空等场景；增加独立 WASM
`unreachable` trap 的宿主观察。新增 `wait_word` 等待握手要求 downlink mode 返回其底层 mailbox
Signal 的真实等待字，由接收 Worker 的 PARKED 状态确认后才触发 stop。
同域多 Worker 的 API 查询若在注册表锁的短暂竞争窗口返回专用 `LIBOS_VERIFICATION_BUSY:`，
worker harness 通过 `setTimeout(0)` 让出执行权并有界重试；非 BUSY 错误仍作为显式失败处理。

以上只说明 fixture 已接线，**尚无本轮运行证据**。此前日志记录的是直接 include LibOS 源码的旧探针
及其旧 WASM hash，不能作为新 engine dependency / verification API 版本的验证结果。后续须用
文首固定工具链命令重建后再运行浏览器 fixture，并记录新产物身份与观察结果。

仍未覆盖：真实 `apps/web-wasm` 的 wasm-bindgen glue/导出本身、正式 `engine-supervisor` 的宿主故障
广播、产品 `GlobalFault`/tombstone 接线、产品 facade child panic 与 hard trap 生命周期，以及真实
World 的 receiver/业务资产对账。此前记录的 `GLOBAL_FAULT` 单例广播仍只是旧探针证据，没有接入本轮
新 API harness。此处的 `unreachable` 只确认隔离模块中的 WASM trap 能被浏览器 Worker 宿主观察，
不代表产品 child trap 已恢复或完成清理；hard trap 后不得调用 `finish`。

新增 `#[cfg(test)] mod libos` 将 23 项测试纳入 engine 单元测试，不启用生产 runtime。以 `cargo test -p engine --lib --no-run --offline -j 8`、外部 180 秒 deadline 编译，完成用时 36.80 秒；采样中单个 rustc 前端约占一个核，准备停止时构建已结束，未证明该编译阶段充分利用多核。随后 `node scripts/run-with-deadline.mjs 10000 -- target/debug/deps/engine-36d6163108e86dba libos:: --test-threads=8` 通过 23 项，用例执行约 0.11 秒；二进制名称因本机构建而异。

## 实例级故障域验证

探针启用 `verification-harness`，经 `GlobalFault::initialize` 创建实例级域并登记通道；接收 Worker 登记等待后，第三个 Worker 在其独立 WASM instance 中调用 `GlobalFault::abort`，接收方返回 `Aborted`。三个 instance 使用同一 module 和 shared memory；这验证了此 fixture 中全局域状态的跨 instance 通知路径；调用来自探针，**不是**实际 panic，也没有使用产品的受控 tombstone std 或 JS `GLOBAL_ABORT`。Native 隔离测试额外覆盖初始化前故障、域存入与发布之间故障、未发布域不可访问及并发初始化/故障。验证开关下已将 `GLOBAL_FAULT.abort()` 接入 engine 的 `wasm_tombstone_early`，但该真实入口尚未由本探针执行，现有 runtime 的通道也尚未登记到全局域。

## 停止通知与队列（2026-11-11）

扩展 fixture 直接引用当前 LibOS 的 `worker_wait`、`wake` 和相关源码，新增 hostStop：Worker 登记 PARKED 后，另一 Worker 先设置共享 shutdown 标志，再调用实际 `WorkerWake::wake_for_host_stop`；接收端返回 None，随后同一接收端读取队列为空。先用旧二进制运行新探针，观察缺少 `probe_create_stop` 的明确失败；重编后运行三次均输出预期结果，最终一次观察到监督命令退出 0，[一次输出](host-stop-browser.log) 记录 `hostStop` 和 `queueEmpty: true`，该日志本身不记录进程退出码。

构建固定 nightly-2026-09-05、8 Cargo jobs、共享 memory 和 atomics，外部 290000ms deadline；测试由 `node scripts/run-with-deadline.mjs 10000 -- node agents/libos-integration/browser-probe/run.mjs` 执行。WASM SHA-256 为 `6d3a13029d0960c6e94333bfacef34a52610e0a101b88644ba73b596c1fc1fbb`；当时 mailbox、worker_wait、wake 的 SHA-256 分别为 `4eaee94e754d2c7510cfe282005fd0c0a48fccf8736f719d40615e3b862f0811`、`52a67d2508dd0c3376ff01d46de307e4390c2fba6e1bc5295d94752d237165f3`、`677968e15749e1d33b2f3ee1f7ab58dc972dba855a35433cbcdf257621b51ca6`，并未冻结完整源码依赖闭包。

该探针使用隔离 tombstone 替身和 `panic_abort` std，不是产品的受控 std、真实 World 或宿主故障广播；PARKED 只证明登记，不能证明已进入底层 atomic wait。分配的对象直到实例结束才释放，该结果不证明 receiver、在途资金股份或其他资源完成回收，也不是性能测试。独立复核确认测试时序和这些边界。
