# 浏览器 GameSession 宿主故障验证

日期：2026-11-11。此验证不替代完整故障清理验收。

使用 `libos-upstream`、受控 tombstone std 和真实浏览器 supervisor 创建 `GameSession`。engine 在开始批量调用 `step` 前通知主线程；主线程调用真实 supervisor 的 `discard`，由 supervisor 同时发布现有 host abort 和 LibOS 故障通知。批量推进报错后，同一 `GameSession` 通过公开 `step` 与 `save` 再次检查终态。三次执行均由进程外 supervisor 以 15000ms 总期限约束，结果与进程输出分别保存在 [第一次结果](host-abort-session-1.json)、[第一次日志](host-abort-session-1.log)、[第二次结果](host-abort-session-2.json)、[第二次日志](host-abort-session-2.log)、[第三次结果](host-abort-session-3.json) 和 [第三次日志](host-abort-session-3.log)。构建产物的 WASM 与 glue hash 在结果中记录。

三次均观察到注入的 `LIBOS_HOST_ABORT_PROBE`，首次批量推进返回包含 `HostAborted { phase: TickConverge, who: None }` 的错误；后续 step 和 save 均返回与首次失败相同的错误，第三次脚本明确断言了这一点。三次探针在首次失败后的重试前后读取的 tick 均为 0。supervisor 的最终报告均为 `incomplete: true`：尽管其内部最终 snapshot 为 disposed、资源计数为零，这不证明所有 Worker 已正常退出或所有消息与内存均已安全回收。

`executing` 通知发生在批量调用之前，不能严格证明故障在哪一个 tick 或指定接收等待点发布；本次错误字符串显示收到故障时的相位，不能替代阶段同步门。重试前后 tick 一致只说明失败后再次调用没有推进，并不能证明首次失败之前一定没有提交；本次恰好观察到首次失败后 tick 为 0。此测试覆盖引擎 `save` 门，不覆盖 WorkerHost、IndexedDB 或日界存档发布。未覆盖真实 worker panic、hard trap、Seal、Drain 的确定注入和完整退出确认。

为验证 fixture 缺少探针时不会误报成功，先对旧产物运行，得到 `diagnostic_game_failure_probe is not a function` 的失败；该失败只证明测试入口缺失，不能作为行为测试的失败证据。随后新增验证专用探针并重新构建，再执行上述三个样本。真实 World 的具体阶段、panic 和故障清理仍须独立验证。

## 实际 shutdown 与 child drain

前述三个样本没有调用 `GameSession.shutdown`，也没有等待 child drain。为查清 `incomplete`，后续 fixture 在同样故障和会话探针之后消费真实 `GameSession`，同时对 supervisor 发起 `waitForChildrenExit`，共用 3500ms 的关闭截止时间。三个独立浏览器样本见 [第一次](host-abort-shutdown-1.json)、[第二次](host-abort-shutdown-2.json)、[第三次](host-abort-shutdown-3.json)，各自同名 `.log` 记录进程输出和退出状态，外层进程树 deadline 为 15000ms。

三个样本的 `shutdown` 均返回失败，主错误为 `session_poison`；报告记录 6 个 owned handle 的 6 次 join 均已返回，对应 1 个 group 和 5 个 desk，但每个 worker 的结果均为 `HostAborted`，正常 GroupFinal 和 DeskFinal 均为 0。三个样本的 supervisor child drain 均成功，其最终故障报告仍为 `incomplete: true`。child drain 成功表示该 supervisor 的 child 资源表、manifest 和待回收队列满足 drain 条件；它不证明 engine/ingress quiescence、共享 memory 最终释放或其他故障场景无泄漏。

第三次运行使用加强后的断言，要求失败 Session 的主错误仍含 `HostAborted`、owned 与 joined 数量一致、每个 join 有不同 worker 身份且 child drain 成功。此断言验证列出的事实，不把 worker 返回的错误或缺失的 Final 说成成功；也不把 supervisor 的最终 `incomplete` 当成完整清理确认。受控 panic 与 hard trap 的真实退出，以及具体阶段同步和端到端存档边界仍需另行验证。
