# LibOS 上行试接：真实 GameSession 浏览器测量

日期：2026-11-11。此记录是诊断证据，不是生产性能验收。

同一个诊断外壳直接创建 `GameSession`，通过真实 supervisor、共享内存和子 Worker 运行；两组均启用 `verification-harness` 并确认故障域布局，试接组额外启用 `libos-upstream`。WASM 导出 `diagnostic_upstream_mode` 供脚本拒绝模式不匹配。两组使用产品 `DEFAULT_SETUP`、seed 42、预热 1000 tick 后测量 1000→4000 的 3000 tick；每次采用新的 Chromium 实例并按 std → LibOS → std → LibOS 顺序运行。Native 不在本轮测量内。

| 上行模式 | 采样耗时 | 吞吐 | 采样事件数 | 原始结果 |
|---|---:|---:|---:|---|
| std，首次 | 11.924 秒 | 251.60 tick/s | 21821 | [结果](std-sample-1.json) |
| LibOS | 3.914 秒 | 766.45 tick/s | 21821 | [结果](libos-sample-1.json) |
| std，回切 | 12.076 秒 | 248.42 tick/s | 21821 | [结果](std-sample-2.json) |
| LibOS，再次切换 | 4.077 秒 | 735.92 tick/s | 21821 | [结果](libos-sample-2.json) |

此四次样本中，试接组吞吐约为 std 样本的 2.93–3.09 倍。两组编译产物不同，已分别记录 WASM 和 JS glue 的 SHA-256；两次试接样本、事件计数相同，以及回切现象都不能证明最终状态、交易顺序或所有工作负载一致。浏览器加载的字节与预读取 hash 之间没有独立冻结证明；尚无 CPU/线程窗口统计。

测量绕过 `WorkerHost`、产品帧生成、UI 和存档，不覆盖完整产品路径或跨日；`tick/s` 不能直接换算成模拟时间加速比。关闭浏览器不证明 World 或 worker 正常清理，已知故障处理缺口依然阻止生产接入。必须补充状态摘要、重复交错样本、Native 同口径比较、完整路径及跨日验证后，才能判断用户要求的性能目标。

两组均用 nightly-2026-09-05、受控 tombstone std、release profile（thin LTO、16 codegen units）和 `CARGO_BUILD_JOBS=8` 构建；基准进程由进程外 `runBoundedCommand` 限制为 120000ms，分别保留同名 `.log`。首次试运行被 Vite 白名单拦截，失败证据见 [首次运行失败](首次运行失败.log)；之后将构建目录加入当前验证服务器的允许范围。采样脚本固定当前主机的浏览器路径和端口，要求依次运行，非可移植的正式验收脚本。

## 业务投影摘要补测（2026-11-11）

增加诊断入口，在计时结束后读取 `business_state_hash`，以十进制字符串传递 u64，避免 JavaScript Number 精度损失。两组依次运行，setup、seed 和窗口与上文一致；std [样本](std-hash-sample-1.json) 为 242.71 tick/s，LibOS [样本](libos-hash-sample-1.json) 为 752.09 tick/s。两组预热事件数均为 6032、采样事件数均为 21821，业务投影摘要均为 `6818911892746368900`；`compare.mjs` 对窗口、事件数、摘要和失败记录执行比较并通过。构建使用 8 个 Cargo jobs、thin LTO 和 16 codegen units；两个独立 target 并行构建，浏览器样本顺序运行。采样耗时包含批量 step 返回值的序列化与转换，不包括摘要计算。

此摘要是现有非密码学 FNV-1a 业务投影，不包含完整 Runtime 状态，可能发生碰撞。摘要和事件数量相同不能证明事件内容、交易顺序或完整状态相同；同 seed 也不能保证并发受理顺序相同。该轮仅各一次，不替代交错重复样本、Native 同口径比较、完整产品路径或跨日存档验收。构建日志位于 `/tmp/stock-libos-hash-build.log` 和 `/tmp/stock-libos-hash-std-build.log`，浏览器日志位于 `/tmp/stock-libos-hash-{std,libos}-run.log`，临时日志不作为长期可复现产物。

## Native 与浏览器对照：业务摘要不一致（2026-11-11）

产品配置模块导出的 JSON 与浏览器对 `DEFAULT_SETUP` 序列化的 SHA-256 均为 `0081217daf73b08f2b1e5ec5288ada2379cc12c1ae4b61d7cfefa85c1b71eb14`，两端 seed 均为 42。Native wrapper 在执行前后读取所传 setup 文件和二进制并比对 SHA-256；这不能排除运行期间文件短暂替换后恢复。两端均使用 `GameSession::new` 的默认 1 group，并以 0→1000 预热、1000→4000 采样。Native 使用 Rust 1.96.1、release thin LTO、16 codegen units、`CARGO_BUILD_JOBS=8`，浏览器使用上一节的 nightly WASM LibOS 产物；二进制 hash 保存在各自结果中。

两次 Native [样本 1](native-parity-sample-1.json)、[样本 2](native-parity-sample-2.json) 的采样分别为 843.63ms 和 923.22ms，浏览器 [样本](wasm-parity-sample-1.json) 为 4283.71ms。三次预热、采样事件数分别均为 6032、21821，但两次 Native 的业务摘要均为 `14085708716046230834`，浏览器为 `6818911892746368900`；对照程序按设计失败，原始诊断见 [比较失败](native-wasm-compare-failure.log)。因此当前不能把这些耗时作为业务状态一致条件下的 Native/WASM 性能验收。摘要差异的原因尚未定位；相同 seed 不保证并发受理顺序相同，也尚未排除跨平台表示或其他状态差异。

两端计时都不包含会话启动、开局日界和摘要计算；Native 包含逐次 `step` 事件计数与释放，浏览器还包含批量调用返回值序列化及 JavaScript 转换。两端均未在计时中完成 worker 清理、跨日或存档。当前只有两次 Native 和一次浏览器样本，缺少交错采样和 CPU 窗口统计；下一步应定位业务摘要首个不同字段并核对受理事实，不能仅凭吞吐比判断 LibOS 达标。

## 业务摘要首个差异追踪（2026-11-11）

在 `verification-harness` 下复用业务摘要的原始 JSON 字段追踪，计时后对每个字段生成独立的长度和 FNV 摘要。Native 与 WASM LibOS 各运行一个样本，两端各有 40053 项，其中 83 个同位置摘要不同；首个为零基索引 624。完整账户 roster 均为 20008 个且逐项一致。相邻索引 623 的原始 JSON 均为散户账户 `310` 的账户记录；索引 624 对应该账户的 `ZiNoise` / `Panic` 策略数据。两端该字段原始 JSON 唯一不同项是 `base_observation_probability`：Native 的 f64 bits 为 `3f52ddc6e6251ce9`，WASM 为 `3f52ddc6e6251ceb`，相差 2 ULP。原始样本经 gzip 保存为 [Native](native-trace-owner.json.gz) 和 [WASM](wasm-trace-owner.json.gz)，包含二进制或 WASM/glue hash、完整字段摘要、账户 roster 和上述两个字段的原文。

该概率由 `daily_observations_to_tick_probability` 中的 `exp_m1` 计算，本次字段追踪尚未核验计算输入，后续位值追踪见下一节；其余 82 个差异仍未逐项解释，不能把它们全部归因于 `exp_m1`，或认定这些差异对决策无影响。字段摘要为非密码学 FNV，索引本身并非语义标签；本次根据相邻账户原文和完整 roster 交叉确认首个差异的身份，不据此证明其余位置身份。追踪在采样后复制字段字节并增加内存开销，带 feature 的业务摘要还多一次 TLS 检查；这不是生产性能验收。

## 概率计算位值追踪（2026-11-11）

进一步在验证 feature 中包围每个账户的策略构造，记录账户 ID、`observations_per_day`、`ticks_per_day`、传入 `exp_m1` 的参数和取负后的原始概率位值；追踪仅在 `GameSession::new` 闭包期间开启，非 feature 概率公式不变。两端各记录 20007 次换算，账户 ID 顺序、前两项输入及参数位值均逐项一致，96 次原始概率位值不同。完整样本为 [Native](native-probability-trace.json.gz) 和 [WASM](wasm-probability-trace.json.gz)，均包含对应二进制身份；Native wrapper 仍有前后 hash 无法排除瞬时替换的既有限制。

账户 310 两端 `observations_per_day` bits 均为 `4031a0d3d6da5ed0`，`ticks_per_day` 为 15300，`exp_m1` 输入 bits 均为 `bf52e08f525d6d3a`。取负后原始概率分别为 Native `3f52ddc6e6251ce9` 和 WASM `3f52ddc6e6251cea`，相差 1 ULP。4000 tick 后读取的策略值分别为 `3f52ddc6e6251ce9` 和 `3f52ddc6e6251ceb`；Session 在两者之间执行 JSON 浮点规范化，但该轮尚未直接采集该环节的输入输出或排除中途字段变化，因此当时额外 1 ULP 的来源仍待确认；后续直接测量见下一节。该结果未证明其余 82 个业务摘要差异全部来自同一计算，也不能证明采样阈值和后续交易不受影响。

本轮最终构建中途的一次源码更新已导致旧构建作废，随后分别重新构建；最终构建前后核对的关键源码 SHA-256 包括 `sampling.rs` 的 `4da8afca34b698a0be5c1a7690391c1ca50b5c099655ba25b8419819d8b73a61` 与 `session.rs` 的 `01146b1577009ceb27ef13a185726e22ba5cb0d0b62de224a53e99e756a3f191`。该检查不代表构建期间全部源码闭包已冻结。验证 feature 的 TLS 和记录分配会改变初始化开销；Rust unwind 清理经测试，WASM panic-abort 不运行 Drop，不能据此声明异常恢复。

## 规范化及注意力等待补证（2026-11-11）

在真实 `json_canonical_f64` 调用前后记录同一账户的概率位值，并检查输入与该账户的原始概率一致。Native 与浏览器 LibOS [Native 样本](native-canonical-trace.json.gz)、[WASM 样本](wasm-canonical-trace.json.gz) 各有 20007 条唯一 NPC 记录，记录顺序与该 fixture 的预期账户名册一致；两端 seed、setup 摘要、窗口、账户及换算输入一致。原始概率有 96 条不同，规范化后有 82 条不同。账户 310 的 Native 原始/规范化 bits 均为 `3f52ddc6e6251ce9`；WASM 原始为 `3f52ddc6e6251cea`、规范化为 `3f52ddc6e6251ceb`，两端规范化结果均与 4000 tick 后采样的该账户策略字段相同。因此在这组样本中，WASM 额外的 1 ULP 可直接观察到发生在 JSON 规范化环节；这不证明其他账户的后续状态未变化，也不证明 82 条与此前所有字段摘要差异一一对应。产物 hash 保存在样本中，但仅核验 hash 格式不能证明全部源码闭包冻结。

在 macOS aarch64 的 Native 引擎定向测试中，以账户 310 两个实测概率计算散户最大观察概率，在几何分布边界附近有限搜索合法的 53-bit 随机格点；本机找到 `167286040969392 / 2^53`，实际 `sample_attention_wait` 分别返回 6 和 5 tick，见 [测试输出](attention-witness-macos-arm.log)。该见证说明概率差异存在改变注意力调度的可能；它使用合成随机数和本机 `ln` / `ln_1p`，有限搜索及其结果依赖平台，不证明本次样本真实抽到了该值，也不证明已产生不同委托或成交。WASM 的跨平台实际等待行为仍未对照。

## 隔离数学候选试验（2026-11-11）

诊断 crate 单独引入 `libm 0.2.16`，对两端同一批 20007 个实际记录的 `exp_m1` 参数，在采样完成后计算候选值，再使用当前诊断 crate 的 `serde_json` 作往返。候选仅用于离线比较，**未接入 engine 策略或替换已有存档行为**。本机 Native 与 Chromium WASM 的候选原始概率及 JSON 往返概率均逐位一致；相对于现状，候选会改变 Native 的 96 个原始值（最大 1 ULP）及 82 个 JSON 往返值，WASM 两类均无改变。比较结果见 [日志](math-candidate-comparison.log)，完整样本见 [Native](native-math-candidate.json.gz) 和 [WASM](wasm-math-candidate.json.gz)。对两个既有高精度参考值的隔离单测通过。

两份诊断 crate 均解析 `serde_json 1.0.154` 的 default/std feature，而 workspace 单独解析 engine 时为 `1.0.150` 的 default/std；因此该试验的 JSON 结论不能直接推广到正式产品依赖图。固定输入有限、数学库内部目标差异、不同编译器和架构、精度边界、热路径开销，以及跨平台调度与实际订单轨迹都尚未充分验证。Native 现有档的恢复会重建概率并进行相对容差检查，再校验已存策略与注意力概率；改变初始计算前必须验证旧档恢复和继续推进，不能仅凭 ULP 小就断言兼容。若把 `libm` 引入正式 engine，须先按项目规则记录核心依赖 ADR 并经过独立审查。

## 产品锁定的 serde_json 版本补测（2026-11-11）

保留上一轮两份 [Native 旧锁](native-diagnostic-serde-1.0.154.lock) / [WASM 旧锁](wasm-diagnostic-serde-1.0.154.lock)，将隔离诊断锁中的 `serde_json` 从 `1.0.154` 改为根 workspace 锁定的 `1.0.150`，其余锁定包版本、checksum 和依赖列表不变。两个产物均以 `--locked`、8 个 Cargo jobs 构建；构建日志见 [Native](serde150-native-build.log) / [WASM](serde150-wasm-build.log)，锁文件摘要见 [记录](serde-lock-identities.sha256)。单包 feature 树显示产品 `web-wasm --features libos-upstream` 和两份诊断 crate 的 `serde_json 1.0.150` 均为 default/std，分别见 [产品](serde150-product-tree.log)、[Native](serde150-native-tree.log)、[WASM](serde150-wasm-tree.log)。这些证据不等于正式产品 WASM 和诊断产物字节相同，也没有冻结构建期间全部源码闭包。

在同一 setup、seed、账户顺序及参数下，Native 与 Chromium WASM 对 20007 个候选输入的 raw 和 JSON 往返位值仍均无跨端差异；同平台对比上一轮 `1.0.154`，两种位值也均无变化。相对现状仍为 Native raw 96 项、canonical 82 项变化、raw 最大 1 ULP，WASM 均无变化。完整新样本见 [Native](native-math-serde150.json.gz) / [WASM](wasm-math-serde150.json.gz)，对照见 [跨端](math-serde150-comparison.log)、[Native 版本间](serde-native-version-comparison.log)、[WASM 版本间](serde-wasm-version-comparison.log)。比较器校验产物 hash 格式并记录 hash；版本归因依赖上述锁文件和构建证据，不是仅靠 hash 格式证明。

本轮仅验证 20007 个候选输入及诊断环境的 JSON 往返；`libm` 仍未进入 engine。它不证明全部 f64 输入、跨平台 libm 实现、存档兼容、实际订单顺序、完整产品路径或性能目标。版本间比较器的单元测试覆盖纯比较函数，尚无独立 CLI 级负向测试。

## 旧算法存档恢复与顺序对照（2026-11-11）

在 Native `verification-harness` 中以当前代码的旧概率公式和产品默认 setup、seed 42 建局，推进到 tick 1000，写出并重新读取现行格式存档；这是**旧算法生成的现行格式样本**，不是历史发布版本或旧 schema 的存档。以同一存档分别创建旧算法基准 A、旧算法重复对照 B 和注入 `libm` 候选计算的 C；每条分支恢复后推进 3000 tick 并正常 `shutdown`。实验核验全部 20007 个账户实际参与重建并逐个命中候选计算；候选重建的 raw 概率有 96 项不同。结果门槛要求输入存档与旧算法恢复后再次保存的字节一致、各分支恢复和最终存档字节与业务摘要一致、每 tick 完整事件 JSON 字节一致。事件差异按失败保存，不以最终状态一致掩盖。

早期一次没有 B 对照的实验在事件偏移 1908 失败，原始错误见 [记录](restore-first-failure.log)，无法据此归因。随后增加 B 对照的一次运行全部比较通过，见 [样本](restore-control-first.json)。再以同一二进制和相同 setup、seed 及存档 SHA-256，交错运行以下三次；三次均满足输入/恢复存档字节和最终存档字节及业务摘要一致，但严格事件字节门均失败：

| 次数与执行顺序 | 旧算法 A/B 首差 | A/C 首差 | 失败证据与首差分析 |
|---|---:|---:|---|
| 1，A→B→C | 偏移 1908 | 偏移 1908 | [原始](restore-interleave-1.failure.json)、[分析](restore-interleave-1-first-difference.json) |
| 2，C→A→B | 偏移 2030 | 无 | [原始](restore-interleave-2.failure.json)、[分析](restore-interleave-2-first-difference.json) |
| 3，A→B→C | 无 | 偏移 2518 | [原始](restore-interleave-3.failure.json)、[分析](restore-interleave-3-first-difference.json) |

上述每处**首个不同 tick**的原始事件中，首差都是不同股票的 `OrderAccepted` 出现在同一 `seq` 位置；仅针对该 tick，移除各事件顶层 `seq` 后，事件多重集相同。原始事件 UTF-8 与各自 SHA-256 保存在失败证据中；分析脚本先检查原始 JSON 数字 token，只接受 JavaScript 安全整数形式，拒绝负零、小数、指数和越界值，再执行解析。本次原始首差事件另经独立无损 token 检查，均满足该条件。此观察不能证明其余 tick 的事件顺序一致，也不能忽略 `seq`、同股受理或撮合顺序。由于旧算法 A/B 在前两次自身也出现差异，不能将 A/C 的事件差异归因于候选算法；同时也不能仅凭最终存档一致证明所有中间交易事实等价。`docs/testing.md` 已明确自由并发 rerun 不要求整局字节一致；本实验的严格字节门是诊断用来暴露差异，不是改写该契约。

三次交错实验依次运行以避免彼此争用并保留可解释的执行顺序；每次内部使用真实多 worker runtime，运行时观察到进程 CPU 超过单核，启动命令设置单次外层 deadline 为 85000ms，但本轮未留存独立 CPU/线程采样和启动命令日志，不能据此独立复核并行利用率及 deadline 参数。运行工具在验证或 child 执行失败时记录首错、阶段及截断标记，并清理受控临时目录；外层为整个批次持有并清理临时根目录。构建日志见 [记录](restore-interleave-build.log)，源文件和 lock 摘要见 [记录](restore-interleave-sources.sha256)；批次本身不是正式 simulation-acceptance，也未冻结全部源码闭包。初次构建及探针在当前诊断 crate 的 `serde_json 1.0.150` 和 Native 工具链上执行，未验证真实历史存档、WASM 恢复、跨日或产品宿主路径。候选只在 feature 保护的同步闭包中注入，未接入正式概率算法。

## 逐 tick 局部事件顺序对照（2026-11-11）

为进一步解释跨证券事件交错，在不移除原有严格字节门的前提下，新增只读可见事件投影：逐 tick 校验两侧 `seq` 数组相同且各自跨空 tick 严格递增；仅移除事件顶层 `seq` 后分别保留每只证券及每个账户的事件原顺序，`Trade` 进入该证券及双方账户，无法明确归属证券的日界、自然日和公司披露事件作为全局屏障。除顶层 `seq` 外保留所有事件字段。枚举匹配覆盖当前 11 类事件，未来新增类型不能静默归类；定向测试覆盖同股、同账户、成交双账户、屏障、字段变化和异常序号。

按同一旧算法存档、相同二进制及 setup，依次执行 A→B→C、C→A→B、A→B→C 三次：其中 [第一次](restore-local-order-1.json) 和 [第三次](restore-local-order-3.json) 的 A/B、A/C 均通过严格事件字节门；[第二次](restore-local-order-2.failure.json) 的旧算法 A/B 在偏移 1908 出现严格事件差异，按原门槛报告失败，候选 A/C 严格一致。三个样本共六组比较均遍历完整 3000 tick，**局部可见事件投影未发现差异**；输入存档恢复后的字节、各分支最终存档字节及业务摘要均一致，候选重建仍有 96 个原始概率变化。批次退出码为失败，摘要见 [记录](restore-local-batch-summary.json)；结果不能记为严格事件字节验收通过。

投影相同只能说明这些输出事件在该观察窗口内的同股及同账户序列、事件内容和全局屏障符合上述比较条件；它不能还原未公开的 ingress receipt、证明同价受理 FIFO、撮合事实、所有中间状态，或宣称可随意改变对外全局 `seq`。现行 [上交所交易规则（2026 年修订）](https://www.sse.com.cn/lawandrules/sselawsrules2025/trade/universal/c/c_20260424_10816492.shtml) 和 [深交所交易规则（2026 年修订）第 3.4.2 条](https://docs.static.szse.cn/www/lawrules/rule/trade/current/W020260424690713155663.pdf) 自 2026-07-06 起施行；深交所规则对竞价的价格、时间优先及交易主机接受申报时间有明确规定。该诊断未更改或验证交易所规则，项目局部接收顺序契约仍以 ADR-0032 为准。

本批依次运行以隔离不同样本对共享 CPU 的干扰，每个样本内部使用真实 worker runtime；[命令记录](restore-local-command.txt) 使用进程外 290000ms deadline，批次内部共享 280000ms deadline、每个子进程不超过 85000ms。结果或失败证据在各自临时目录清理后发布，批次结束后外部持有的临时根目录已清理；本批只留存一次 [进程 CPU 采样](restore-local-cpu-sample.log)（129.9%），未获得有效线程采样，不代表整个窗口的利用率。该批不是正式 simulation-acceptance；[构建日志](restore-local-build.log)、[关键源码与 lock 摘要](restore-local-sources.sha256) 和样本中的二进制 hash 可供核对，但没有冻结全部源码闭包。该样本仍是现行代码生成的旧算法存档，仅覆盖 Native、一个 seed 和未跨日窗口；历史版本旧档、WASM、产品宿主、实际 receipt 与性能目标仍未验收。

本次执行后发现批次工具原本会在基础设施超时或清理未确认时继续下一个样本；三次实际子进程均已退出，故不改变本批结果。独立复核进一步指出，仅凭已存在的失败证据无法安全区分本次对照差异、旧证据与外层超时；因此修正后的工具遇到**任何**失败均停止并标为 fatal，不自动启动下一样本，共享 deadline 耗尽时尽力发布已完成结果摘要；若外层强杀或写入失败，摘要仍可能无法发布。新增短测试覆盖停止行为。实际执行时的原工具保留在 [快照](restore-batch-observed.mjs)，修正后的工具供后续实验使用。

### 实际 runtime 事实补充对照（2026-11-11）

通过 `verification-harness` 读取每个已提交 tick 的 `TickRecord`，逐类型比较完整 typed 值，并保留同股及相关账户的顺序；Trade 同时覆盖 maker 和 taker。五类分别为成交、挂单生命周期、交易部拒绝回执、组端拒绝和集合竞价事实，不重建不同类别之间的先后。具体字段、比较和计数见 [探针](../../web-architecture-diagnosis/bare-world/src/bin/restore_probe.rs) 和 [投影](fact_projection.rs)。

实际执行一轮 Native A/B/C、各自恢复后推进 3000 tick，外层 deadline 150000ms，原严格事件字节门禁保持不变。[失败证据](restore-typed-facts-1.json.failure) 包含输入及二进制 SHA-256、完整结果和清理状态。A/B 和 A/C 的业务摘要、最终存档与局部事件比较一致；各自 6818 条生命周期事实的同股及同账户顺序一致，成交、交易部拒绝、组端拒绝和集合竞价计数均为零，这些类别没有得到非空覆盖。A/B 和 A/C 在 offset 1982 的严格事件字节比较失败：不同股票的两条 OrderAccepted 交错顺序不同；本轮**未通过严格门禁**。事件级差异不能归因于候选算法，因为旧算法 A/B 也发生同样差异。

此对照不是完整 ingress receipt，也不证明实际同价 FIFO、跨事实类型顺序或历史存档/WASM 的兼容性；独立复核还指出应补充真实 typed 事实的定向负测。采样期间单次进程 CPU 为 154.7%、RSS 约 1.57 GiB（[采样](restore-typed-facts-cpu.log)），仅为瞬时样本，不构成 CPU 利用率统计或性能比较；三分支保存完整记录增加了诊断内存开销。失败路径确认临时存档清理成功、stderr 未截断。

## 同候选概率的 Native / WASM 受控对照

此前两端 `exp_m1` 和 JSON 规范化产生位值差异，原算法的业务摘要不能作为跨端一致证据。本轮只在两份**验证程序的新建 `GameSession` 闭包期间**，通过已有 `verification_with_observation_math` 使用同一个 `-libm::expm1` 候选；WASM 使用 `libos-worker-experiment`，Native 使用现有 std runtime。没有修改正式 engine 算法、引入 engine 依赖或迁移存档；闭包退出后恢复原函数。候选使用验证工程已有 `libm 0.2.16`。它不覆盖旧档恢复、其他线程或后续重建，也不代表最终数学选型。

### 受控窗口的游戏时钟加速比

[setup 字节](acceleration-setup.json) 的 SHA-256 与上一节未开启画像的四份样本一致。依据 [交易规则中的游戏时钟约定](../../../docs/trading-rules.md) 和 Web `TradingTimeline`，此 setup 的开盘、连续及收盘窗口分别为 900、14220、180 tick；连续阶段对应 14220 个模拟秒。样本从 tick 1000 到 4000，完整位于同一日连续阶段，对应 3000 模拟秒。这里是游戏时钟换算，不宣称改变或完整模拟现实交易时间规则。

[换算程序](acceleration-window.mjs) 校验 setup 的 SHA-256、相同样本窗口和既有候选跨端比较后，调用 [连续窗口计算器](acceleration.mjs)；该计算器拒绝跨阶段、跨日、零耗时及无效或溢出结果，不外推其他窗口。两对关闭画像样本的结果如下：

| 运行对 | Native | WASM |
| --- | ---: | ---: |
| [Native A](subprofile-control-native-a.json) / [WASM B](subprofile-control-wasm-b.result.json) | 3736.64× | 2386.96× |
| [Native E](subprofile-control-native-e.json) / [WASM F](subprofile-control-wasm-f.result.json) | 3383.85× | 2407.72× |

以上只覆盖单机两对、新建 Session、同候选观察概率、该固定输入的 3000 tick 连续交易窗口；不包含产品 UI、存档、跨日和完整生命周期，不证明完整交易顺序及 FIFO 相同。不能据此认定产品已经达到或未达到整个目标；但它为本受控窗口提供了与约 3000× 目标可直接比较的游戏时钟口径。计算器先补失败测试再实现；独立复核发现极小正耗时可能使结果溢出，现已补失败用例并显式拒绝非有限结果。

浏览器摘要来自 `JSON.stringify` 的实际字节；换算必须使用摘要相同的文件，语义相同但空白或字段顺序不同的 JSON 也会被拒绝。直接计算器测试覆盖跨阶段窗口，命令行测试覆盖原样输入、setup 字节变化、业务摘要不一致和异常采样窗口；命令行中的异常窗口由既有对照门先拒绝，不能称为已到达计算器的跨阶段分支。两组共 4 项 Node 测试通过。
