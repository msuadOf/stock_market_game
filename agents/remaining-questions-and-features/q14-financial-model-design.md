# 公司基本面与经营系统设计蓝图

日期：2026-10-06。

本文给出公司系统的共同接口、简单基本面生成与完整经营仿真两种实现，以及状态、披露和接入边界。公司、行业、因子来源与讨论沿革放在第五章。

用户明确：`simple` 与 `simulation` 对上层提供相同功能和业务语义，包括财务查询、披露、分红、配股、增发与回购。`simple` 按上次结算的账面数据与百分比规则调整营收和开支，再计算利润及其他基本面；它只展示汇总账面数据，不追踪公司真实资金流向，没有“每月生成多少公司资金”的概念。具体客户、生产及研发过程可以省略。`simulation` 从经营、客户及融资事实形成财务结果。两者新局选定、局内不切换，内部复杂度不同不构成上层功能缺失。以下目录、类型和公式是目标设计，尚未搬迁运行时代码；参数均为虚拟假设，不以参考公司的统计自动填充。

## 一、共同抽象接口与运行架构

### 1. 系统边界和依赖关系

`company` 表示整个公司领域；经济环境只是仿真中的一种输入。把完整公司系统放在 `company/economy` 下，会误导调用方认为公司账簿、客户、项目、研发都是“环境”的附属，也容易迫使简单模式携带完整财务系统。

目标改为 `company/` 提供薄接口，`simple/` 与 `simulation/` 并列。仿真实现名称确定为 `CompanySimulation`；`simulation` 表示完整公司仿真，涵盖经营、客户、研发、财务和结算，`environment` 仅表示其中的环境输入。这里“薄”指只负责共同身份、调用和结果定义，不替两种模式计算业务：

```text
GameSession／CivilClock
        │ 日期、指令、已发生外部事件
        ▼
CompanySystem：整局选定一种实现
        ├── SimpleFundamentals
        │      可配置结算周期的营收与开支 → 一致财务状态
        └── CompanySimulation
               环境 → 行业 → 业务 → 客户／结算 → accounting
        │
        ▼
共同财务查询、股本行为及披露材料
        │
        ▼
information：公开披露 → 账户本人获知 → NPC 判断／玩家查询

成功自然日日结 → 所选实现的必要状态 → 宿主存档
```

`session → company` 是共同依赖，两种实现复用 `accounting` 的金额、财务规则与共同结算能力。Web、Server、Desktop 使用同一 engine；公司模型不依赖网络、数据库或 UI，不设置证券成交价格。`simple` 的公司财务是明确标注的账面生成模型，不建立真实公司资金来源链；投资者端的分红、认购、回购委托与成交仍是实际账户和股份操作，不能重复发放、给认购者补钱或伪造成交。`simulation` 仍保持有限现金与明确资金来源约束。


`accounting/` 继续提供唯一的金额、记账、计量及报表算法；`simulation/finance/` 持有或组织本局需要的账套和行业状态，调用这些算法，不复制一套会计实现。`simple/` 只需维护共同功能所需的汇总账面财务和股本状态，不必构造逐客户、逐合同、工厂或研发项目；也不能只是启动完整仿真后隐藏明细。

`CompanyId`、发行人映射和股份数量继续复用。共同发行人身份不能内含强制的 `Books`、`ContractBook` 或客户表；当前 `Company` 恰好持有这些字段，实施时须拆开身份与仿真实体，不能仅移动 `economy/` 的名字就宣称解耦完成。`CompanyKind` 的会计类别与上市板块、经营特征仍分开。

股权登记、分红、配股、增发、回购等规则及结算复用唯一实现，两种模式都必须支持。可分配利润、股份与方案条件等仍需明确，但不能仅因选择 `simple` 就返回功能不支持。用户已否定此前拟议的 `SyntheticFunding` 机制：不新增公司补款周期、额度、申请或虚拟资本投入事件。账面财务如何与实际投资者结算连接，必须明确表达简单模式的模型边界，不能冒称公司资金来源已经真实仿真。

父层只保存选中实现的内部枚举，不建立含全部可选业务字段的万能对象。`simple/` 与 `simulation/` 不互相调用；模式实现私有，上层通过共同入口查询。公共契约包含相同功能、结果结构与业务语义，不暴露内部账簿写接口。

持久设计入口现为 [README.md](../../packages/engine/src/company/simulation/README.md) 与 [DESIGN.md](../../packages/engine/src/company/simulation/DESIGN.md)。此前文件位于 `packages/engine/src/company/economy/system_sim/`；本次只迁移这两份文档并更新现行引用，没有移动仿真运行时代码，也没有注册 runtime `simulation`。后文提到 `company/simulation/` 均指该设计入口及目标实现位置。

### 2. 状态怎么存

```text
CompanySystem
    issuers: 共同公司身份及发行人映射
    implementation:
        Simple → SimpleState
        Simulation → SimulationState
    advanced_through: 已成功推进的自然日

SimpleState
    轻量环境、营收与开支参数、汇总账面财务、股本事件、未公开材料、随机状态

SimulationState
    环境、行业、经营实体、账套／子账、客户、合同、事件及随机状态
```

简单模式保存的是生成规则、汇总账面财务及已执行公司行为；仿真模式还保存经营和客户事实。二者不要求内部字段同构。`simple` 的报表现金是其账面模型的一部分，不声称追踪了真实公司资金来源；`simulation` 的现金只有账簿中的一个权威余额。实际投资者结算另遵账户和股份的唯一事实，不保存可独立变化的第二份投资者余额。

利润、利用率等在仿真中由经营和账务派生；简单模式先生成营收和开支，再推算利润及相关指标。简单模式的生成结果不能伪装为完整账务推导或真实业务事件。每份公开材料保留模式来源、期间、报告范围及可用指标，读者能分辨数据的含义。

### 3. 抽象接口怎么调用

以下名称为拟议契约，不表示当前已经导出：

| 接口 | 输入 | 输出与约束 |
| --- | --- | --- |
| `create` | 模式、共同公司身份、模式专属配置、日期、seed | 完整实例或初始化错误；只有仿真配置要求完整经营期初事实 |
| `advance_day` | 日期、外部输入、已受理指令 | 更新结果与披露候选；简单模式可以只在指定日期更新少量指标 |
| `query_fundamentals` | 公司、期间、范围及可见身份 | 带来源及单位的可用指标；缺失数据返回明确原因 |
| `query_explanation` | 公司、期间及可见身份 | 简化变化分解或仿真事件链，不承诺同等细节 |
| `capabilities` | 公司及当前状态 | 相同功能集合及当前操作条件，不因模式减少功能 |
| `submit_command` | 明确操作及参数 | 使用共同规则校验后受理或拒绝，返回相同语义的业务结果 |
| `export_state / restore` | 成功日终状态／当前完整存档 | 恢复选中实现，拒绝模式与状态不匹配 |

统一查询要求两种模式提供上层功能所需的同一财务契约，包括相互勾稽的报表和股本行为状态。`simple` 通过汇总生成满足契约，不创建虚假具体客户来解释数据。尚未披露、无历史期间或零分母造成的指标不可用，属于两种模式共同的数据条件；不能以简单模式为由省略必需字段或填零。

内部模型推进能读取自己的状态；玩家只读已公开材料；NPC 只使用本人已获知材料。共同接口仍须保留公开日期、报告期间、范围和更正语义。估值所需输入不足时，该分析方法明确不可用，不偷读仿真私账、不静默换方法、不创建共同“正确股价”。

现有 NPC 报告抽取器、公开库、查询 DTO、交易及 UI 调用共同入口，不按 `simple`／`simulation` 分叉业务。新局选择和模型来源说明可以展示模式；同等制度、方案及投资者账户条件下，共同规则给出同等结果。公司现金的模型含义不同：`simple` 的现金仅作账面展示，不冒充 `simulation` 的实际付款预算。功能一致不要求两种模式生成相同业绩，也不要求它们具有相同内部事件链。

金额沿用现有边界：`Money` 传十进制分字符串，`AccountingAmount` 传元字符串。两者内部精度、换算与溢出检查不得因模式或显示方式改变。

### 4. 一天如何推进

父层负责共同的日期、事务与披露规则，具体计算交给实现：

```text
advance_day(date):
    校验日期、输入身份和重复执行
    建立所选模式的候选状态
    调用该模式的 advance_day
    收集本日到期的披露材料
    校验该模式的不变量与共同输出
    成功则提交；系统错误则保留原状态
```

简单模式按配置的基本面结算周期更新营收与开支，支持月、季度、半年和年；其余日期处理披露、股本行为及明确结算事件，不需要为了共享接口伪造每日采购与收付。基本面结算与报告公开排期分开配置，不因改变结算周期就改写公告日期。仿真模式月初更新环境和计划，每日执行履约、到期事项及资金结算，期末从账簿生成报告。不在每个证券 tick 扫描全部经营实体。

仿真的计划只使用此前事实；未来交付和未到账资金不能提前支撑付款。普通偿付按原合同到期日、登记序号分配现金；这不代替破产清偿规则。现金不足是业务结果；借贷不平、非法引用、溢出是系统错误。两种模式都不能静默吞错。

### 5. 并行、原子性和随机数

公共输入形成一次只读快照，公司独立计算可以并行。简单模式按公司更新指标；仿真模式并行生成提案，共享付款人的现金由唯一所有者分配，再原子更新双方账务。同一现金不能被多个提案分别花掉。

各模式分别保存环境、公司及必要项目的随机状态。失败重试复用输入与抽样事实，不重抽以谋求成功。经营内部处理顺序不修改证券委托受理顺序；固定输入与事件轨迹下验证恢复和并行结果，不要求不同外部到达顺序只凭同 seed 就得到相同整局。

### 6. 新局、前史和存档

新局选 `Simple` 或 `Simulation`，局内不切换，加载时严格恢复原模式。未知模式、缺失字段、模式状态不匹配显式报错，不引入 schema 版本、迁移或降级。

两种模式各自生成带明确日期的虚拟基本面前史。简单模式的汇总财务和趋势连续，仿真模式的经营状态及期末账簿连续；两种模式均须使期初财务与已生成历史衔接。前史截止开局前一日，证券前史仍使用独立规则，不把基本面生成视为撮合成交。

仅成功自然日日结生成持久存档。当前模型状态、未公开材料及随机状态需要保存；简单模式保存结算周期、期间基准和趋势进度，仿真额外保存计划、未清债务等继续执行所需事实。恢复不重新抽取已确定的趋势、扰动或计划，写盘失败保留上一有效日终档。

## 二、简单基本面生成的算法

### 1. 目标与边界

`simple` 用少量年化趋势、扰动和结算周期参数生成连续且一致的财务状态。结算周期可配置为月、季度、半年或年，不固定为月度。它与 `simulation` 对上层功能相同，包括财务查询、信息披露、分红、配股、增发、回购等；省略的是详细经营过程，不是这些功能所需的财务与结算结果。

| 内容 | 简单实现 |
| --- | --- |
| 驱动输入 | 营收与开支各自的年化趋势、小幅随机扰动、结算周期及开支比例 |
| 派生结果 | 利润、净资产及同口径 ROE 等，不独立抽取后互相覆盖 |
| 财务状态 | 满足共同报告、税务、股本行为所需的汇总余额与变动 |
| 公司资金 | 仅作为汇总账面数据，不追踪真实流向，不设置补款或每月资金生成额度 |
| 股本行为 | 各公司可配置的行为偏好生成计划，复用共同条件校验、股份登记和资金结算 |
| 可省略过程 | 具体客户、真实订单、工厂排产、研发项目及逐合同经营网络 |
| 保存事实 | 结算周期、年化参数、趋势进度、已生成结果、未完成公司行为与随机状态 |

共同身份不强制包含复杂经营对象。实现可复用现有账簿承接汇总事件，而不运行完整经营仿真；不能以“不模拟具体客户”为理由省略应有的报告字段或给玩家返回功能不支持。

初始化允许按 seed 生成可编辑的虚拟预设，也允许从开局股价、总股本及明确标注为虚拟假设的 PE／PB 倍率反推初始利润和权益，再由同期间营收、开支和税务关系确定一致的初值。预览配置与实际创建使用同一 seed 和参数，用户编辑的配置不得被重新抽样覆盖。这只是一次性的初始匹配：后续结算不从股价重新锚定，读档不重新初始化，不引入共同正确股价，也不保证开盘不涨跌。测试须覆盖反推金额与期间一致性、预览原样消费、编辑保留及恢复不重复校准。

### 2. 期间输入：年化趋势、结算周期与开支增长

采用用户确认的方向：直接调整营收和开支，然后算出利润，不把目标利润或目标 ROE 作为另一套独立驱动。默认采用持续一段时间的趋势加小幅随机波动，各公司的营收与开支分别配置；增长、平稳或下滑阶段不保证公司一定盈利，也不保证亏损后自动恢复。趋势持续时间按自然时间表达，不能把“持续三个周期”同时解释成三个月和三年。具体默认数值仍须明确，3% 和 6% 只是示例。

增长趋势统一按年化配置，再换算到所选结算周期。在一个趋势不变的完整期间内：

$$
\mathrm{PeriodGrowth}
=(1+\mathrm{AnnualGrowth})^{\mathrm{PeriodMonths}/12}-1
$$

| 英文标识 | 中文解释与单位 |
| --- | --- |
| `AnnualGrowth` | 年化增长趋势，无量纲；年增长 12% 写作 0.12，不是每期都增长 12% |
| `PeriodMonths` | 结算周期月数；月、季度、半年、年分别为 1、3、6、12 |
| `PeriodGrowth` | 换算后的本期趋势增长率，无量纲，尚未包含随机扰动 |

例如年化增长 12%，对应月度约 0.949%、季度约 2.874%、半年约 5.830%、年度 12%。季度不是直接用 12% 除以 4；复利换算使相同且不变的年度趋势在不同周期下保持一致。趋势在期间内改变时，应按实际持续时间分段计算并复合，不能用期末趋势覆盖整段历史。

随机扰动单独定义，幅度要结合时间跨度明确配置，不把月度扰动原样用于年度，也不把上述增长率公式冒充波动率换算公式。用户确认按各结算周期分别配置扰动，不强制内部按月抽样再聚合；具体分布及虚拟预设在配置中明确。不据此承诺不同周期、同一 seed 会生成完全相同的路径。抽样事实与趋势进度必须可保存、可恢复。

以下 `t` 表示一个已明确起止日期的结算期间，`t-1` 表示前一个同长度期间；`RevenueGrowth` 和 `FixedExpenseGrowth` 是各自趋势换算并结合扰动后实际采用的期间变化率：

$$
\begin{aligned}
\mathrm{Revenue}_{t}
&=\mathrm{Revenue}_{t-1}\times(1+\mathrm{RevenueGrowth}_{t}) \\
\mathrm{FixedExpense}_{t}
&=\mathrm{FixedExpense}_{t-1}\times(1+\mathrm{FixedExpenseGrowth}_{t}) \\
\mathrm{VariableExpense}_{t}
&=\mathrm{Revenue}_{t}\times\mathrm{VariableExpenseRatio}_{t}
\end{aligned}
$$

| 英文标识 | 中文解释与单位 |
| --- | --- |
| `Revenue` | 本结算期间确认的营收，元，不是本期实际收款 |
| `RevenueGrowth` | 营收相对上一同长度期间的变化率，无量纲；3% 用 0.03 表示 |
| `FixedExpense` | 本期不随本期销量直接变化的固定开支，元；固定不代表永远不变 |
| `FixedExpenseGrowth` | 固定开支相对上一同长度期间的变化率，无量纲 |
| `VariableExpense` | 本结算期间的变动开支，元 |
| `VariableExpenseRatio` | 变动开支相对营收的比例，无量纲 |

变动开支也可以配置为按自身年化趋势换算期间增长率后更新金额；同一开支项只能选择一个生成规则，不能同时按金额增长和营收比例重复生成。固定开支与变动开支是建模分类，生成后仍映射到明确且互不重复的会计科目；它们不直接等同于财报中的某一整行。增长率不得使非负营收或开支变成负值，比例超过 100% 可以表示合法的高成本或亏损，范围由明确模型配置校验。

期间变化只决定当前期间的汇总业务金额，不把未来期间计划提前确认为收入。季度营收应与上一季度比较，年度营收与上一年度比较，不能把一个月的营收乘季度增长系数就称为季度营收。初始化及虚拟前史必须提供匹配期间长度的基准；本轮没有约定局内切换周期时的重分期规则，不可静默复用不同长度基准。零营收乘增长率仍是零，需要明确的初次营业或复业基准才能重新产生营收；不能隐式补默认值。金额使用精确类型与明确舍入，生成状态和随机流可保存、可恢复。

### 3. 利润与 ROE 从一致数据计算

利润来自本期实际采用的收入与费用项目，不能再独立乘一个“利润增长 3%”系数：

$$
\begin{aligned}
\mathrm{ProfitBeforeTax}
&=\mathrm{Revenue}+\mathrm{OtherRecognizedIncome}
 -\mathrm{FixedExpense}-\mathrm{VariableExpense}-\mathrm{OtherRecognizedExpense} \\
\mathrm{NetIncome}
&=\mathrm{ProfitBeforeTax}-\mathrm{IncomeTaxExpense}
\end{aligned}
$$

`ProfitBeforeTax` 为税前利润，`NetIncome` 为净利润；`OtherRecognizedIncome` 为前项尚未包含的其他已确认收益，`OtherRecognizedExpense` 为前项尚未包含的其他已确认费用，`IncomeTaxExpense` 为当期所得税费用，单位都是元。利息、折旧、减值等按所属科目计入一次，不能在固定／变动开支中扣过后又在“其他”重复扣。所得税沿用适用的会计与期间处理，不把所有亏损自动变成税款返现。

**虚拟算例（选择月度结算）：** 上月营收 1,000 元，固定开支 300 元，变动开支率 40%；假设两个月均没有其他损益与所得税费用，则上月净利润为 `1,000 - 300 - 400 = 300` 元。假设年化趋势换算并结合扰动后，本月实际采用营收增长 6%、固定开支增长 3%，变动开支率不变；这些是本期结果，不是年化配置默认值：

$$
\begin{aligned}
\mathrm{Revenue}_{t}&=1{,}000\times1.06=1{,}060 \\
\mathrm{FixedExpense}_{t}&=300\times1.03=309 \\
\mathrm{VariableExpense}_{t}&=1{,}060\times0.40=424 \\
\mathrm{NetIncome}_{t}&=1{,}060-309-424=327
\end{aligned}
$$

利润从 300 增加到 327，增长 9%，不是预先设定的 3% 或 6%。若另一期营收降至 500，固定开支仍为 309，变动开支为 200，相同简化条件下利润为 -9。亏损及改善由收入与费用之差产生，无须另定“负利润乘增长率”的规则。这些算例省略税费只用于解释关系，不代表真实公司免税或游戏税率为零。

ROE 是共同指标层按适用 A 股口径计算的财务分析指标，不是简单模式最底层的生成参数。公司模型提供同期间、同范围的利润、权益及权益变动事实，其基本关系为：

$$
\mathrm{PeriodROE}
=\frac{\mathrm{PeriodNetIncome}}{\mathrm{AverageEquity}}
$$

`PeriodNetIncome` 是指定期间净利润，`AverageEquity` 是同期间、同报告范围的平均净资产，单位均为元；`PeriodROE` 为该期间净资产收益率，无量纲。月利润 327 元、该月平均净资产 10,000 元时，月 ROE 为 3.27%，不能直接显示为年度 ROE。合并归母口径使用归母利润与归母权益；报告指标采用既有定义，不能用期末权益随意替代平均值。有分红、增资或回购时，平均权益应反映变动时点。平均权益非正时明确说明指标不适用，不输出误导性收益率。

### 4. 其他账面财务数据与实际结算边界

营收和开支不能唯一决定全部资产负债项目。模型使用明确配置的资产结构、债务与账面变化规则，生成共同报表需要的汇总结果，不以此扩建真实客户偿付或公司现金来源系统。同一项账面变化只确认一次；参数或目标互相矛盾时显式拒绝，不靠改写历史股本行为或利润来补平。

用户对资金问题的最新回答为：“不用关注有多少公司资金，因为公司基本面数据是由上个次结算按百分比增减而来的”；投资金额也只是账面数据，`simple` 不追踪真实资金流向；每月生成资金金额“没有这个概念”。因此取消此前 `SyntheticFunding`、生成触发、默认额度及虚拟资本投入映射提案，而不是把其待定选项自动设为零或一种融资。

账面现金、权益、收入、费用与现金流展示仍需保持共同口径和数学关系，不冒称存在真实经营收付款。分红等对实际投资者账户的作用与公司账面展示分别表达：执行必须有明确方案和幂等标识，失败原子，不能因查询、恢复或技术重试重复发放。投资者现金与股份事实不能按百分比覆盖，认购需要本人实际现金，回购需要真实委托与成交。此账面模型边界不扩展到仿真模式；`simulation` 仍保存有限现金及明确经营／融资来源。

用户确认：公司报表现金不是实际付款预算，`simple` 分红按可分配利润与方案等条件给持股人实际到账，不因公司账面现金不足拒绝。配股、增发仍检查投资者本人现金，回购仍需实际成交。`simulation` 不因此免除公司真实现金约束。

每个结算期间的财务结果与该期间已执行的股本行为合并核对：分红影响现金、应付款及权益，配股／增发认购影响现金和股本相关项目，回购按适用规则处理现金及权益，不作为经营开支再扣一次。不能每到期末按比例覆盖实际结算余额，导致已付分红或已收认购款消失。

### 5. 股本行为、披露与验证

用户确认每家公司具有可配置的公司行为偏好，例如偏好分红、配股、增发或回购。轻量规则结合偏好、财务条件和显式参数生成计划，使用可复现随机源，不必模拟管理层决策过程；不能用全公司同一固定概率代替个体偏好。偏好影响是否提出方案及其配置，不保证方案获准或完成，具体检查频率和数值预设仍需明确。两种模式调用相同执行机制，制度与方案条件、时点、税务、股份数量、投资者资金收付和失败原子性不因模式简化；公司端的实际付款预算只属于仿真模式，简单模式按前节的账面边界处理。具体制度仍按实施时适用的 A 股官方规则核验，本文不新增现实制度解释。

计划不等于完成：需撮合的回购仍通过实际订单与成交完成，不伪造卖方或成交；投资者参与配股、增发仍需用本人实际现金认购。公司账面展示不意味着给认购者补钱，也不意味着取消方案条件或将全部回购自动成交。

已生成且覆盖报告期间的流量按期间汇总，期末余额使用对应日期状态，比率重新按期间口径计算，不直接相加各期 ROE。基本面结算周期与 `ReportFrequency` 的公开排期分别表达，不能把年度结果直接当成某季度结果，也不能因尚未结算而公开未来业绩。用户确认只按所配置的周期生成，无须为了较短报告强制内部月度生成；尚无已结算窗口时须在共同查询契约明确表达资料尚未形成及原因，不默认均分全年金额、不伪造较短期间结果，也不把缺数据静默显示为零。按规定披露时点公开已形成材料；生成来源可说明为简化模型，不捏造客户、订单或研发经历。UI、NPC、交易及股本行为消费者无需写模式分支，内部调试信息不作为上层必需依赖。

短测至少覆盖：四种结算周期及年化换算、同长度期间基准、趋势持续时间、扰动与恢复、营收与开支不同增速、亏损、零基数、非法参数、费用不重复计入、跨期结转、ROE 期间／权益口径、公司行为偏好与执行条件分离、公司行为幂等、已执行股本行为不被期末覆盖，以及两种模式的共同查询和结算契约。测试不要求相同 seed 在两种不同模型下生成相同业绩。本文只规定目标，不表示功能或测试已经实现。

## 三、仿真经营系统的算法

### 1. 运行对象与职责

仿真模式采用“公共环境 → 行业市场 → 公司业务单元 → 合同与结算 → 会计报告”的结构。

| 对象 | 权威状态 | 输出 |
| --- | --- | --- |
| 环境 | 利率、资源价格、需求环境等虚拟状态 | 各行业当期可读快照 |
| 行业市场 | 市场总量、技术渗透、竞争主体和周期 | 分产品、区域及期间的需求池 |
| 公司业务单元 | 产品、产能、工艺、渠道、项目或金融合同 | 需求承接、交付与经营事件 |
| 管理决策 | 明确预算及优先级 | 定价、采购、研发、扩产等指令 |
| 客户与债务 | 独立现金、经营收支、债务及偿付状态 | 可实际执行的付款 |
| 账簿与子账 | 现金、资产、负债、收入和费用事实 | 报表、结账与公开材料 |

`CompanyKind` 继续表达已有会计类别；成长、周期、研发等只是业务特征。公司可以拥有多个业务单元。哪些单元适用哪些行业处理器需显式登记，不能创建一个包含所有行业空字段的万能对象。

### 2. 月初更新环境与需求

环境按月更新，合同和到期事项按自然日执行。不同环境变量分别演化，不统一压成一个景气乘数。对于有界需求变化，可以采用：

```text
行业需求变化 = persistence × 上月需求变化 + 有界行业冲击
基础市场活动量 = 上月活动量 × (1 + 行业需求变化)
技术采用比例 = 上月采用比例 + 新采用比例 - 退出或替代比例
行业产品需求 = 基础市场活动量 × 技术采用比例 × 单位活动产品用量
```

周期可以用带持续状态的阶段机实现：扩张、减速、收缩、修复各有虚拟持续时间分布与需求变化区间。阶段只影响需求、价格或成本输入，不规定公司利润必然涨跌。阶段变化写入环境事件并保留随机结果。

技术扩散可使用 `新增采用 = speed × adoption × (ceiling - adoption)` 的候选关系，校验参数以保证不越界；零采用率由启动事件处理。采用接近上限后仍可有替换需求或总市场扩张，不强制整家公司衰退。

例如“辆／月 × 新能源采用比例 × 千瓦时／辆”得到电池需求“千瓦时／月”。已经包含采用比例的新能源车辆量不得再乘一次采用比例。医疗、房屋、电力等需求使用自己的单位和驱动，不强套汽车公式。

### 3. 报价、竞争与需求分配

每个业务单元根据前期成本、库存、订单和策略提出报价；需求分配在同一产品与地区的市场内进行：

1. 计算价格、质量、渠道和品牌的标准化响应。响应函数采用配置明确的分段曲线，避免不明 0～1 评分直接乘利润。
2. 把各项响应组合成非负吸引力权重，并保留外部竞争者或“不购买”的选项。
3. 用权重占比分配需求，总量不超过市场需求池；整数数量用最大余数法分配，相同余数按稳定业务单元标识处理。
4. 分配量只是候选需求；经过合同、客户条件与交付能力校验后才能成为订单。
5. 无法承接的需求按既定规则保留为未满足需求或延后，不无限循环重分配直到全部卖出。

归一化只分配同一个需求池，不保证所有公司都增长。历史实际市占率按真实销量另算；不能把候选份额直接写入已实现销售指标。

售价提高通过价格响应影响需求；产品组合决定汇总 `ASP`。量增、提价与产品升级分别解释，不能在平均售价之外再重复加一次“产品结构收益”。

### 4. 经营预算和资源分配

月初预算只形成行动计划，不动现金。每天执行前重新检查资源：

```text
可用现金 = 账簿现金 - 已有合法占用
先处理已到期的普通义务
再按本公司的明确优先级处理可选采购、研发及扩产
每个行动：
    校验实际现金、已获授信、设备和材料
    资源足够 → 生成付款或已允许信用采购事件
    资源不足 → 记录未执行、缩量或延期结果
```

研发与扩产谁优先属于公司政策配置，不设全体公司统一的隐含顺序。只有可拆分计划才能缩量，明确数量的不可拆分操作需要拒绝或延期。授信只有按合同真正提款后才成为可用资金。

已经发生的劳动、服务或合同义务形成应付款；尚未执行的可选研发不凭空形成债务。经营困难可以导致缩减投入和真实违约，不通过自动融资保证持续增长。

### 5. 制造与产品模块

制造模块依次处理排产、资源占用、产出、交付与成本结转：

```text
可排产量 = min(计划量, 材料可支持量, 设备工时可支持量, 已获资金支持量)
合格产出 = 根据实际投入、工艺和良率计算
交付量 = min(到期且可交付订单量, 当时可售库存)
期末库存 = 期初库存 + 已完成合格产出 - 交付 - 报废及其他出库
收入 = Σ(满足确认条件的交付数量 × 合同净单价)
```

多产品共用产线按预先确定的排产优先级占用工时，一份工时不能被多个产品使用。产出按完成日期进入库存；需要陈化、认证或验收的对象未满足条件前不能交付。

例：期初可售 100 件，当期新增合格品 40 件，符合交付条件的订单为 120 件，可以交付 120 件。不能因本期产能为 40 件就限制只能销售 40 件。

成本归集复用存货和固定资产子账。收入减营业成本是毛利；收入减所定义变动成本是贡献毛益。制造固定成本与折旧已进入营业成本的部分，不能在营业利润下再扣一次。闲置成本、异常损耗等按明确会计规则处理。

设备建设按真实付款和工程进度形成在建资产，达到使用条件才增加产能、转入固定资产并开始相应折旧。不能支付后马上无限增加产能，也不能将资本开支和折旧同时全额计入当期费用。

### 6. 研发、品牌和客户关系模块

研发项目状态采用“立项 → 进行中 → 阶段评估 → 下一阶段／成功／失败／暂停”的状态机。每个项目记录目标、阶段、已投入、剩余工作、最早评估日期、所需资源和结果分布。

```text
本期有效工作 = min(剩余工作, 实际资源投入 × 对应效率)
剩余工作 -= 本期有效工作
若完成工作且达到阶段时间条件：
    按本阶段条件抽取一次结果
    成功 → 进入下一阶段或登记技术成果
    失败 → 记录终止、损失及可能保留的知识
    延期 → 生成明确新增工作或新的检查日期
```

项目完成不直接增加收入。形成的新产品仍经过认证、客户采用、产能和销售流程；授权业务按合同处理。费用化、资本化、摊销和减值由会计条件决定，不由“研发成功”标签直接决定。

品牌、渠道、技术及客户关系使用各自慢状态更新：

```text
期末状态 = 期初状态 - 已发生衰减或流失 + 本期验证有效的增量
```

实际投入只提供产生增量的机会或条件，不保证成功；状态有明确单位或定义域。营销失败可以只有费用没有品牌提升，客户增长也可能伴随维护成本上升。

平台业务使用“触达 → 转化 → 活跃／留存 → 真实交易或服务 → 收费”的链条。网络效应作用于触达、转化或单位获客成本，不能直接把用户数转为现金。

### 7. 客户、回款与违约模块

普通客户使用统一算法但拥有独立状态：现金、经营收入支出计划、债务、逾期记录。重要客户增加个体参数；不扩展为完整上市公司。

经营现金来源按预先配置的外部业务计划或实际交易生成，计划与待偿债缺口无关；只在到达事件日期时入账。给外部来源起名字不能替代资金规则。如果交易对手也在系统内，必须实际扣减对方资金；未模拟的外部经济边界须在事件中明示。

```text
对每个付款人：
    执行当期允许的实际经营收支
    按(原到期日, 登记序号)遍历已到期债务
    payment = min(可用现金, 剩余债务)
    在一个事务中扣付款人现金、增加收款人现金、减少债务和对应应收
    未清偿部分保留原到期日和逾期起点
```

现金不足不是技术错误，不回滚已经合法形成的部分付款，也不重新抽收入补缺口。同一付款事务的双方更新要么都成功，要么都不生效。

信用减值、核销和债务免除是不同事件。核销可以减少债权人的账面应收，不自动删除付款人的债务；后续回收依据核销记录记账，不重复确认原销售收入。事件标识及已处理状态阻止重试重复回收。

### 8. 行业专属模块怎么执行

这些模块共享事件、账簿和结算接口，但各自计算业务，不共用一条利润公式。

| 模块 | 计算步骤 | 输出及边界 |
| --- | --- | --- |
| 项目开发 | 购地和开工 → 分期开发及资金投入 → 预售与合同负债 → 满足交付条件 → 收入及项目成本结转 | 按项目批次保留成本和进度；预售不是利润，借款费用按规则资本化或费用化，减值单独处理 |
| 银行 | 更新实际存贷款合同 → 按计息基数及日数计息 → 实际收付 → 更新信用损失和资本、流动性约束 | 净利息收入为利息收入减利息支出；NIM 从平均生息资产派生；贷款支出受已建模的资金和授信约束 |
| 保险 | 按合同处理承保、保费收款与服务期间 → 赔付事项 → 准备金或合同负债计量 → 投资与收付 | 接现有保险处理器；保费不全等于当期收入，准备金不等于现金支付 |
| 资源 | 根据矿体和工艺排产 → 扣减相应储量 → 产出库存 → 实际销售 → 成本、折耗和税费 | 品位、回收率和储量单位明确；产量不等于销量，单位价差不是净利润 |
| 券商 | 已发生经纪量与费率 → 资管合同及平均受托资产 → 投行业务履约 → 自营持仓计量与收付 | 经纪收入不得与现有费用重复生成；AUM 不属于公司自有现金，自营收益不能直接按指数增长率发钱 |
| 公用事业 | 可用装机与运行时数 → 来水／燃料及调度约束 → 发电和上网电量 → 对应售电合同计量 | 功率乘时间才是电量；市场电价与受管制价格分开，检修和资源不足影响产出 |
| 多业务／一体化 | 各单元完成业务 → 配对内部供货 → 汇总外部收支 → 按主体与合并范围抵销 | 内部利润不能重复变为集团利润，一体化不保证降低全部风险 |

其中可直接采用的计算关系是：

```text
银行净利息收入 = 各资产合同利息收入之和 - 各负债合同利息支出之和
年化 NIM = 期间净利息收入 / 期间平均生息资产 / 期间年占比
经纪收入 = Σ(合同计费基础 × 适用费率)
基础资管费 = 平均计费 AUM × 年费率 × 合同期间年占比
售电金额 = Σ(已结算上网电量 × 对应合同电价)
资源销售收入 = Σ(实际销售数量 × 对应销售价格)
```

计息和年占比使用各合同的日数口径，不统一默认为 365。零分母指标明确不可用。税费、折旧、信用损失等通过会计过程影响利润，不能在上述金额之后统一重复扣一次。

放贷能力不是 `资产 × 比例`：分别检查可用资金、风险加权资产、监管资本及合同约束。若未实现某监管约束，应显式登记简化，不能声称完整银行仿真。设备、医药、器械等认证与审批也采取相同原则。

### 9. 如何形成利润和现金流

每一项业务事实生成业务事件和会计分录。报告从账簿汇总，不允许生成报告后反向修正经营状态。

| 事件 | 主要财务影响 |
| --- | --- |
| 交付并满足收入确认条件 | 收入与应收／现金；同时结转对应成本 |
| 客户付款 | 现金和应收变化，无第二次销售收入 |
| 发生研发或服务 | 按条件确认费用、资产或应付；付款另记 |
| 设备购建 | 现金／应付与在建或固定资产；以后按规则折旧 |
| 借款提款 | 增现金、增债务，无营业收入 |
| 偿还借款本金 | 减现金、减债务，不当作费用 |
| 实际发生利息、税费、减值 | 进入各自适用的会计期间和科目 |
| 合并与内部交易 | 按正确范围抵销，不重复计算资产与利润 |

现金余额来自真实收付，经营、投资和筹资现金流分别分类。可选的 `Free Cash Flow` 必须标明定义，例如经营现金流减现金资本开支；它不是可分红金额，也不直接套用银行。

不同公司的生命周期由需求、竞争、资源、产品和资金约束自然变化。所谓成长、成熟或周期下行，是对结果和机制的解释，不是每月替换公司类型来规定利润曲线。

### 10. 初始化和一轮完整例子

初始化按以下顺序执行：

1. 选择业务模块、产品和公司参数。
2. 指定现金、设备、库存、项目、债务等期初事实及资金来源。
3. 指定品牌、技术、渠道等非账面经营状态，不自动确认为资产。
4. 建立期初账簿与子账，校验资源数量及金额对应关系。
5. 建立债务、合同、到期调度和随机状态，再进入自然日推进。

禁止仅根据净资产反推全部产能。相同资产规模可以来自大量现金、工厂、地产项目或贷款，不能强制获得相同收入。

一个虚拟制造情景：本月承接可交付需求 120 件、期初可售库存 20 件，现有资源只支持新增合格品 80 件，因此实际最多交付 100 件。每件合同价 100 元，确认收入 10,000 元；剩余 20 件按订单条款延期或取消。

假设已售货物成本为 6,000 元，另有本期费用化研发 2,000 元和销售费用 500 元，则在没有其他损益、利息与税费时，税前结果为 1,500 元。客户当期只支付 6,000 元，则尚有应收 4,000 元；实际现金变动还要扣除当期真正发生的采购、研发等付款，不能用 1,500 元直接加现金。

若下一月客户补付 4,000 元，现金改善但不再次增加销售收入。若研发成功，也先形成技术或产品状态，经过后续经营才可能带来收入。该例同时说明需求、交付、收入、利润和收款的不同含义。

本轮只读检查确认：`company/operations` 已有逐自然日经营编排，`company/scheduler` 已有到期队列，`session/company_operations` 将经营接到 CivilClock 日结；`accounting` 已有账簿、存货、应收、固定资产与报告模块。存在这些模块不代表本文全部机制已经实现。

普通到期队列不能代替财务事件幂等记录：原队列来源 key 出队后可再次使用，需要另以业务来源及已处理事实防止重复过账。新增实现不能仅凭“调度器没有待办”推断该业务从未执行。

### 2. 实施次序及交付条件

| 顺序 | 交付物 | 可观察结果 |
| --- | --- | --- |
| 1 | 父目录封装、两个实现目录、共同模式及严格状态恢复 | 上层只依赖父层；新局可选、局内不可切换、错误模式拒绝 |

| 验证对象 | 最小有意义案例 |

| 因子或原材料名称 | 作用对象与建模口径 |
| --- | --- |
| 经济增长 `GDP growth`、通胀 `inflation`、消费信心 `consumer confidence` | 作为虚拟需求或价格环境；未建完整宏观经济核算时，不把生成的增长因子称为已核算 GDP |
| 利率 `interest rate`、汇率、能源成本 | 分别作用于具体浮息合同、币种敞口和生产投入，不能统一重复扣利润 |
| 商品价格 `commodity prices`、资源敞口 `commodity_exposure` | 保留品种、计价单位和购销方向；同一价格对上游销售与下游采购的影响不同 |
| 房屋需求 `housing demand` | 按区域、产品与期间作用于销售机会及价格，不直接覆盖交付收入 |
| 股票市场活动 `stock market activity` | 分别记录实际成交额、客户资产、融资业务和发行承销活动；本局不存在的业务不伪造为已发生 |
| 新能源技术渗透 `EV penetration` | 与汽车总需求、单车电池用量及公司份额分开 |
| 半导体资本开支 `semiconductor capex` | 影响设备需求，经过订单、验证、交付才产生收入，不与当期芯片销量等同 |
| 医疗需求 `healthcare demand` | 区分患者用药、医院设备采购、预算与采购时点 |
| 电力需求 `electricity demand` | 与发电资源、调度、售电合同及价格共同决定业务 |
| 市场容量 `market_size`、增长 `market_growth`、潜在市场 `potential_market` | 明确产品、区域、量纲和期间；潜在总量不等于当期可服务或已成交需求 |
| 竞争 `competition`、进入壁垒 `entry_barrier`、监管 `regulation` | 通过进入退出、认证、报价及业务许可等具体机制生效，不能只给利润乘一个系数 |
| 行业周期 `cyclicality`、技术进步 `technology_progress` | 表示供需与技术环境的变化；与公司自身技术能力、产品更替及市场周期区分 |

#### 公司机制与派生指标

| 机制／原材料名称 | 类别与作用位置 | 口径及防止重复计算的要求 |
| --- | --- | --- |
| 需求增长 `demand_growth`、`Market Growth` | 环境输入，影响需求基数 | 明确月度或年度，与行业 `market_growth` 同义时复用同一事实 |
| 渗透率 `market_penetration` | 市场状态，影响可服务需求 | 与公司市占率分开；同一技术的采用比例与客户覆盖比例不能混用 |
| 市占率 `market_share`、`Market Share` | 需求分配状态或实际销量派生值 | 定义市场边界，不独立配置互相矛盾的候选份额和实际份额 |
| 品牌 `brand`、`brand_power`、`brand_stock` | 持续状态，影响认知、留存和价格响应 | 品牌评分如采用须说明意义，不自动成为无形资产 |
| 定价能力 `pricing_power`、`Pricing Power` | 需求弹性、竞争和差异化共同表现 | 与品牌影响不重复叠加；提高报价会影响需求 |
| 稀缺性 `scarcity` | 可用供给、陈化周期、资源及准入约束 | 尽量从约束表达；供给减少不保证收入或利润增加 |
| 客户黏性 `customer_loyalty`、`customer_stock` | 客户关系与留存状态 | 活跃客户、合同客户和潜在客户分别定义，忠诚度不保证付款能力 |
| 渠道 `channel_strength`、`distribution`、`distribution_stock` | 可触达客户、地区及销售网络状态 | 建设和维护有成本；与用户触达和品牌作用区分 |
| 全球化 `globalization`、海外份额 | 地区业务与渠道组合 | 收入分地区计量，考虑汇率、准入和物流；不单独产生增长奖励 |
| 技术 `technology`、`technology_stock`、`Technology` | 产品性能、工艺和技术积累状态 | 可能过时或被替代，不等同于全部可资本化研发资产 |
| 研发能力 `rnd_capability`、`R&D capability` | 项目执行资源与经验 | 与本期研发预算分开，不能仅按支出金额保证技术突破 |
| 研发强度 `rnd_intensity`、`R&D` | 预算政策或实际投入比例 | 目标比例与实际支出分开；收入为零时比率不可直接使用 |
| 研发时滞 `rnd_lag`、`time_to_next_stage` | 项目阶段时钟与条件 | 时间经过不等于完成；投入中断后的推进规则须明确 |
| 研发管线 `rnd_pipeline`、`rnd_projects`、`rnd_stock` | 同一组项目事实的集合与汇总 | 不保存三份可独立改变的重复项目资产 |
| 研发成败 `success_probability`、`accumulated_rnd` | 虚拟结果分布与累计投入事实 | 累计投入不能重复累计，概率需有阶段与条件，不冒充真实校准 |
| 专利与竞争 `exclusivity`、`competitor_count` | 产品／项目的权利范围和竞争状态 | 独占期限、地域与替代品不同；有专利不等于无竞争 |
| 产能 `capacity`、`fab_capacity`、`production_capacity`、`Capacity` | 设备、产线与可用加工能力 | 按产品及期间表达，投产、停机和共享设备约束一致 |
| 产能依赖 `capacity_intensity` | 业务结构对内部产能的依赖 | 外包、采购与自制分别建模，不再以无单位分数重复放大产量 |
| 利用率 `utilization`、`Utilization` | 产量相对可用产能的派生结果 | 零产能时明确不可用，不另外抽取利用率并覆盖实际产量 |
| 资本强度 `capital_intensity` | 资产配置、扩产投入及派生比率 | 分清资产／收入、资本开支／收入等定义，不用一个值表示所有含义 |
| 单位成本 `unit_cost`、`Variable Cost` | 产品成本输入或成本核算结果 | 单位、产品与期间一致，不把单位成本直接减总收入 |
| 固定成本 `fixed_cost`、`fixed_cost_ratio`、`Fixed Cost` | 特定期间及活动范围内的成本 | 固定成本金额与其占比不是两笔支出；停产和扩产后可改变 |
| 效率 `cost_efficiency`、`productivity` | 工时、材料耗用、良率与流程 | 效率改进有来源和边界，不与降本参数重复奖励 |
| 库存周期 `inventory_cycle`、`Working Capital` | 在制品、陈化、库存批次及周转结果 | 生产等待时间与财务存货周转天数分开；不是无单位的 0.95 |
| 回款周期 `receivable_days` | 合同账期或实际回款统计 | 两者分开；平均天数不覆盖具体逾期起点与部分偿付 |
| 杠杆 `leverage`、`Leverage` | 债务事实、派生杠杆及融资政策 | 实际杠杆与目标杠杆分开，不自动按目标补借款 |
| 资金实力 `capital_strength` | 现金、授信条件、资本和债务的综合描述 | 权益、可动用现金与未提款授信不能相加为可花费余额 |
| 周转效率 `asset_turnover` | 收入相对相应平均资产的派生值 | 期间与合并范围一致，不反向强制生成收入 |
| 利率敏感度 `rate_sensitivity` | 具体资产负债合同的利率暴露 | 固定／浮动、重定价时点分别处理，已计合同利息后不重复扣罚 |
| 宏观敏感度 `economic_beta`、`Cyclicality` | 需求、价格或成本对环境的响应 | 指明响应对象，不等同于股票收益率的市场 beta |
| 信用风险 `credit_risk` | 客户、合同或贷款的风险与收款状态 | 概率、预期损失、不良贷款、实际欠款和现金流分别记录 |
| 一体化 `vertical_integration` | 业务单元之间的供货与控制关系 | 用内部交易和外部净敞口表达，不作为天然降低风险的常数 |
| 网络效应 `network_effect` | 用户触达、转化、留存和获客成本反馈 | 有竞争、饱和及服务成本，不能把用户增长当现金流入 |
| 管理 `management`、`Decision` | 预算、定价、扩产、融资等决策规则 | 不使用“管理优秀”直接乘利润；结果依实际约束和经营事件产生 |

原材料最后概括的 12 个因子也都在表中保留：`Market Growth`、`Market Share`、`Brand / Pricing Power`、`Technology`、`R&D`、`Capacity`、`Utilization`、`Variable Cost`、`Fixed Cost`、`Working Capital`、`Leverage` 和 `Cyclicality`。这些是阅读与配置维度，不要求恰好 12 个代码字段。

不同产品的件、吨、千瓦时不能直接相加；金额、比率和时间不能共用一套无单位评分。标签仅从允许访问的事实推导，不透露尚未公开的公司状态。

### 3. 计算口径修正与可替换细节

- 原文的 `Sales = min(Demand, Capacity, Inventory)` 改为生产受资源约束、交付受当时可用库存约束；当期产能不限制旧库存销售。
- 原文的“收入减可变成本等于毛利”改为贡献毛益；财报毛利按营业成本计算，固定制造成本和折旧只归集一次。
- 原文的“研发不是费用”改为经营侧形成管线与技术状态，会计侧按条件费用化或资本化；不保证投入即产生能力。
- 原文的“资产直接初始化全部经营状态”改为共同配置经营资源与资金来源，再建立一致账簿。
- 原文的“一体化必然降低波动”“工程研发必然低风险”“公用事业必然稳定”改为可由业务和风险条件检验的结果。
- 原文的“产能乘来水就是电量”补入时间和物理约束；NIM、增长率和费率补入期间与年化口径。
- 原文的“十余个因子覆盖所有公司”保留为组织方式；不宣称少量样本已穷尽现实业务。
- `Binary R&D`、`Incremental R&D`、`Frontier R&D` 分别指阶段成败、渐进改进和门槛突破，可在同一项目组合，不固定为三类行业。
- 并购增加合并收入须有真实对价、资金来源、控制时点与范围变化，不全解释为内生需求增长。
- `State_t + Environment_t + Decision_t + RandomEvents_t → State_{t+1}` 是第三章的状态转移思想；报表来自会计事件。`cyclical_company_profit -= random()` 及 `Assets → Scale → RandomProfit` 是仿真模式不采用的反例；简单模式可以统计化生成营收与开支，但按第二章从这些项目计算利润，不再独立随机覆盖利润。

具体默认增长率、噪声幅度、研发结果分布及行业政策参数尚未定为最终产品参数；两种模式的上层功能集合必须一致。本文已经给出它们的接口位置、单位和执行步骤，实施时应以显式配置和短测试固定，而不是埋入不可解释常数。涉及真实会计或交易制度的细节，沿用正式规范并核验适用的官方依据；本文不充当法源。

### 4. 讨论沿革与关联文档

讨论形成三项决定：参考公司采用可叠加机制解释；同时保留轻量基本面生成与丰富经营仿真；新局选定实现且同一局不切换。简单模式可以省略客户、产能和研发等内部过程，但必须提供与仿真模式相同的上层功能、完整财务结果与股本行为。最新确认采用营收及开支百分比变化驱动利润，仅展示汇总账面财务、不追踪真实公司资金流向；此前 `SyntheticFunding` 提案和“简单模式可因缺少现金或报表而不支持功能”的方案均取消。用户允许可编辑、按 seed 复现且明确标注虚拟的默认参数预设，并允许初始化时由股价、股份数量及明确虚拟估值倍率反推基本面初值，改善开盘的初始匹配。营收、开支与税务仍一致推导利润；后续不按股价重锚，不生成共同正确股价或强制撮合稳定，不保证开盘没有涨跌。不使用真实统计，不将算例自动作为默认数值。`company/` 作为公司领域入口，`environment` 只表示各实现需要的环境输入，不再用 `economy/` 包办两套公司系统。
