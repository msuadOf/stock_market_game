**What you'll get:** 股票模拟引擎改为并行架构并附实测提速证据——同一只股票内交易严格排队，不同股票和不同账户可并行运转；**密封操作（成交/撤单/拒单/竞价完成/日界）产生的资金释放与入账在下一密封批次才可用，报价过期释放是例外（在本批次截点前即可用）**；游戏行为除**明确登记的九条分歧**（时间粒度、托管预留口径、**卖单费用封顶于所得（你已裁定）**等）外保持 A 股语义。

**Why this approach:** 买单预留资金，卖单预留可卖股票；撮合只操作本股票的托管资产，不同步等待其他实体或获取跨实体业务锁。实现唯一的并行代码路径（不建串行参考版本），正确性风险由跨线程数、调度扰动、新旧语义投影对比及守恒检查共同控制。这些检查提供测试覆盖范围内的验证证据，不构成整个系统正确或绝无死锁的数学证明。

**What it will NOT do:** 不迁移旧存档（旧档会被明确拒绝）；不预设提速幅度（只报实测）；不承诺跑满全部 CPU 核心或绝对无死锁；**除分歧 #9 明确批准的"卖单费用实收封顶与卖单零现金预留"外，不改变 nominal 费用函数、税率、最低佣金累计口径、买方费用语义及 T+1、集合竞价、涨跌停等 A 股规则本身**；不引入消息队列或 actor 框架。

**Effort:** XL
**Risk:** High - 引擎 tick 全流程重构且无独立串行参考；语义漂移风险由 扰动门禁 + 语义投影语料 + 双账本资源守恒 + 保留语义测试 控制
**Decisions to sanity-check:** 分配截点 `seal_allocation_snapshot`（**post-P0 预算公式**，无独立释放项；卖单现金占用恒 0，预算只减买单占用）；envelope 为资源向量、双账本（封前/密封）分资源守恒、聚合=逐键方程求和；**卖单费用封顶于所得（用户已裁定，分歧 #9）：本腿实收 = min(累计应计 − 已实收, 本腿成交额)，分项按 佣金→印花税→过户费 优先级拆分，deliver ≥ 0、spent.cash 恒 0、卖单预留恒 0；接受差异双向如实登记（旧预留 > 可用现金时旧拒新收；旧预留 == 0 时零现金接受相等）**；**买单价格改善差额逐次释放**（同现行公开行为）；**终结转移一律清零**；收据来源 tagged（SealedIntent|P0Expiry|Auction|DayEnd）+ 每来源因果序号（时序按构造安全）+ 收据链校验；P3 产 `EnvelopeDraft`、溢出即类型化中止（无事件泄漏）；事件源索引唯一序数映射；策略状态 `StrategyState` 唯一权威（profile 派生、封闭注册表、无 downcast）；比较键双侧可派生（固定规则 + 穷举 match 编译器强制 + 逐 tick 身份/载荷多重集比较；帧内数组重排不构成新分歧）；任务 2 全绿骨架（各实现批次按 TDD 先红后绿；进入共享集成基线前须测试与独立审查通过）；类序保留 `npc → player → plan_chain`；毒化仅类型化失败；双哈希回滚；worker 内拒单消耗 ID；跨 envelope 同 tick 撤单取消；不加自成交限制；WASM 保留多线程；不建串行参考（用户已定）。

## Scope
### Must have
- 账户预拨托管（资源向量 envelope）→ 股票独立撮合 → 收据结算的完整闭环，含部分成交、撤单、过期、集合竞价、日界；**双账本转移方程完备**（封前 P0 账本 + 密封批账本，cash 与 shares 分别守恒，聚合 = 逐键方程求和）。
- **单一并行实现**：阶段化 tick 管线 + 阶段边界 rayon 并行（native 与 wasm 同一并行代码路径），不建独立串行参考版本。
- `step()` 返回 `Result`；**毒化仅覆盖类型化失败与不变量违规**（panic 不承诺恢复）；**全阶段 shadow 化（含策略影子竞技场）+ `commit_tick` 单点权威提交**；双哈希回滚判据；静默点存档 v2（含全量策略状态），旧档显式拒绝。
- 三宿主（web-wasm / server / desktop）致命错误映射 + TS 类型再生。
- 确定性三重门禁：跨线程预算（1/2/4/auto）+ 重复运行字节对等；**带收据的执行顺序扰动对等**（防空转 + 负对照）；**重构前语义投影语料对等**（每分歧定向场景 + 字段级允许变换 + seq 结构化比较器含旧侧派生比较键，排除 9 条已批准分歧）。
- envelope 双账本逐键守恒 + 账户聚合守恒（同公式）；实测性能证据（重构前后同机同种子对比）。
- 诊断基线迁移说明与全新 source-fingerprinted K7 矩阵（94 次执行 = 85 canonical + 9 determinism rerun；包含链校验 + 独立根目录核验脚本）。
- ADR-0017 + 分歧台账（9 条）+ **数据流契约**（见任务 2）先行。
- 每批完整 diff 的独立 subagent 审查及修复后复核；顶层任务汇总组件、接线与原有验收证据（AGENTS.md 大 A 语义门禁）。

### Must NOT have (guardrails, anti-slop, scope boundaries)
- **不得实现独立的串行参考引擎或双代码路径**（用户明确免除；预算=1 的并行运行即对照基准）。
- engine 内不得引入 channel/actor/线程所有权框架；跨实体不得加锁或阻塞发送。
- 不得做旧档迁移器；不得删除用户旧存档文件。
- 不得承诺或"验收"绝对无死锁、跑满核心、新旧输出整体字节一致、具体提速幅度——禁止出现在文档与提交信息中；性能只报实测。
- 不得静默增删自成交（STP）策略、T+1、集合竞价决胜、涨跌停；**除分歧 #9 批准的卖单实收封顶与卖单零现金预留外，不得改变 nominal 费用公式（佣金/印花税/过户费的应计函数、税率、最低佣金累计口径）与买方费用语义**。
- 不得用 grep/日志冒充测试运行证据；不得伪造性能数字。
- worker 不得分配全局 OrderId/seq；FIFO 不得取决于线程调度、锁竞争、hash 迭代序或墙钟。
- 不得宣称跨预算对等即"语义正确性证明"；分歧 #6 的 seq 差异必须用结构化比较器核验（含旧侧派生键），不得用通配忽略。
- 市场 tick 的业务权威状态只能由 `commit_tick` 提交（含 P0 过期与 P2 策略执行——一律 shadow）；类型化失败仅允许写入既定 poison/错误元数据，并验证业务哈希不变。自然日日结按已批准 CivilUpdate 契约走独立 `end_civil_day` 边界，不伪造市场 tick 或移入撮合提交。下文同类“单点提交”限制均指此市场 tick 边界，不豁免自然日更新自身的校验与错误交付。
- 基线采集只允许**新增**采集 harness（不改既有引擎源码）；业务重构不得早于语料封存。
- 策略决策语义不得因 `StrategyState` 序列化而改变（往返必须逐字段等价）。

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: TDD（项目铁律）— 每个实现批次先写失败测试再实现；框架 = cargo test（Rust）+ pnpm types:check（TS 契约）。
- Evidence: .omo/evidence/escrow-parallel-engine/task-<N>/（attemptDir = .omo/evidence/escrow-parallel-engine/）。QA 命令须核对实际符号和用例数，筛选命令运行 0 个测试不算通过；记录真实退出码，不能用 tail/grep 的成功退出覆盖上游失败。
- **保留语义测试按四类清单管理（任务 2 冻结 `b_test_inventory` 入 manifest；任务 3 交付 `preserved-test-inventory.md` + hunk 级校验器）**：(a) 源码与断言**逐字节不变**的测试（校验器断言 diff 为空；费用/T+1/竞价/笼子/整手零股/Money 舍入的主体，买侧与终态语义）——必须在线程预算=1 与 auto 两档通过；(b) 预留数值/费用实收断言受 #9 影响而修改的测试（**与冻结清单逐一精确比对（文件/符号/#9 效应 ID/允许变换），缺失/新增/改类/扩大输出失败码（ADDED/MISSING/RECLASSIFIED/EXPANDED）并使任务 3 不通过**）；(c) 仅因存档 v2 / step() Result / 事件形状而重写的测试（**allowlist：仅 API/schema/Result/事件形状构造；触及预留数值/可用现金计算/接受断言/决策链输出/场景输入的 hunk 强制归 (b)**）；(d) **校验器**：`preserved_test_baseline_sha`（规范时点 = 任务 2 第 0 步、干净工作树验证后、任何既有源码/测试修改前；校验器验证提交存在且为祖先）对当前工作树 `git diff <sha> -- packages/engine/tests`，拒绝未预期未跟踪替换；**每个被修改的既有测试符号/hunk 必须有类别，(b)/(c) 须带分歧编号与理由**——**不得使用无范围"不经修改"的总称断言，也不得只做文件名级清单**。
- 确定性验证分层：**调度一致性**通过跨预算、重复运行和带收据的扰动对比，验证已覆盖执行条件下的结果一致性；**语义正确性风险**由四类语料（对等：旧预留==0、无欠费前缀、无反馈；#9 隔离定向：预留、接受翻转及实收差异；受控存活卖单：枚举的 #9 费用/预留/余额及 #7 表示差异；现实压力：新引擎确定性/守恒/安全）、保留测试清单和双账本检查共同提供受限验证证据与验收门禁。有限测试不证明所有输入及调度下的整体正确性，两类证据不得互相冒充。**"零人工干预"范围 = 验证命令的执行与判定；F1-F4 后的最终完成声明确认是独立的人工确认点**。压力语料不提供历史行为保真的证据，不得作超出测试覆盖范围的声明。
- 回滚判据：`business_state_hash`（仅排除 poison/错误元数据，失败 tick 前后必须相等）+ `session_state_hash`（仅允许 poison 字段差异）；字段枚举入 ADR。
- 每批改动由未参与实现的 subagent 独立审查完整批次 diff（大 A 语义、必要性、边界漂移），发现修复后复核；一个顶层任务可包含多个批次，只有汇总全部批次复核、接线复核及原有验收证据后才能完成（docs/principles.md + AGENTS.md）。

### Parallel execution waves
> 2026-09-20 用户批准的调度调整：8 条实现线 + 1 名集成负责人 + 2 名独立审查者 + 1 名专职验证者 V1，总并发上限 12（包含主协调 agent 与全部后代）。本节替代原先“任务 3 全部完成后才能开始 4–6”的开发顺序；仅调整工作组织，不改变 ADR-0017、九条分歧、运行时阶段顺序或任何验收标准。

- Wave 1（基础证据核验与复用）：保留任务 1 → 2 的 ADR、基线封存和骨架门禁。先确认现有成果及保留测试校验器状态，复用已完成实现，不重复采集或重写封存证据。
- Wave 2a（接口与所有权）：集成负责人基于当前代码固定可编译的候选、已校验操作/envelope、股票输出/收据、结算输出契约；逐线登记具体文件、共享接口版本、输入输出、针对性测试及交付条件。已有 `P2CandidateBatch`、`EnvelopeReceipt`、ledger/transition API 优先复用，新增类型名称不在本计划预定。按下文“开工前放行”区分契约准备与真实依赖开发；满足对应条件的实现线立即开工，不等无关上游组件完成。
- Wave 2b（并行组件开发）：下表八线各自按 TDD 实现并验证组件。构造输入只能用于组件测试，不能替代真实会话接入证据。任务 3 的保留测试增量门禁仍约束受保护改动，账本组件随所属联合批次独立验收，不作为同批候选接线的逐组件审核前置；真实成交、撤单、竞价、跨 tick 守恒留在集成验收，任务 3 顶层勾选保持未完成直至原有全部要求通过。
- Wave 2c（持续集成）：集成负责人按下文联合批次协议持续组装候选实现，批次测试与完整 diff 独立复核通过后才纳入已验收基线；尽早在真实 `GameSession` 测试中贯通下单→撮合→收据→结算→提交，再覆盖部分成交、撤单、竞价与跨日。局部闭环只证明已覆盖场景；隔离候选路径须等完整 P2–P8 输出与失败边界就绪，由 P9 单点提交；对用户启用的正式切换还须通过任务 8 的存档/恢复门禁（见下文依赖边界），并移除旧兼容桥的重复路由/撮合/结算调用。不得新增另一套串行参考引擎或长期双业务路径。
- Wave 3（存档/宿主）：任务 7 的组件可在 Wave 2 并行，整体验收须完成 3–6 接入与失败注入；任务 7 前置是 3–6 的运行时接入及其所需失败边界证据，不等待依赖存档的顶层验收；任务 8 仍在任务 7 完成后实施；任务 7 的运行时接入/三宿主验收可在隔离候选版本完成，不以前置正式切换或存档 v2 完成为条件。任务 3 的审计历史存档、任务 6 的竞价余单恢复子验收在 8 完成后回填，3/6 顶层在此之前保持未完成。宿主接入由集成负责人分配已空闲实现线，不增加并发上限，不挤占未完成的关键接线。
- Wave 4（证据）：任务 9 在 3–8 整体验收后执行完整确定性/性能门禁。
- Wave 5（收口）：10 与 11 的核验工具开发/预检可并行；10 及 11 核验脚本的相关改动合入稳定快照后，才运行 11 的最终 94 次 K7 矩阵 → 12。全部任务完成后 F1–F4 并行，所有原有终审条件保留；最终验收须核对证据源码指纹，后续改动影响既有门禁输入时重跑受影响门禁。

| 2. 放行与派工 | 对已冻结的联合交付安排批量独立审查，对同批契约固定的组件允许候选接线，对已审整批放行验收基线；按 API/文件/WIP/席位及资源条件，非阻塞续派返修、就绪批次及 V1 请求 | 优先解除关键路径，其次完成积压集成，再启动独立工作；不等所有线一起就绪 |
| 3. 实施接线 | 选择一项就绪的联合接线批次，在隔离候选副本先写真实 GameSession 场景再并行补齐整链实现；同批未审依赖按联合批次协议使用，不等每个 wrapper 单独获批 | 每个可交付切片必须有实际补丁、可观察测试或明确缺口；不能反复只读接口却不推进 |
| 4. 冻结与交接 | 把联合修订、完整 diff、依赖指纹、场景清单与实际已知失败交独立 reviewer，同时将批量验证请求交 V1；二者可读同一冻结输入并行执行，失败未清不得通过 | 在另一个副本准备下一就绪切片，或解除上游缺口；不继续改正在验证的快照 |
| 5. 接纳与重排 | 按原门禁确认准确修订的测试和审查结果，再更新已验收集成基线；核对真实接线行为而不只看组件绿灯 | 放行依赖、释放完成批次的 WIP，检查原任务剩余验收；只有全部满足才勾选 |
| 6. 无可做事项 | 执行下文等待前检查；有解除阻塞的在途作业才有限等待，无在途解除者则明确报告真实缺口 | 唤醒后回到步骤 1，不直接再次 wait |

- **保护 main 的实现时间**：完成一轮必要的收取/派工后，就进入步骤 3，不靠反复 `list_agents`、重读 plan、重写证据维持忙碌。main 同时只主动编辑一项接线批次；已冻结的上一批验证可与下一批准备重叠，仍按所涉及各线的两批 WIP 计数。通知到达不要求打断半个补丁，但在下个安全边界及时处理；依赖失效优先暂停相关写入。若全部接线输入都未就绪，明确选择一项可解除阻塞的共享契约/集成夹具工作；没有则按步骤 6 处理，不虚构工作。
- **交接即释放执行席位**：worker 交付被冻结的批次后，若无已分配且就绪的独立工作，结束本轮；reviewer 给出结论后亦结束本轮，不能一直等返修。main 根据最新结论对已结束者用 `followup_task`，对仍运行者用 `send_message`。结束轮次不删除会话、文件或批次 WIP；后台作业存在时须明确移交作业监护与收取者，不允许无人收取退出码。
- **派工最小回执**：复用“开工前放行”的完整字段，另明确本批结束条件和返回给谁；main 自身的接线批次也登记相同边界。收到“组件通过”先核对具体修订/测试/独立复核，不能仅凭 agent 的完成标签放行。收到 NEEDS FIX 将发现汇入本批修复清单并分派属主，不让 reviewer 实现自己的修复，也不扩大批次范围；独立问题并行修，共享入口问题由 main 逐项修。
- **接线推进顺序**：先用真实玩家路径逐段贯通到 P9，再覆盖 NPC/计划链、成交/撤单、竞价/日界、跨 tick 与失败回滚；这是集成验证的优先次序，相关组件和独立场景仍可提前并行，原有阶段/失败/宿主门禁一个不少。某段依赖阻塞时切到已就绪且可独立验证的场景，不要求等待整线完工。生产切换仍由 Wave 2c 放行，局部闭环不授权半成品入口上线。
- **进度汇报**：有实质变化时报告本轮接通的场景、已审/待审/待构建/返修批次、实际开发/验证/等待数量、main 的下一动作和阻塞属主。无变化则指出仍缺哪项证据，不以 agent 数量、测试总数或耗时冒充完成比例。测试/审查成为瓶颈时先处理队列与资源，接线成为瓶颈时 main 回到代码；不通过增开无关任务掩盖瓶颈。

### Main agent dispatch and blocking wait protocol
> 本节明确 Codex 的操作选择，适用于每轮交付、审查返回与等待唤醒；只约束开发调度，不改变游戏阶段、验收依赖或交易语义。工具名与参数以当前会话实际提供的 schema 为准。

| 条件 | 主 agent 必须执行的动作 | 是否等待子任务完成 |
| --- | --- | --- |
| 有就绪批次、接口与路径已确认、资源及 WIP 允许，且需新席位 | Codex `collaboration.spawn_agent` 创建有明确交付的小任务；返回 ID 后继续派发其他就绪工作或集成 | 否；创建返回不代表任务完成，禁止紧接无条件 `wait_agent` |
| 合适的既有 subagent 已结束本轮，仍有可做批次 | 用 `collaboration.followup_task` 续派并触发下一轮；记录新批次与归属 | 否；优先复用，不为同一职责重复创建 |
| 运行中的 subagent 需要补充接口、修复要求或状态信息 | 用 `collaboration.send_message` 通知；主 agent 继续其他工作 | 否；`send_message` 不会唤醒已结束的 agent，已结束者须用 `followup_task` |
| 某一条线等待接口、测试或审查，但其他线或主 agent 有可推进事项 | 派发其他就绪批次，或由主 agent 固定共享接口、准备接线测试、集成已批准组件、处理审查发现 | 否；局部阻塞不能升级为全局等待 |
| 全部可执行事项均受真实依赖、资源或安全快照边界阻塞，且有在途任务/作业能解除阻塞 | 完成下述等待前检查后，调用 `collaboration.wait_agent`；等待后台命令则使用该命令返回的作业 ID 和配套等待工具 | 是；每次阻塞最多 60 秒，完成通知或新消息可提前唤醒 |
| 无可推进事项，也没有能解除阻塞的在途任务/作业 | 明确报告阻塞、所缺输入及解除条件；需要用户输入时提出具体问题 | 不反复调用 `wait_agent`；无人执行的任务不会因等待自动恢复 |

- **等待前检查（每次必做）**：main 必须在当前摘要记录 `等待对象/修订、解除属主、在途作业、下一次解除后动作`，并逐项核对：①已审组件或同批固定契约组件能否候选接线；②固定契约能否编写下游实现/独立夹具/场景；③能否处理已有批次的接口、证据或返修；④空闲席位是否有就绪任务。可执行者先做；不可执行者写准确的 API/文件/WIP/资源原因，不能仅写“等 reviewer”。引用已有未变记录即可，不重复建账。等待返回先处理通知；同一原因连续两次等待返回仍无进展时，main 必须核对实际作业输出及依赖图，决定继续有证据的在途作业、拆出独立准备任务或按“有界升级”处理。只调用 `list_agents` 不算完成此检查；不得为避免等待而把未审内容放入已验收基线或开第三批；同批未审候选接线按联合批次协议执行。
- **等待记录与唤醒**：在现有调度回执中注明等待哪一批/哪一作业、具体依赖、解除负责人、以及其他席位无可执行工作的原因；同一等待原因可引用并更新原记录。每次 `wait_agent` 返回后都先处理通知并重做等待前检查，不得直接连续 wait。超时不等于卡死，也不等于通过；没有进展时核对真实阻塞并沿用有界升级规则，不用重复探索或重复测试填充并发。
- **交付即重新排程**：组件、审查和验证结果均触发 Main agent operating loop；本轮 `completed` 不是顶层任务完成。按该节释放/续派席位，不能把已结束任务长期计为运行中。
- **子 agent 同样避免空等**：每次创建、续派及上下文交接均附当前计划版本、文件归属、接口状态、验证环境和等待规则，不能假定旧会话自动重读计划。交付冻结批次 A 后，只能继续已分配且符合隔离/WIP 条件的独立批次 B；无可执行工作则交接并结束本轮，由主协调安排审查与续派。确需等待在途接口/作业时同样每次最多 60 秒，先报告对象与解除条件；不得用反复短 wait 替代交付结束，也不得自行越界接任务。
- **约束优先于补满席位**：不以“保持 12 个 running”为目标。12 席位、每线最多 2 个未集成批次、模型/强度适配、独立审查与资源限制全部保留；冻结快照验证不得与同一源码快照写入并行，需持续开发则先隔离。主 agent 自己的共享接口/接线工作不能全部转化为“等 worker”。
- **omo 对应操作**：在 omo 中仅用实际支持的 `task(..., run_in_background=true)` 或等价后台续派；Codex 使用上表原生工具，不传不存在的 `run_in_background` 参数。后台派发仍需等待工具返回任务标识，但不等待子任务执行结束；现有“等待期间推进下一项”条款按本节条件执行。

### Pipelined delivery and overlapping waits
> 2026-09-20 用户批准：开发组织改为有边界的联合批次流水线（替代逐 wrapper 等审核的串行交付），重叠模型请求、测试、审查和集成的等待时间；保留上述 12 席位及模型分工。本节的“批次”是开发交付批次，不是游戏 `TickBatch`，不改变运行时 tick 顺序、单点提交或任何原有验收门禁。

- **开工前放行**：每批写明可观察交付、原任务/涉及 L 线、独占文件、共享入口负责人、模型/强度、API 契约、隔离候选副本及验收场景。跨已关闭批次复用验收实现；同一联合批次内允许依照固定契约并行编写生产者/消费者、调用尚未单独验收的实现，由 main 在隔离候选源码统一注册和组装。缺失符号/尚未实现可作为该候选批次的真实红灯，不得伪装断言失败；不得污染其他批次或已验收基线。接口变化通知全部同批消费者，一起更新；行为未定的领域规则不能借批量开发自行裁定。

- **验收场景前置**：在红灯实现前把该批承诺转成具体输入与可观察断言。按涉及范围覆盖真实非空输入、完整 key/owner/intent 载荷、同账户多输出序号、失败原子性、跨 tick 累计状态和类型化错误分支；策略预算须验证消费 P1 密封值，不从后续可变 shadow 重算，同批撤换释放不回补。仅适用场景纳入该批，不重复所有顶层矩阵。跨层或有争议的契约先安排有限范围语义复核，结论稳定后实施；参与设计者不再担任该批最终独立审查者。不得用空输入、零测试或仅旧路径测试证明新路径行为。
- **生产接线优先**：协调者维护一条明确关键路径，逐项列出真实生产入口、所需组件/接口、阻塞属主、联合接线批次与端到端场景。复用已批准成果，在同批固定契约下提前组装未审接缝，遇到缺口纳入当前联合批次的必要子任务，同时派发其他独立工作；不能持续增加外围组件而不推进闭环。每轮交接报告已通过的真实路径终点及下一缺口；只到 P3 的测试明确标为部分接线，后续按联合批次固定契约扩到 P4/P5/P6/P7/P8/P9，不能停留在测试骨架。独立复核期间主协调继续下一就绪接线准备；证据整理优先复用空闲席位，避免挤占关键路径实现和复核。先在隔离集成快照用真实 GameSession 和组件贯通下单→校验→撮合→收据→结算→提交的定向场景，再扩展跨 tick、竞价/日界与失败场景；这不是提前启用不完整生产路径或新增串行参考。正式切换仍按 Wave 2c 的完整阶段/失败门禁执行，禁止同一操作同时经过新组件和旧桥重复执行。每次交付后重排关键路径，集成待办计入所属线 WIP；既有批次 A 的接线、接线审查和返修均属于 A 的生命周期，不另加一次批次计数，达到两批上限时仍可推进 A 集成以释放名额。真正独立的新接线批次才计入其涉及线的新 WIP，已满时不得开启；不能以换 agent 名字逃避积压限制。
- **交审前场景核对**：实现者在批次记录逐项关联“承诺行为 → 测试符号/输入 → 断言 → 实际结果”，不适用项注明原因，main 核对场景与断言已写入，再集中派审核和验证；允许结果尚红或存在已登记缺陷，全部修复前不得 APPROVE。接线批次必须覆盖其实际涉及的：session 配置/时钟的非默认值（T+1 false/true 为配置接线测试，不改变对外 T+1 规则）；跨股票相同 local index 的身份隔离；账本/结算重复收据按既有唯一性契约类型化拒绝、不得重复结算（仅已批准的投影重放契约检查其身份键与副作用幂等，不能将其推广为 P5/P6 重复收据静默跳过）；前阶段成功后后阶段类型化失败的整体原子性（逐容器/游标校验）；错误变体、专属 location 与实际上下文值。只测各组件各自失败不能替代接缝失败。保留原 TDD 红灯命令与原始结果，编译阻断如实标为未进入断言，不伪造历史红灯。缺场景则先补；测试实现与业务实现仍属同批，初次批审可报告真实失败，不以“reviewer 会发现”作为省略断言的理由；此核对不替代独立完整 diff 审查。
- **联合批次交付**：以一条可验证端到端行为作为交付单位，允许多线组件、适配器、wrapper、模块注册与接线一次写齐；不为每个函数、注册动作或纯格式修订单独建立串行审核链。内部可做小步 TDD/提交，整批必须有边界、完整 diff 与可定位的失败清单。不得把所有剩余任务合成无法审查的大包；一旦达到本批固定场景就冻结，不不断追加无关能力。

- **最小交接记录**：在现有任务 evidence/notepad 中记录批次 ID、属主、准确文件、依赖批次/接口版本、基线及当前源码指纹、完整批次 diff、先红后绿命令/结果、异步作业 ID、审查状态、集成状态及阻塞。复用现有记录和后台任务机制，不为本次调度另建调度器、消息队列或守护进程。
- **流水线状态与放行**：`场景/契约固定 → 隔离候选批量实现及组装 → 整批冻结 → 独立完整 diff 审查 ∥ V1 批量验证 → 按失败清单修复/复核 → 纳入已验收集成基线`。候选组装不要求同批每个组件先单独 APPROVE；测试通过与独立复核通过仍是验收基线放行的共同前置。正式启用继续等待原有完整阶段、存档及后续门禁。审查者至少一人覆盖整批完整 diff 且未参与该批设计/实现；可由第二 reviewer 并行检查高风险部分，不能把碎片审查拼成无人负责的整批批准。

- **等待期间推进下一项**：只有独立批次 B 已分配、接口就绪且验证隔离/WIP 允许时，实现者才在 A 验证期间开发 B；协调者优先接入另一已批准批次或解除关键路径。否则按 Main agent dispatch and blocking wait protocol 交接结束或有条件等待。完成通知触发结果处理；无通知能力时有界查询，不忙轮询。
- **下游提前准备**：统一遵循“开工前放行”；同一联合批次契约固定即可编写下游真实接线，不限于纸面方案或夹具。批次之间有真实依赖时，未验收内容不能冒充已批准基线；需要共同调试的上下游应在开工前显式归入同一有边界批次，保留原子任务映射与每线 WIP，不靠事后改名绕过积压。

- **源码和构建隔离**：默认在独立 worktree 或等价源码副本中开发与验证批次，复制必要的未提交/未跟踪源码、依赖与配置并记录基线/完整输入指纹；不能只从 HEAD 建副本后遗漏现有成果。A 测试/审查读取冻结快照，B 继续开发须在另一可写副本。相关并行 Cargo 作业使用独立 `CARGO_TARGET_DIR`、输出/端口/存档目录；只分 target 不能隔离源码，源码隔离也不免除 CPU/内存排程。若环境不能隔离，协调者显式安排同一验证输入的单写窗口与冻结验证窗口：写窗口内暂停该输入的其他测试/审查，验证窗口内禁止相关源码写入，其他线转做不冲突工作。返修同样遵守独立副本或已登记的单写/冻结窗口，在稳定输入上完成红绿与冻结；不得在未隔离且未登记窗口的共享树直接跑红测，定向测试也不豁免。禁止把一条线的缺失 API、缺失模块或红灯测试污染其他批次/无关线；同批登记的红灯允许在稳定输入按需检查，无变化时不反复重编；模块注册由 main 在联合候选副本内统一准备；组件组装期间允许登记中的红灯，但与该输入冲突的构建/审核须停在冻结窗口，独立线继续。隔离副本不授权任何 agent 越过共享文件属主或覆盖他人改动。
- **修复和证据归属**：A 失败时形成 A 的新修订快照，保留原失败结果；不得修改正在验证的 A 或把旧版通过结果归给新版。接口/行为修复影响 B 时立即暂停受影响消费者并标记其证据待更新，修复后重跑相关测试和独立复核。无关线继续推进；旧证据可作参考，不替代最终集成版本验证。
- **限制积压**：每条实现线最多同时有 2 批已开始但未完成集成验收的工作（包含开发、等待测试/审查和待集成批次）。达到上限后优先修复、补交接或协助解除已有批次阻塞，不再开第三批；跨线联合批次计入每个参与线。取消/合并批次须明确记录，不能靠改名绕过上限。审查和集成优先处理阻塞下游的最早就绪批次，避免实现产出堆积成另一条串行长队。
- **资源排程**：12 是 agent 并发上限，不是重型编译数量；全量和局部作业均按下节 V1 规则分配资源。独立审查者亲自复跑的定向命令保留，排入资源窗口；性能测量独占规定资源，暂停干扰对比的编译/压力任务。构建锁、磁盘配额或其他批次编译失败记为“验证阻塞”，不算本批通过或语义失败。不得用重复构建填满席位。
- **进展展示与完成边界**：递归统计主协调与全部后代，分别列出实际开发/审查、等待工具/构建锁、已结束待续派及未派发；`running` 或历史会话总数不能冒充有效并行度。按批次展示测试快照、审查与集成状态、最近实质产出、阻塞属主，并报告最近一次真实接线推进，而非只报单测数量。任务 8 开工、任务 9 全矩阵、F1–F4 与生产切换仍遵循原计划；组件通过不能替代顶层验收。

### Dedicated verification seat and build scheduling
> 2026-09-20 用户批准新增 V1；总上限 12 包含主 agent、全部子孙 agent 和 V1。新增的是验证执行职责，不增加实现线或放宽两批 WIP。下述规则统一约束前后各任务的 QA/验收命令：原有覆盖要求保留，执行属主与资源排程按本节；旧定向命令的 target 限定按下述等价映射处理。

- **执行边界**：主协调、L1–L8、审查者自行执行限定文件的格式/静态检查、选定 target 的检查及定向 unit/integration tests；全包/全 workspace 构建、完整回归、完整宿主构建和最终矩阵统一提交 V1。任务属主仍负责设计场景、修复失败和解释结果；V1 不写业务实现，也不以命令绿灯签署独立语义 APPROVE。F1–F4 各自结论仍由原终审者给出，F3 真实 Web 操作不委托 V1 代替。
- **局部不等于廉价**：Rust 单元测试通常仍需编译整个 crate 及依赖，`cargo check` 也不是纯语法检查。按实际冷编译、链接和缓存状态判断开销，不能因命令带过滤词就绕过资源限制。模块单测采用 `cargo test -p engine --lib <实际过滤词>`，独立集成测试采用 `--test <实际 target> <过滤词>`；旧 QA 中未带 target 的过滤命令先定位全部匹配用例及其 target，逐项转换为 `--lib`/`--test` 并记录与原覆盖的等价映射；包含 doctest 或其他 target 时保留对应执行，不能只挑其中一个 target 冒充完整覆盖。无法确认等价范围时交 V1 运行原命令。原定完整回归命令不缩减范围。执行后检查目标用例确实运行且数量符合预期；格式/静态检查不替代行为测试或 TDD 红绿证据。
- **生成型验证**：冻结基线保持只读；`types:check` 等会先生成文件的命令在从该基线建立的可丢弃验证副本运行。记录运行前后源码、生成文件与 lockfile 差异，按原检查契约判断；需要纳入交付的生成差异交属主作为新修订修复并独立复核，不回写冻结基线，不把运行中改变后的输入冒充原指纹。输出日志和构建产物写入登记目录。
- **统一构建契约**：V1 与协调者一次登记工具链、manifest/lockfile、features、target triple、profile、RUSTFLAGS、Cargo jobs、格式配置及对应源码指纹；实现者与 reviewer 沿用相同基准，确需变更则记录原因与失效证据。edition/style edition 从对应 crate manifest 与仓库 formatter 配置解析，不能凭默认值或 reviewer 偏好在 2021/2024 间切换。限定文件格式检查传入解析后的有效配置；全仓库格式门禁由 V1 按项目命令执行。禁止仅为隐藏 warning 改 RUSTFLAGS 或创建新 target 重编；保留原始日志，展示时摘要告警，不吞退出码。
- **冻结交审协议**：按“属主完成场景/测试编写、格式化并记录已运行检查和已知失败 → main 固定基线及完整批次 diff → 创建不可改的完整输入快照（或登记等效冻结窗口） → reviewer/V1 确认同一快照与配置 → 开始检查”执行。输入清单覆盖所需源码（含未跟踪文件）、模块注册、依赖清单/锁文件、构建脚本、工具链和格式配置，不只哈希本批两个文件。优先使用物理副本，复制在输入稳定窗口进行，复制前后核对清单一致，否则重新冻结。环境无法隔离而使用已登记冻结窗口时，原输入同样具备完整清单/指纹，直到验证结束禁止任何人写入该输入；不能同时在该输入开发 B，其他不冲突工作可继续。reviewer/V1 只对给定路径和快照标识验证，不临时从共享树补文件。开始及结束检查输入清单，除“生成型验证”明确登记的输出外不得变化。共享树后续独立改动不否定真正冻结副本，但接纳/合入时须核对依赖，变化则形成新的集成修订。
- **快照或格式分歧处理**：哈希不符立即拒收该输入，暂停相关批次放行；不能边改冻结目录边补跑并把结果改名为“合并快照”。确需合并则新建修订、完整输入清单及受影响门禁。格式结果矛盾先比较 rustfmt 版本、manifest edition、style edition、配置路径、工作目录及精确命令；在统一配置的可写副本由文件属主格式化一次，再冻结。V1/reviewer 不格式化共享文件。纯格式差异可经 diff 证明后缩小复核/重跑范围，但不能宣称旧哈希测试在新哈希上重新执行；原要求全量验证的里程碑仍保留。
- **资源配额与缓存**：初始同时最多 2 个重型作业（全量和局部冷编译合计），其中全量最多 1 个；这只是保守起点，V1 据可用 CPU、内存、磁盘/用户配额及实际峰值登记调整，性能验收仍独占。V1 在现有资源记录中登记固定 target 路径、属主、工具链/配置指纹、占用作业、最近使用及保留/回收原因；无在途占用且配置兼容时，顺序验证新的源码修订复用该 target，让 Cargo 正常增量失效。reviewer 保留自己的独立 target。批次完成或 agent 结束本轮不构成清理理由，禁止默认“新建 target → 验证 → 删除”；不同并发源码副本不共享可写 target。检查可用空间和配额，而不只看 `df`；无法查询配额时注明未知，发生配额失败先停止放行新的重型作业并定位。复制源码前核对大小并排除已登记的 target、`.review-targets` 及其他实际构建/缓存目录；不能仅排除名字叫 `target` 的目录，也不能误排除构建所需源码或配置。磁盘不足先限流和核查占用，再由 V1 只回收确认没有在途作业使用、归属明确的过期构建产物，保留冻结源码、diff、日志与哈希；回收须登记确切目录、属主确认或已结束作业证据；进程不可见不能证明无人使用，无法确认则不删。资源恢复有证据后才重试，不能通过换目录不断重试，不能删除他人未交接产物。必要的关闭增量/调试信息等配置调整由 V1 统一登记，正式验收和性能 profile 不得悄悄降级。
- **异步申请与公平排队**：复用 evidence/notepad 和原生消息，不新建调度服务。请求包含批次/修订、冻结输入指纹、命令及期望用例、工具链配置、目录归属、是否需独立复跑、优先级与解除的依赖；提交请求后即可继续独立工作或交接结束，不为等 V1 回执阻塞；main 负责追踪未确认请求，收到 V1 作业/队列标识后更新摘要，未获资源放行不得自行启动重型作业。关键路径返修和接线验收优先，随后已就绪组件与其余门禁；不能无限插队饿死既有请求。等价且同指纹/配置/范围的普通请求合并；要求 reviewer 亲自复跑的独立验证不能由实现方日志替代。V1 为这些局部复跑分配资源，reviewer 自己执行；独立完整复跑由未参与实现的 V1 执行并供 reviewer 核对。
- **红绿与验收分层**：组件开发仍先红后绿，内部修复可在联合批次内集中进行，整批独立复核；不要求每个组件先单独完成审核或全量回归才允许同批候选接线；有明确全量验收要求的批次/顶层任务仍等 V1 结果。V1 在相关稳定集成快照和原定里程碑执行完整门禁，不能用局部绿灯替代任务 2、任务 9、最终 K7 等原有完整要求。构建成功不代表测试通过；证据记录真实退出码、测试数量、源码/配置指纹与失效范围。失败交回对应属主返修，新修订重跑受影响门禁，旧版成功不得归给新版。
- **V1 生命周期**：协调者用非阻塞创建/续派分配 V1，重型作业资源只由一个当前 V1 管理，转交须移交在途作业和队列。无排队请求且无在途作业时结束本轮，有新请求由协调者续派；存在后台构建时继续收取结果并处理可放行请求，不将监护责任留空；不得让空闲 V1 长期 wait。所有席位遵循前述最多 60 秒阻塞及交付后重排规则；局部验证排队不阻塞其他轻量任务。运行中的长构建可后台继续，60 秒限制约束单次工具等待，不要求每 60 秒终止构建。

### Coordination and verification rules
- 集成负责人是共享类型、`session.rs`、`pipeline/mod.rs`、`pipeline/shadow.rs`、模块注册及运行时阶段调度的唯一编辑者。派发前登记每条线的实际独占文件；现有共享文件中的抽取/改动由负责人执行，再交付各线，不允许多个 worker 同时修改同一路径。
- 主协调 agent 兼任集成负责人，复用 8 个实现席位、2 个独立审查席位与 1 个 V1 专职验证席位。12 上限按同时在途的主协调与全部后代计数（包含阻塞等待中的 agent），不是累计创建会话数；平台若另限制保留会话数，按实际槽位约束处理。子 agent 的审查请求统一交协调者；仅经协调者分配空闲席位及独立性后才可创建下级审查者，不得自行递归扩张。角色可以调整，但参与该批设计/实现者不得审自己的批次，调为实现者的原审查席位须另派未参与者复核。
- 审查者 A 重点检查 A 股语义、已登记游戏简化、资金股份守恒与边界测试；审查者 B 重点检查完整 diff、接口一致性、最小范围及重复执行风险。每批改动必须至少由一名未参与实现者审查完整批次 diff，并回答项目规定的三项问题；两人分工不免除完整审查，发现修复后必须复核。最终 F1–F4 仍分别产出所需结论，复用空闲槽位执行。
- 每条线明确区分“候选已交付（未单独验收，列已知失败/未执行项）”“组件已验收 / 集成待验收”“联合集成通过”，附修改文件、接口版本、实际测试/审核结果和剩余阻塞；候选交付可用于同批组装，不能标为通过。只有满足原任务全部 Acceptance/QA 与独立复核，才能勾选顶层任务；不能把八线局部完成等同于任务 3–7 完成。
- 测试与实现同属一条线，先红后绿；已有断言、四类清单、封存基线及 ADR 边界不因并行而放宽。保留测试门禁失败时修复确切问题，不扩大 allowlist 掩盖错误。接口变更由负责人统一通知消费者并补契约测试。
- 组件期间由属主运行针对性测试及受影响保留测试的增量门禁；主协调确定验收范围、源码快照和关键路径优先级，V1 统一安排资源并执行完整测试、完整保留测试门禁、确定性与性能矩阵。快照绑定、并发写入限制与构建隔离统一遵循上文“源码和构建隔离”“修复和证据归属”“资源排程”，不因命令成功退出而省略输入指纹或独立复核。
- 当前执行接续：先盘点全部在途与已交付批次，映射回 L1–L8 和现有 WIP；优先补齐真实接线关键路径的依赖并集成已批准组件，再派发可独立推进的工作。此调度修订不重置 checkbox、运行会话或封存证据，不代表运行中的 agent 已读取。main 在下一安全交接发送当前计划内容指纹、相关规则差异及归属/资源变化；V1 须回执固定缓存路径与当前作业表，reviewer 须回执输入快照/配置，实现者须回执文件归属和验收场景；对方确认前不得把它统计为已迁移，也不得放行受新规则影响的新作业，已有长作业登记后受控收尾，不为改调度规则盲目终止或重复启动。随后按 Main agent operating loop 持续推进。

### Runtime integration, persistence and activation boundary
> 本节明确任务 7→8 的原顺序与正式启用的区别，禁止把存档和生产切换互相设为前置。
