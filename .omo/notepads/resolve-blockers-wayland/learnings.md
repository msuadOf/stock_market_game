## 2026-09-17 Task 7 explicit K7 maximum thread cap (V6)

- `--max-threads <positive integer|auto>` is a cap for `after` and `sensitivity`, distinct from `--batch-size` (which remains a count of charged child executions). Omitted and `auto` select the dynamic budget. A positive value records the requested maximum and uses `min(process_available_cpu_count, maximum)` for `RAYON_NUM_THREADS`; an over-available maximum never claims or creates more CPU capacity.
- Dynamic detection starts with Node 24 `os.availableParallelism()` (Linux affinity-aware), falls back only when it is unusable to host logical CPU count, then tightens on finite cgroup-v2 `cpu.max`. Fractional cgroup quota is conservatively floored to a whole worker with a minimum of one, so `250000 100000` bounds a CPU-heavy Rayon pool to two threads rather than three.
- Policy schema `k7-resource-policy-v3` binds `maximum_thread_count` and effective `rayon_threads_per_seed` into every matrix identity, checkpoint, determinism receipt, and final manifest. Therefore V5 evidence is intentionally source-stale and cannot resume under V6.

Green result: pinned Node 24.18 `node --test scripts/simulation/baseline-run.test.mjs`, 61/61. Engine diagnostics 18/18 and engine example clippy pass. ## 2026-09-17 FIFO write-channel ownership trace

- Authoritative mutable state is session-wide, not per stock: `packages/engine/src/session.rs:946-1003` owns markets/order books, accounts cash/positions, auction queues, pending intents, parent orders, pending plan events, plans, diagnostics, global `next_order_id`/`seq`, and civil clock. `Market` owns one stock book plus last/close prices and limits (`packages/engine/src/market.rs:37-59`); `OrderBook::place` mutates price/time FIFO state and `next_seq` (`packages/engine/src/orderbook.rs:199-220,253-415`).
- Tick routing is a single ordered transaction: `GameSession::step` (`session.rs:1977-2393`) gathers NPC decisions, sorts by `AccountId` (`2086-2173`), appends player intents, routes each intent in that order (`2175-2204`), then runs the belief/plan chain (`2206-2209`), stock-ordered auction/price publication (`2211-2335`), day-end expiry/market close/T+1 unlock/plan day-end (`2338-2391`). `enqueue_player_intent` appends to the session vector for next-tick execution (`session.rs:3658-3679`); this is logical FIFO only, not a concurrent wall-clock arrival contract.
- Continuous routing is not stock-local: `route_intent` (`session.rs:2762-2809`) prevalidates cash/holdings/cage and existing reservations, clones the stock market, calls `Market::place`, then builds fills for both maker and taker (`2876-2974`), settles accounts and revalidates every live reservation before committing the candidate market (`3000-3060`). `settle_order_fills` aggregates by global `OrderId`, then mutates account cash/positions in ordered buy-then-sell maps (`session.rs:3335-3467`). A trade on stock X can therefore mutate accounts that also have orders on every other stock.
- Reservation authority is global: `validate_live_reservations_with` scans all continuous markets and all non-replacement auction queues, aggregates cash by `AccountId` and sells by `(AccountId, StockCode)`, then compares against account cash and T+1-adjusted sellable holdings (`session.rs:3555-3656`). Per-stock writers alone are unsafe because same-account cross-stock orders race on shared cash/holdings and reservation invariants; a coordinator or account/resource reservation owner must serialize or deterministically arbitrate these commits.
- Auction state is also per-stock but commits globally coupled state: `complete_auction` removes that stock queue, preserves price/time ordering by `(Reverse(limit), arrival_seq)`/`(limit, arrival_seq)`, stages remainders, backs up participant accounts, settles, revalidates global reservations, rolls back accounts on failure, records plan/retail/causal facts, and emits completion/trade events (`session/auction.rs:249-549`). Auction phase/cutoff routing is explicit (`session.rs:150-162,2175-2199`); closing auction is non-cancelable and final completion occurs in stock-code order (`2229-2275`).
- Account semantics are authoritative and must remain behind the commit boundary: `Account` owns cash and positions (`account.rs:87-102`), buy settlement deducts fees and adds T+1-locked holdings (`214-269`), sell settlement checks `sellable_qty = qty - t1_locked` and applies fees (`322-375`), and `apply_trade_batch` preserves fee aggregation (`419-457`). T+1 unlock is a session-wide day-end pass over all accounts (`session.rs:2363-2372`), so it cannot be delegated independently to stock channels without an epoch/barrier.
- Plans are cross-tick and account+stock keyed but not stock-owned: `PlanBook` is one global map plus `(AccountId, StockCode)` index and monotonic PlanId (`plans/mod.rs:128-139,239-262`); `apply` is an ordered state transition (`288-319`). Parent orders are session-owned by account then stock (`session.rs:961-963`); child submission/cancellation can cancel/reprice existing working orders, install parent links, allocate global `OrderId`, and synchronously synchronize pending plan events (`session/plan_execution/actions.rs:42-177`). Pending accepted/fill/day-end facts are applied in queue order, with terminal-plan retention and linked-parent removal (`synchronization.rs:46-120`). Thus a stock queue needs a coordinator for account-plan ownership and event application.
- Events/causal order are globally sequenced: every Event carries `seq` (`session.rs:164-239`), allocated by one mutable session counter (`1752-1760`); causal decision indices use the causal fact vector length and are recorded during routing/settlement. A parallel stock worker must not mint independent final sequence numbers or append directly to shared causal/event vectors.
- Proposed safe seam: immutable `TradeRequest` carries `(tick_epoch, producer/logical_source, producer_sequence, AccountId, StockCode, intent, plan/parent correlation)` and is asynchronously enqueued only to the channel for its target stock/entity. At tick barrier, a session coordinator closes the intake snapshot, assigns/validates a deterministic request key, and drains each stock channel FIFO. Per-stock FIFO is deterministic only after enqueue order is defined; MPSC arrival order from concurrent producers is race-dependent wall-clock order and must not be treated as logical FIFO. For reproducibility, producer sequence must be assigned before concurrent enqueue (or requests must be merged by a stable key such as `(tick, source_kind/source_id, producer_seq)`); do not use receive timing.
- Candidate entity key: `StockCode` is the minimum matching-book owner; `AccountId` is a second mandatory resource owner for cash, holdings, reservations, strategies, parent orders, plan state, and T+1. A stock-only channel is therefore insufficient. Use either (a) a single deterministic session coordinator over stock queues plus account/resource locks/validation and ordered commit, or (b) a canonical transaction coordinator that batches all requests, reserves account resources, executes stock-book mutations, settles both counterparties, applies plans, and serially publishes events. Any cross-stock transaction touching the same account must be ordered by a deterministic conflict key, not concurrent wall-clock completion.
- Required deterministic merge key for final event/causal output: `(tick, phase_rank, logical_request_key, stock_code, local_fill_ordinal, event_kind_rank)` where `logical_request_key` is assigned before enqueue; preserve existing global `seq` as the emitted contiguous order. Within one stock retain order-book price/time priority and fill order; across stocks use canonical `StockCode` order where current code does so. Plan events must merge by their originating routed request/fill ordinal, and day-end/T+1/cutoff barriers must follow the existing phase order.
- Conclusion: one FIFO write channel per stock is safe only for isolated book mutation plus immutable result production. It is not safe as the complete authoritative write model. A shared coordinator is required for account cash/holdings/T+1 reservations, cross-stock budget conflicts, global OrderId/Event seq/causal facts, parent orders/PlanBook/pending plan events, auction-to-continuous transitions, day-end expiry and T+1 unlock. Preserve A-share price/time priority, reservation-before-commit with rollback, T+1, auction cutoffs, and causal/event sequence by making the drain/commit barrier synchronous and deterministic.
