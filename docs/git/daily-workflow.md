# 日常 Git 工作流指令

对会修改文件的日常任务，以及用户要求查看或保存本地进度的任务，按以下流程执行。

1. 先检查 Git 状态、当前分支和未提交修改。
2. 将任务拆为尽可能小且独立的改动。若将开始实质性修改而当前位于 `main`、`master` 等受保护分支，创建合适的工作分支：文档使用 `docs/xxx`，功能使用 `feat/<scope>-xxx`，修复使用 `fix/<scope>-xxx`。不要直接向受保护分支提交。
3. 将任务开始前已有的未提交修改视为用户或其他协作者的工作。不得修改、暂存、提交、重置、清理、覆盖或删除它们。只暂存和提交本次任务中你明确新增或修改的文件。
4. 若本次任务需要修改一个已有未提交改动的文件，或无法安全区分改动归属，停止该操作并用中文说明具体文件、风险和可选处理方式，等待用户决定。
5. 按项目要求实施，并运行与改动相称的测试、lint、类型检查或构建。不得为了通过检查而删改测试、弱化断言、静默吞错或伪造结果。检查失败时，如实报告失败原因和已完成部分。
6. 当本次改动完成且相关检查通过后，自动创建一个小而聚焦的**本地**提交。提交信息遵守项目的 Conventional Commits 约定。提交前再次核对暂存区，确认不含敏感文件、构建产物或他人的改动。
7. 最后用非技术语言报告：完成了什么、检查是否通过、是否已保存为本地提交、以及是否需要用户决定下一步。可以附上提交短哈希和分支名，但不要假设用户理解它们。

## 需要用户明确确认的操作

以下操作前，先用一句中文说明将做什么、会影响哪里、是否可撤销，然后等待用户的明确确认：

- 推送到任何远端；
- 创建远端仓库、Issue、Pull Request、Release，或合并 Pull Request；
- 修改历史、强制推送、覆盖/删除/暂存已有修改；
- 解决会改变既有内容的合并冲突。

若用户明确要求“只检查”，则不修改文件、不创建提交、不上传。
