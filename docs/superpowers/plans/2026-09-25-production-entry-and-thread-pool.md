# 单局生产入口与多线程容量实施计划

## 目标

同一局的盘前、连续交易、集合竞价都让本 tick 已就绪的 NPC、玩家及计划请求进入同一交易处理路径。请求来源、账户号、计划号、数组位置和事件号不提供交易优先级。仅在同股订单簿、同账户实际资金或股份争用、以及计划确实依赖前一步反馈时等待。使用 Rayon 原生线程池执行可并行的账户与股票任务；任务数不受线程池容量限制，也不为股票或账户常驻分配线程。

NPC 在 tick `n−1` 完成决策后，把请求随候选原子提交，tick `n` 才受理。玩家在 tick `n` 异步入队，tick `n+1` 的交易入口才消费。撤单交给对应订单簿，全部成交明确反馈业务失败，部分成交撤余量；业务失败通知计划而不使整轮回滚。原有任意命令、请求和挂单条数配额不得恢复。

## 当前证据与缺口

- 三个交易阶段现共用就绪入口与逐股反馈流；计划根观察和 P3/P4 只读输入准备并行，股票完成即可交付 typed 反馈并继续同股计划动作。P3 和计划状态仍由协调线程处理，计划根仍需要复制一个 tick 观察影子；继续优化时要区分真实依赖与协调器成本。
- 计划根已从 NPC 注意力、积极/每日型策略开盘时点与活跃计划观察条件共同启动；无既有计划的积极机构也可在开盘观察并建立当日到期计划，长期价值与防御型策略可跳过每日观察。本计划上次复核价及本人已获知相关资料数参与唤醒。当前仍遍历活跃计划检查价格和资料条件，尚无价格区间反向索引。个人状态在独立根任务中准备，再交回可丢弃的 tick 候选；共享计划簿、母单和待反馈状态不能被当作纯只读请求提前跨过交易反馈。
- 浏览器使用 `navigator.hardwareConcurrency` 初始化 WASM Rayon 池，并允许可选正整数 `threadCount`；原生 server、desktop 复用 engine 的 Rayon 默认池，可用 Rayon 环境设置选择池大小。池大小只限制同时运行的物理任务，不限制订单、账户或计划数量；浏览器 WASM 的 `u32` 参数上界属于接口表示能力。
- 前一阶段源码的三来源活跃 400 tick 同输入单次 1 worker 为 14.163 秒、8 worker 为 8.273 与 8.887 秒；后一轮 8 worker 的原生进程 CPU 为 293%。旧源码覆盖三个交易阶段的 120 tick 输入曾测得 1／8 worker 为 10.227／7.035 秒。当前策略和账本源码在该 120 tick 输入上重测为 46.619／34.577 秒，且实际产生约 13.5–13.9 万笔其他 NPC 留簿委托，不能把旧数字当成当前吞吐。当前源码的这组单次配对约有 1.35 倍整轮加速，仍需继续降低高挂单负载的撮合成本。原始结果见文末；单次数据不代表稳定速度。

## 一次写完整功能的实施单元

1. **线程配置与平台入口。** 核对三宿主是否在实际进程内使用多线程；只在有明确调用入口时提供可选正整数线程池参数。默认由平台和运行时选池大小。配置失败显式报告，不静默退回单线程。不得把池大小用于限制交易任务数、请求数或挂单数。
2. **计划状态与统一就绪入口。** 把根观察的候选及个人状态变更与共享计划簿、母单、待反馈命令的应用分开；在各交易阶段复用同一局部受理路径。计划根和续步各自在真正就绪时加入；只对同一资源冲突建立局部顺序。撤单反馈驱动必要的重算，不让一条计划独占入口。
3. **整轮成本。** 对 P8 决策快照、NPC 队列、P9 候选提交和旧状态释放做结构性精简，避免重复构造与深复制。每个改动以同一源码下整轮 1 与多 worker 的完成时间判断；若多线程仍慢，不能以局部阶段、行数或线程存在作为成功证据。
4. **验证与复核。** 用少量代表性测试核对跨 tick 请求时点、同股价格时间规则、同账户资金/股份、计划撤单反馈、业务失败与致命失败隔离、三个交易阶段和存读档。普通单命令及单 case 以用户要求的 5 秒为目标；确实无法短化的整轮验收采用进程外 5 分钟共享 deadline。真实 NPC、玩家、计划均有活跃委托的负载须交替测 1 与多 worker 的整轮时间，并记录实际线程及 CPU 利用率。最后由未实施的 subagent 审查完整 diff 与 A 股语义。

## 完成条件

代码中没有来源类别固定优先级，也没有因身份编号建立交易先后；三宿主在各自平台进程内通过同一 engine 多线程任务运行。所有业务边界和失败原子性通过必要验证；已删除容量配额未恢复。真实三来源活跃负载的整轮多 worker 速度快于同源码 1 worker，并有完整运行、线程/CPU 和交易正确性的证据。未达到这一点时，计划继续保持未完成。

## 当前进度（2026-09-25）

Web host 已允许可选正整数 `threadCount` 直接配置 WASM Rayon 池；未指定时使用浏览器硬件并发报告值，参数不限制交易请求或任务数。原生端仍使用同进程 Rayon 默认池，可按 Rayon 的标准环境配置选择容量。已删除只供旧原始 NPC 候选适配测试使用的组合路径，生产投影候选与玩家队列的身份校验仍在；NPC 投影观察适配器只编入测试。Web 定向 8 项短测、TypeScript 检查、engine 相关 11 项短测和 engine 编译通过。本批没有改变三阶段计划状态边界，也未取得新的三来源整轮加速证据，因此完成条件尚未满足。

局部受理现只让账户现金链和同账户同股票链各自当前就绪的请求进入对应股票入口，消除了预先为所有请求排股票顺序可能造成的跨股票依赖环；账户内撤旧再下新仍按实际接收顺序。这个顺序在生产入口可验证：玩家只属于玩家账户，NPC 请求在前一 tick 入队，计划根属于对应 NPC 账户并在当前 tick 生成。两条局部受理短测及盘前、连续交易、集合竞价各一条定向测试通过；独立复核撤回了最初对跨来源同账户顺序的疑虑。此项修复不证明计划根与 P3/P4 已完全贯通，也不证明整轮多线程加速；后两项仍是完成条件。

三个生产交易阶段现在共用 `ReadyIngress` 捕获已就绪请求和计划根，并在各自 P3/P4 准备完成后通过同一局部受理逻辑取得首批候选；重复的阶段收件代码和对应旧错误包装已删除。engine 编译与三阶段各一条定向交易测试通过。计划反馈仍依赖阶段现有的 typed P3/P4 续行，阶段间是否还有无关请求等待的屏障、以及真实三来源整轮加速，尚需继续改造与验收。

重新复核旧合批实验时确认了一处当前仍可达的计划状态错误：同向修订目标若小于旧活动子单可能成交的总量，先改计划再撮合会使真实成交落到较小的新目标上，严重时使 tick 致命失败。现在这类修订先请求撤旧；撤单成功后若期间发生部分成交或其他计划变化，不再应用过期修订，而反馈等待重评。若旧单已全部成交、撤单返回业务失败，已完成计划不再接受一次非法的平静观察。三条针对该边界的短测和既有重构/竞价撤单测试通过。正常撤单失败仍是业务反馈；计划何时重新唤醒并在同 tick 续算仍需单独审查，不能把“等待重评”误称为已完成整条计划链的并发调度。

后续复核发现并修复了子单引用问题：部分成交后成功撤余量，会将计划簿与母单的活动子单同时清空；子单全部成交但计划目标尚未完成时，成交事实携带 `child_complete`，计划簿不再保留已经结束的子单。撤单期间计划成交状态变化时，计划按原观察条件在本 tick 重评；撤单因旧单已全部成交而业务失败、计划仍活跃时，也保留失败反馈并重评。普通撤旧换新的过时报价则重新计算账户报价。连续交易和集合竞价的成交事实、Web 存档解析已同步新字段，相关短测与前端类型检查通过。生产 P3/P4 仍有整批反馈屏障，三来源真实活跃负载的整轮加速尚无合格证据，完成条件仍未满足。

三个阶段现把 post-P0 的 P3/P4 初始化输入先从候选会话取出，再用同一局内的 Rayon 线程与计划根就绪准备并行初始化私有协调器；计划根仍只修改可丢弃的 tick 候选，任何一侧失败都不发布权威状态。阶段计时契约升为 v2：P2 是“决策及协调器工作”，包含计划决策、反馈与并行准备的重叠墙钟；P3/P4 各自还包含输入准备与后续实际请求工作，但不另计并行的协调器初始化。单个阶段数字不能推断并行分支各自耗时。engine 编译、三个阶段的失败回滚短测和阶段计时短测通过。这一步不拆除整批反馈屏障，也尚无整轮加速证据。
