# 单局多线程与长期运行实施计划（2026-09-24）

## 目标与边界

一局市场由同一份 Rust 引擎状态推进。账户、股票、到期计划等形成数量不受固定线程数约束的任务；Rayon 把任务安排到运行时线程，操作系统再调度这些线程。业务代码不按实体创建常驻线程；请求在对应账户或股票的受理边界形成局部受理事实，互不冲突的请求无须比较全局先后。浏览器在共享内存 WASM Worker 池内执行；原生 server/desktop 在各自应用进程内执行。Web 线程池使用浏览器报告的硬件并发数；原生端使用 Rayon 默认池。池容量只决定可同时运行多少任务，不限制交易任务数，也不充当业务优先级。账户资源争用按该账户的请求接收事实裁决，不能把 worker 完成或拿锁先后冒充接收顺序；当前三类来源如何在局部受理边界登记仍需代码迁移。

当前阶段没有旧版兼容要求。删除停用的串行路径和只为该路径存在的测试。有效测试留下资金、持仓、价格时间优先、计划依赖、失败原子性、存读档与三宿主协议的行为边界。普通小测单命令和单用例最多 5 秒；确属长期验收的批次最多 5 分钟，并使用多核。

## 实施顺序

**2026-09-25 请求时点与合批复核修订：** NPC 在 `n-1` tick 形成供 `n` 受理的请求；玩家在 `n` tick 只是异步入队，按该账户实际接收先后保存，到 `n+1` 才参加批量交易。当前 `pending_player` 已在下一次 `step` 才取出，但 NPC 仍在同一次 `step` 内生成并进入交易，且三个入口仍把 NPC、玩家、计划分成固定类别顺序。入口应先从前一 tick 的就绪队列取得 NPC 与玩家请求，再接纳当前已就绪的计划命令；来源标签只用于识别，不定义优先级。账户资源争用按该账户真实接收顺序处理；同股委托按适用价格和时间规则处理。无关账户和股票无需确定跨运行顺序，允许并发调度产生不同受理先后；不引入全局递增受理号。

此前两次提前合批的复核结论须拆开看。**真实状态错误**是计划根在请求正式受理前改动计划簿、母单和待反馈状态，及合批时预先为整轮已接受计划单安装母单，可能使随后成交归属或剩余量使用过期状态；这些要靠只读准备、局部写入和按对应 P4 事实应用来修复。**模型允许的结果**是旧单在计划撤单前被别人的委托全部成交，导致撤单业务失败；这应明确反馈“已成交、无法撤单”给计划，不使整 tick 致命回滚，也不阻断无关请求并行。现有 `OrderNotFound` 是业务拒绝且计划会收到报告，但尚不能区分已成交和未知或已撤订单。计划后续动作只在确实依赖该反馈时等待。旧实验的整轮性能也未证明收益，且负载没有刻意覆盖多股活跃计划委托；下一次性能验收必须换用真实活跃交易负载。

**生产改造的接线顺序：**

1. 在 tick 边界保存 NPC 上一 tick 形成的请求，保留生成时的观察版本和目标受理 tick；玩家队列在宿主异步收件，正式验收入队后按本人接收先后保存，并在下一 tick 封口取出。队列及策略状态必须随候选一起原子提交、随存档恢复；失败不能丢请求或让请求提前交易。当前 `enqueue_player_intent(&mut GameSession)` 只覆盖两次 `step` 之间的调用，运行中的异步收件还需宿主入口承接。
2. 让计划根观察返回各账户自己的状态变更和就绪请求，正式应用时只改对应账户及计划；若先前撮合已改变它所读的订单或计划，就用最新业务事实重新决定该请求。请求来源、账户号、计划号、数组位置和全局编号均不授予交易优先级。
3. 三个交易阶段接同一就绪请求入口：账户资源校验只在本账户真实争用时按接收先后处理，股票订单簿按本股适用的价格和时间规则处理；彼此独立的账户和股票交给 Rayon 任务并行。计划的下一命令只挂在自己确需等待的结果上。母单在对应 P4 接受事实到达时安装并复查最新计划，不提前为整轮安装。
4. 订单簿保留足以区分“已全部成交”和“从未存在/已撤”的终结事实；撤单对已成交订单返回明确业务拒绝，部分成交则撤剩余。计划接收该结果后决定自己的后续动作，正常业务拒绝不触发整 tick 回滚；真正的状态、账本或身份不变量错误仍丢弃整个私有候选。
5. 用真实多股活跃 NPC、玩家和计划委托穿过盘前、连续交易和集合竞价，核对账户资源、同股规则、计划反馈、失败隔离和存读档；然后在同一源码、同一负载、默认操作系统调度下交替测量 1 worker 与多 worker 的**整轮**耗时及 CPU 利用率。局部阶段变快不能代替整轮结果。

**当前主链：隔离计划状态，再打通三个交易阶段的局部受理。** `PlanChainOperationBatch::yield_adaptive_candidates` 目前借用整个可变 `GameSession`。`prepare_plan_observation` 已先做成只读，认领及报告效果随后在协调器的当前账户操作位置应用；但 `prepare_next_account` 仍会写个人注意力、关注列表、价格记忆、获知记录及信念，生命周期和后续路由仍会修改共享计划簿、母单、待处理计划事件与诊断事实。`FrozenPlanChainObservation` 只切换账户、盘口与竞价订单，不能隔离这些写入。不能只看最后发出的候选账户和股票，就把提前遍历根计划认作无冲突。下一步要把根决策的写入做成可逐账户、逐计划核对的私有变更，明确每条候选实际读取的版本与等待的 typed 结果；随后让首轮已就绪请求在盘前、连续交易和集合竞价共用局部受理入口。只有同账户资源争用、同股适用价格时间规则及计划真实依赖才形成顺序。全局身份只在业务受理后用于引用，不能让所有请求等待编号或按来源归并。每个完整批次都用生产入口的交易语义、失败回滚和真实活跃委托整轮时间验收；外围成本的局部改善不计作主链完成。

**计划根个人状态所有权批（2026-09-25）：** 本轮把注意力个人流、关注列表、价格记忆、获知状态和信念簿取成账户私有状态，根观察方法只读会话的账户、市场、公司资料、公开信息和时钟等观察输入；根完成后才把个人状态装回本轮私有候选。诊断事实先随根返回，再按原根内顺序写入。计划簿、母单、pending 和后续路由仍在可变 `GameSession`，所以来源屏障没有拆掉。共享 `Arc` 值在取出时仍会复制，`information` 也仍随 tick shadow 整图复制；本批建立所有权接缝，不声称零复制或加速。`cargo check -p engine --all-features`、相关短测和 16 测试线程的引擎库长验收 **732/732** 通过（跳过 53 项会写入现存 `bindings/` 的生成测试）；未实施者独立复核未发现 A 股观察、策略、诊断或回滚语义阻断。五股、20,007 NPC、1200 tick 同场景按旧版 1 → 新版 8 → 新版 1 → 旧版 8 worker 单次交替测得整轮 **37.499 → 35.572 → 35.500 → 38.588 秒**，四次 PASS；原始请求、结果、进程外 CPU 与线程采样在 `.tmp/plan-root-personal-*`。新版 8 worker 最多 9 线程、平均约 2.09 核，整轮与新版 1 worker 几乎持平；每种条件只测一次，不能把跨版本差异归因于本批，也不能宣称已得到单局多核加速。下一步须隔离计划簿、母单和待反馈命令写入，才能让真正就绪的计划请求与其他来源一起进入生产 P3/P4。

1. **宿主入口与旧代码清理。** Web Worker 初始化使用经校验的 `navigator.hardwareConcurrency`；无合法数值就明确报错。初始化失败立即拒绝 `createWorkerHost`。删掉未被生产引用的主线程 `wasm-host`、其源码检查测试，以及未调用且忽略 Promise 的 `init_threads` 绑定。保留真正用于错误报告的 Worker 分类器。原生端继续使用 Rayon 默认池；server 的跨会话 Fastest 信号量先保留，因为它保护 Tokio I/O，待同步计算移出 I/O 执行器时再一起调整。
2. **P6 账户结算。** P5 收据按账户聚合后，每个受影响账户在私有副本上并行结算，同账户同股票仍按 Buy 再 Sell。所有账户及零售经验投影成功后才一次性写回。去掉 P6 的“全账户复制 → 受影响账户再复制”两层复制；随后把零售投影读取改为只访问本次需要的账户，避免重复制全体持仓。验证不同 Rayon 池容量与失败时全状态不变。
3. **删除引擎测试专用串行回退。** 移除 `step_current_behavior` 与只为旧回退存在的构造器、对照测试和兼容桥；仍有真实计划路由调用的逻辑先迁入当前阶段管线，再删除旧入口。保留单一路径的规则测试，不拿旧实现输出当真值。
4. **按真实冲突受理并扩大单局任务。** 玩家、NPC 与计划提出的委托地位相同，来源只供审计。异步请求进入相关账户与股票的受理位置：同股委托按该交易阶段适用的规则受理，并在订单簿中遵守价格、时间优先；撤单按目标订单、所有权和阶段处理，不因同股就把不同旧单的撤销强行排成交易总序；同账户请求实际争用现金或股份时按该账户收到请求的先后裁决；同一计划的后续动作仅在需要前一步 typed 结果时等待。两个账户交易不同股票、互不争用资源时无须建立总序，可以同时计算。每个 tick 封口外部新请求，统一完成本轮适用撮合后一次发布状态。订单、事件、收据和存档身份只负责引用与记录；即使某种输出格式需要排序，也不能把排序放到交易关键路径上，不能以编号决定交易优先级，更不能让所有请求为分配全局递增号穿过单一业务关口。P3 的共享容量限制仍须明确处理，不得借来源、账户号或 worker 完成顺序暗定优先。计划的后续请求在依赖结果产生后才成为就绪请求，不能让某账户整条计划链占住其他请求。

**第 4 步的具体数据流。** 每条请求保留来源身份，并只在它实际触及的账户、股票冲突处登记先后；不为无关请求建立局部位置或全局位置。P3 按账户实际争用的资金、股份和本账户限制处理，账户之间可以同时准备；P4 按股票适用的价格、时间规则处理，股票之间可以同时推进。计划后续命令只等待自己必需的 typed 结果。`P2CandidateKey`、`sealed_index`、`OrderId` 和事件号可用于引用、审计和存档，但不能以它们的跨账户或跨股票大小决定优先权，也不能为了可复现性强制独立任务按编号归并。现行全局挂单数与计划事件槽位是引擎容量限制；若容量不足，它们需要明确政策或整体失败，不能借来源类别和账户编号暗定赢家。

5. **长期运行状态所有权。** 普通 tick 的全量 JSON 哈希已移除；接着消除执行 shadow 的整局复制和其余随历史增长的扫描。改为按实际触及实体的私有补丁、共享只读版本；未来若建立增量摘要，用独立全量检查抽样对照。历史冷热分层与持久化另按 ADR-0018 的待决边界推进。

## 交易语义与待决事项

已接受的 ADR-0017 当前规定 P0 后预算截点、同账户预算仲裁、同股票顺序、收据连续身份与 P9 单点提交；其 `npc → player → plan_chain` 来源类序已由用户在 2026-09-24 明确否定，须迁移为局部冲突顺序。请求可异步受理，状态在 tick 中统一撮合更新；同股、同账户实际资源争用和真实计划依赖才建立交易先后。身份供审计、输出和存档引用，不要求独立请求在不同运行中获得相同的跨实体编号，更不能用重放需要倒推交易总序。当前代码仍保留旧类序，本计划不能把它称为目标行为。ADR-0018 其余旧观察版本、永久历史粒度、旧私有版本期限、崩溃恢复和 2099 年后的规则仍未裁决；不得借并行重构暗中改变这些政策。
