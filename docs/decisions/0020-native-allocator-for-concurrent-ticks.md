# ADR-0020：原生端并发 tick 的内存分配器

- **状态：** proposed
- **日期：** 2026-09-26
- **范围：** 同一局 Linux/macOS 原生引擎的多线程计算；浏览器 WASM 与 Windows 不适用

## 问题

单局交易入口已经让独立股票和账户在同一进程内并行处理，但实际活跃负载的完整 tick
仍可能因内存分配、释放而比单线程慢。订单、策略状态和候选版本在不同线程生成，
提交时又要释放上一版本；这些成本不能从订单簿阶段的耗时推断。

用相同的 20 股、20,007 个 NPC、4 个计划账户、每 tick 一条玩家请求、400 个 tick
的输入运行优化构建，得到以下单次测量（单位：秒，越少越好）：

| 内存分配器 | 1 worker 完整 step | 8 worker 完整 step | 1/8 加速比 |
| --- | ---: | ---: | ---: |
| 系统默认 glibc | 21.13 | 23.22 | 0.91 |
| 临时预加载系统 jemalloc | 15.37 | 12.00 | 1.28 |
| 正式链接 `tikv-jemallocator` | 15.69 | 11.80 | 1.33 |

两次运行使用相同输入指纹 `6b228c4db35963bb`，均产生 NPC、玩家和计划的活跃交易。
P9 旧状态替换阶段在 8 worker 下从 5.25 秒降为约 1.32 秒；P2、P4、P8 也下降。
这些是单次测量，不代表所有机器或负载的稳定加速比，也尚不足以证明高并行目标已完成。

## 决定

Linux/macOS 原生目标由引擎统一选择 jemalloc 作为全局内存分配器，使用
`tikv-jemallocator` 的目标平台条件依赖。浏览器 WASM 与 Windows 不链接该分配器，
继续使用各自平台支持的分配方式。该依赖的已知支持平台是 Linux/macOS；仓库的
Windows MSVC 构建不能被一个尚未验证支持它的分配器阻断。选择发生在进程级内存
管理层，不增加交易优先级、请求容量限制、线程数规则或第二套撮合实现。
Linux/macOS 的服务器、桌面和原生测试/性能样例共用同一引擎设置。

新增这个核心依赖的理由是同输入整轮测量已显示原生多线程分配器是实际瓶颈。
正式链接的构建已复现整轮改善；仍须检查三个交易阶段、计划反馈和失败回滚。
以后变更分配器或执行路径时，要重新测完整 tick，不能只引用预加载实验。

## 边界

- 内存分配器不决定请求何时受理。NPC 在前一 tick 形成的请求和玩家异步入队请求
  仍按 [ADR-0018](0018-long-running-immutable-timeline.md) 的时点进入下一 tick。
- 同股价格时间规则、同账户资金和股份约束、计划依赖、部分或全部成交后的撤单反馈
  均由交易代码处理；更换分配器不得改变这些业务规则。
- Linux 的改善不能当作 macOS、Windows 或浏览器 WASM 的性能证据。后两种平台
  仍用各自分配器；各平台要用真实多线程构建和活跃交易负载另行测量。即使 Linux
  取得加速，距离“极致并行度”仍须看整轮加速比。
